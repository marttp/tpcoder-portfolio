## Why AI System Design Needs a Different Guide

ถ้าจะเรียก model API สักครั้ง ทุกวันนี้ทำได้ง่ายครับ ปัญหาเริ่มตอนเราต้องเอา call นั้นไปต่อเป็น product ที่มีคนใช้งาน

พอขึ้น production เราต้องดูอีกหลายเรื่อง ตั้งแต่ data, API, storage, security, monitoring, cost ไปจนถึงวิธีรับมือเมื่อ model ตอบพลาด และถ้า model เรียก tool ได้ เราก็ต้องกำหนดด้วยว่าเรียกอะไรได้ ทำอะไรได้ และควรหยุดเมื่อไหร่

บทความนี้ผมเลยอยากเริ่มจาก product problem ก่อน แล้วค่อยเพิ่มส่วนที่จำเป็นจนกลายเป็นระบบที่ทีมเอาไปรันและดูแลต่อได้

แกนหลักมี 1 ประโยคครับ:

**Model เป็น component ที่คาดเดาผลลัพธ์ได้ยากกว่าส่วนอื่น ส่วน product จะน่าเชื่อถือแค่ไหน ขึ้นอยู่กับระบบที่เราสร้างไว้รอบ model**

เนื้อหาจะครอบคลุมทั้ง predictive ML, recommendation, RAG, LLM workflow และ agent แต่ไม่ได้หมายความว่า product ทุกตัวต้องมี agent, vector database หรือ train model เองนะครับ เราจะเลือกใช้เมื่อ requirement พาไปถึงจุดนั้น

ตัวอย่างหลักเป็น customer support assistant สมมุติ ช่วงแรกให้ตอบคำถามจาก approved document ก่อน แล้วค่อยเพิ่มการ lookup order และสร้าง support ticket ตัวอย่างนี้มีไว้พาไล่ design เท่านั้น ไม่ได้อ้างว่าเป็น project ที่ผมเคยทำ

ถ้าจะอ่านตั้งแต่ต้นจนจบ เนื้อหาจะแบ่งเป็น 6 ส่วน:

1. กำหนด product และ risk
2. วาง data และ knowledge path
3. เพิ่ม decision และ action
4. พาระบบขึ้น production
5. รวมทุกส่วนในตัวอย่างเดียว
6. นำวิธีคิดไปใช้ตอน coach หรือ mentor คนอื่น

## Part 1: Define the Product and Its Risk

### First, Name the Type of AI System

คำว่า AI system กว้างมากครับ ก่อนวาด architecture ลองบอกให้ได้ก่อนว่าคุณกำลังแก้ปัญหาแบบไหน

| System type | Example | Main design pressure |
|---|---|---|
| Predictive ML | fraud score | feature freshness, accuracy, latency |
| Recommendation | product ranking | candidate retrieval, ranking, feedback |
| RAG | ตอบจาก company document | retrieval quality, grounding, access control |
| LLM workflow | classify และสรุป case | prompt version, evaluation, cost |
| Agent | ตรวจข้อมูลและลงมือทำ | tool, state, permission, recovery |
| Generative media | สร้าง image, audio หรือ video | async job, storage, moderation, GPU cost |

Product เดียวอาจใช้หลายแบบร่วมกัน เช่น recommendation ใช้ predictive model จัดอันดับ แล้วให้ LLM ช่วยอธิบายผล ส่วน support assistant อาจใช้ RAG ตอนตอบคำถาม และเรียก agent เมื่อต้องสร้าง ticket

แต่อย่าเพิ่งเอาทุกอย่างมารวมกันตั้งแต่วันแรกครับ แต่ละส่วนมี metric และ failure mode คนละชุด ยิ่งใส่เร็ว เราก็ยิ่งต้องดูแลของที่ยังไม่รู้ว่าจำเป็นหรือเปล่า

เริ่มด้วยคำถามเหล่านี้:

- output เป็น score, ranking, text, image, plan หรือ action?
- ระบบต้องใช้ private data ที่สดแค่ไหน?
- คน review output ได้ไหม?
- คำตอบผิดมี cost เท่าไร?
- ต้องตอบใน 100 milliseconds หรือรอ 30 seconds ได้?
- model แค่ตอบ หรือแก้ state ของระบบอื่นได้ด้วย?
- rule หรือ normal search แก้ได้ปลอดภัยกว่าหรือเปล่า?

ข้อสุดท้ายอยากให้หยุดคิดสักนิดครับ ถ้า rule หรือ search ปกติแก้โจทย์ได้ปลอดภัยกว่า เราก็ไม่ต้องฝืนใส่ model ใช้ AI เมื่อ value ที่ได้คุ้มกับ uncertainty ที่เพิ่มเข้ามา

ก่อนคุยเรื่อง model ลองเขียนขอบเขตของ product ให้ชัดก่อน:

- input และ output มีหน้าตาอย่างไร
- ต้องตอบหรือทำงานเสร็จภายในเวลาเท่าไร
- failure และ refusal แบบไหนยอมรับได้
- data แบบไหนอยู่ในระบบ และส่งไปที่ provider ได้แค่ไหน
- จุดใดต้องให้คน review
- รองรับ volume และ cost ได้เท่าไร

ระบบรอบ model ต้องตอบได้ว่า:

- input แบบไหนอนุญาต?
- user คนนี้เข้าถึง context ใดได้?
- model และ prompt version ไหนควรรัน?
- timeout แล้วทำอย่างไร?
- output ถูกตรวจอย่างไร?
- quality วัดจากอะไร?
- bad release rollback อย่างไร?
- high-risk action ให้ใคร review?

Model อาจตอบเก่งมากครับ แต่ product ก็ยังพังได้เพราะ access control ผิด, timeout ไม่มี fallback หรือไม่มีใครรู้ว่า release ไหนทำให้ quality ตก จุดนี้เป็นภาพที่ผมอยากให้คุณจำไว้ตลอดบทความ

### Define Success Before Choosing a Model

คำว่า quality ของ AI วัดด้วยเลขตัวเดียวไม่ได้ครับ ต้องเลือก metric ให้เข้ากับผลลัพธ์ที่ product ต้องส่งมอบ

#### Predictive ML metrics

ถ้าเป็น predictive ML คุณอาจดู precision, recall, false positive/negative rate, ranking quality, calibration และ model drift เลือกเฉพาะตัวที่ตอบ risk ของ product ได้

สมมุติว่าเป็น fraud system เราอยากจับ bad transaction ให้ได้มากขึ้น แต่ถ้า false positive สูงเกินไป ลูกค้าที่ดีก็โดน block ตามไปด้วย จะเลือกสมดุลแบบไหนจึงเป็น business decision ไม่ได้จบที่ model score อย่างเดียว

#### Generative AI metrics

สิ่งที่ควรวัดมี:

- task completion
- factual grounding
- citation ที่ถูก
- policy compliance
- helpfulness
- tool-call accuracy
- human acceptance
- cost per completed task
- end-to-end latency

อย่าดูแค่ว่าคำตอบอ่านลื่นหรือเปล่าครับ เพราะคำตอบที่อ่านดูมั่นใจอาจผิด หรืออ้าง source ที่ไม่รองรับคำตอบก็ได้

สำหรับ support assistant เราอาจกำหนดเป้าหมายว่า:

- ตอบจาก approved support document เท่านั้น
- แสดง source ที่ใช้
- refuse เมื่อไม่มี source รองรับ
- customer data อยู่ใน access boundary ที่ถูก
- ส่ง account-specific risk case ให้คน
- ตอบสิ่งที่มีประโยชน์ครั้งแรกภายในไม่กี่วินาที

พอรู้ว่าจะวัดอะไร เราก็รู้ว่า architecture ต้องช่วยรักษาอะไรบ้าง

Design เท่านี้อาจพอสำหรับ writing helper, internal summary ที่ risk ต่ำ, prototype สำหรับเช็กว่าคนอยากใช้ feature ไหม หรือ classification ที่มี output schema ชัด

แม้เป็นเวอร์ชันเล็กก็ต้อง observable:

- บันทึก prompt version

สำหรับ support assistant จุดอ่อนจะเห็นเร็ว general model ไม่รู้ product policy ล่าสุด และอาจสร้างคำตอบที่ไม่มี source รองรับ Constraint ถัดไปจึงเป็น private knowledge ที่มีการ update อยู่เรื่อย ๆ

### Choose Between Prompting, RAG, Fine-Tuning, and Training

4 วิธีนี้แก้คนละปัญหา ไม่ได้เป็น level ที่ทุก product ต้องไล่ตามลำดับ

| ปัญหาที่เหลือ | เริ่มจาก | เหตุผล |
|---|---|---|
| Instruction หรือ output format ยังไม่ดี | prompt และ structured output | เปลี่ยนง่าย ค่าใช้จ่ายต่ำ และย้อนกลับง่าย |
| Model ขาดข้อมูลใหม่หรือ private fact | RAG หรือ normal lookup tool | แยก knowledge ออกจาก model และ update source ได้ |
| Behavior, style หรือ domain pattern เดิมพลาดซ้ำ | fine-tuning | สอน behavior ที่เกิดซ้ำผ่านตัวอย่างได้ |
| Model ที่มีอยู่แก้ core task ไม่ได้ | custom training | ควบคุมได้มากขึ้น แต่ใช้ data และ operation สูงที่สุด |

Fine-tuning ไม่ควรถูกใช้แทน database ครับ เพราะ fact ที่อยู่ใน weight นั้น update, delete, cite และจำกัดสิทธิ์ตาม user ได้ยาก ส่วน RAG ก็แก้ behavior ไม่ได้ทุกแบบ ต่อให้ retrieve document ได้ดีขึ้น model ก็ยังใช้ format ผิดหรือเลือก tool ผิดได้

ผมจะเริ่มจาก change ที่เล็กและย้อนกลับง่ายที่สุดก่อน แล้วค่อยขยับเมื่อ evaluation บอกได้ว่าปัญหาที่เหลือคืออะไร แนวคิดนี้ไปทางเดียวกับคำแนะนำของ Google Cloud เรื่อง [การเลือก fine-tuning และ RAG](https://cloud.google.com/use-cases/fine-tuning-ai-models)

## Part 2: Build the Data and Knowledge Paths

### Predictive ML: Two Connected Pipelines

ถ้าเป็น predictive ML ให้แยกภาพออกเป็น 2 path ก่อนครับ ฝั่ง offline ใช้เรียนรู้จาก historical data ส่วนฝั่ง online รับ request ที่เข้ามาใน production

#### Offline learning path

ฝั่ง offline รับงานที่ใช้เวลานาน เช่นรวบรวม historical data, ตรวจ data quality, สร้าง feature, train model, เปรียบเทียบแต่ละ version แล้วค่อย publish ตัวที่ผ่านเข้า registry

#### Online serving path

ฝั่ง online รับ live traffic งานจึงต้องสั้นกว่า ตั้งแต่รับ request, ดึง feature ล่าสุด, run inference, ใช้ business rule แล้วคืนหรือเก็บ prediction จากนั้นค่อยบันทึก outcome ที่เกิดตามมา

จุดที่ต้องระวังคือ 2 path นี้ต้องเข้าใจ feature แบบเดียวกันครับ ถ้า training คำนวณ feature แบบ A แต่ serving คำนวณแบบ B model ก็จะเจอ data คนละหน้าตาเมื่อขึ้น production ปัญหานี้เรียกว่า training-serving skew

Feature store ช่วยให้ทั้ง 2 ฝั่งใช้ feature definition และ serving path ร่วมกันได้ แต่ยังต้องดู data version, transformation code, missing value และ time boundary อยู่ดี มี feature store แล้วไม่ได้แปลว่า training-serving skew จะหายไปเอง

### Batch, Streaming, and Feature Pipelines

Data ที่ใช้กับ AI มักเข้ามา 2 ทาง:

- **Batch ingestion** อ่าน data ก้อนที่มีขอบเขตตาม schedule เหมาะกับ historical training, daily report และ backfill ขนาดใหญ่
- **Streaming ingestion** รับ event ตอนเข้ามา เหมาะกับ fraud signal, live recommendation, monitoring และ fresh online feature

หลายระบบใช้คู่กัน daily batch สร้าง training dataset หลัก ส่วน stream เติม recent user activity

ไม่ว่าจะเลือกทางไหน ingestion path ยังต้องรองรับ schema validation, event/processing time, duplicate, late/out-of-order event, replay, backfill, retention, lineage และ access control

ส่วน feature pipeline มีหน้าที่เปลี่ยน raw data ให้เป็น model input ทุก feature ควรมี definition, owner, freshness target และ data source ที่ตามกลับไปดูได้

Feature store มักมี 2 view:

- offline store สำหรับ training read ขนาดใหญ่
- online store สำหรับ low-latency inference

Store ทั้ง 2 ฝั่งต้องคืน feature ที่มีความหมายเดียวกัน ณ เวลาเดียวกัน และตอนสร้าง training data ต้องใช้ point-in-time join เพื่อกันไม่ให้ model เห็น data ที่เกิดหลัง prediction event

### Training at Scale and Model Lifecycle

Training เริ่มจาก process เดียวบนเครื่องเดียวได้ แล้วค่อยขยายเป็น distributed job เมื่อขนาด data หรือ model บังคับให้ต้องทำ:

- ใช้ data parallelism เมื่อแต่ละ worker train model copy ของตัวเองด้วย data คนละ batch
- ใช้ model, tensor หรือ pipeline parallelism เมื่อ model ใส่ device เดียวไม่พอ
- checkpoint long-running job
- retry failed worker อย่างปลอดภัย
- คุม random seed และ environment version
- track compute และ storage cost
- แยก experiment ออกจาก production pipeline

แต่ละ training run ไม่ควรทิ้งไว้แค่ model file ครับ ถ้าอยากสร้างผลลัพธ์เดิมซ้ำได้ เราต้องเก็บ source code version, dataset/feature version, parameter, environment, evaluation result, safety check, artifact และ checksum ไว้ด้วย

Model registry ช่วยเก็บ version ที่ผ่านแต่ละขั้น พร้อม status เช่น candidate, approved, production, rejected และ retired

อย่า promote model จาก offline score ตัวเดียวครับ Model ใหม่อาจแม่นขึ้น แต่ latency, cost, fairness หรือ business result แย่ลงก็ได้

Retraining อาจเริ่มจาก schedule, ปริมาณ data ใหม่, drift หรือ quality ที่ตก แต่ automatic retraining ไม่จำเป็นต้องตามด้วย automatic release ให้คั่น evaluation และ approval gate ไว้ก่อนเสมอ

### Data Quality Is a Production Dependency

Server ทุกตัวอาจยัง healthy แต่ AI system ให้ผลลัพธ์แย่ลงได้ครับ

![Raw data is checked and versioned before training and serving](/assets/images/blogs/practical-ai-system-design/data-quality-pipeline.png)

สาเหตุอาจเป็น data source หยุดส่ง event, field เปลี่ยนหน่วย, timestamp เปลี่ยน time zone, label มาช้า, app version ใหม่ทำให้ user behavior เปลี่ยน, join แล้ว record ซ้ำ หรือ training หลุดไปใช้ข้อมูลที่ยังไม่มี ณ เวลา prediction

ดังนั้นให้ validate data ทั้งก่อน training และ serving โดยเช็ก schema, range, missing value, distribution, volume, freshness, uniqueness, label delay และ access policy

Dataset ต้องมี version หรือมี snapshot ที่สร้างซ้ำได้ ถ้า model ทำงานแย่ ทีมต้องตามกลับไปได้ว่า code, data, feature และ parameter ชุดไหนสร้าง model version นี้ขึ้นมา

Paper [Hidden Technical Debt in Machine Learning Systems](https://research.google/pubs/hidden-technical-debt-in-machine-learning-systems/) อธิบาย debt ที่เกิดจาก data dependency, feedback loop, configuration และสภาพแวดล้อมที่เปลี่ยนไป อ่านแล้วจะเห็นว่า model มักไม่ใช่ส่วนที่ดูแลยากที่สุด

### Recommendation Systems: Retrieve, Rank, and Rerank

สมมุติว่า E-commerce มีสินค้าราว 1,000,000 ชิ้น แต่หน้าแรกแสดงให้ user ดูเพียง 20 ชิ้น เราคงเอา model ราคาแพงไป score สินค้าทุกชิ้นทุก request ไม่ไหวครับ

Recommendation system ขนาดใหญ่จึงค่อย ๆ ลดจำนวนสินค้าลงเป็น stage:

<MermaidDiagram chart={`
flowchart LR
    U["User and context"] --> C["Candidate generation\nhundreds or thousands"]
    C --> R["Ranking model\nscores each candidate"]
    R --> P["Policy and reranking\ndiversity, stock, freshness"]
    P --> O["Top results"]
    O --> F["Clicks, orders, skips,\nand later outcomes"]
    F --> D["Feature and training data"]
`} />

**Candidate generation** เริ่มจากคัดสินค้า 100 หรือ 1,000 รายการจาก source เช่น:

- สินค้ายอดนิยมหรือกำลังเป็น trend
- สินค้าที่คล้ายกับชิ้นที่ user กำลังดู
- collaborative filtering
- user และ item embedding
- recent activity, category หรือ location

เมื่อ candidate เหลือน้อยลง **ranking** ก็ใช้ feature เพิ่มและใช้ model ที่แพงขึ้นได้ จากนั้น **reranking** ค่อยเติม product rule เช่น stock, blocked seller, diversity, freshness และ sponsored placement

แต่ละ stage ควรมี metric ของตัวเอง:

- retrieval recall at K
- ranking quality เช่น NDCG
- end-to-end outcome เช่น click, order หรือ retention
- latency และ cost
- diversity, freshness และ policy violation

[Recommendation guide ของ Google](https://developers.google.com/machine-learning/recommendation/overview/types) แบ่ง flow เป็น candidate generation, scoring และ reranking แบบเดียวกัน ข้อดีของการแยก stage คือคุณวัด scale, quality และ failure ของแต่ละช่วงได้ ไม่ต้องรอดูจากยอด order ปลายทางอย่างเดียว

### Feedback Loops Can Change the Data

อีกเรื่องที่มองข้ามง่ายคือ model สามารถเปลี่ยน data ที่จะย้อนกลับมา train version ถัดไปได้ครับ

สมมุติว่าระบบดันสินค้าบางชิ้นไว้ด้านบน คนก็เห็นและ click มากขึ้น ถ้า model ถัดไปมอง click เป็น preference ล้วน ๆ สินค้าเดิมอาจยิ่งติดอันดับ เพราะ model ก่อนหน้าเป็นคนเพิ่ม exposure ให้ตั้งแต่แรก

จุดที่ควรระวังมี:

- position และ exposure bias
- label ที่มาช้า เช่น return หรือ fraud report
- negative feedback ที่หายไป
- human decision ถูกนำกลับไปใช้เป็น model label
- model output ถูกใช้เป็น training data โดยไม่มี review
- model ต้นทางเปลี่ยน input ของ model ถัดไป

Log ให้ครบว่าระบบแสดงอะไร, score เท่าไร, อยู่ตำแหน่งไหน, ใช้ policy version ใด และเกิด outcome อะไรตามมา หาก product รองรับได้ ให้ใช้ holdout group หรือ controlled exploration และอย่ามองทุก click เป็น clean label

Production ML checklist ของ Google แนะนำให้ตรวจว่า model [ส่งผลต่อ future input data ของตัวเองหรือไม่](https://developers.google.com/machine-learning/crash-course/production-ml-systems/questions) เพราะ feedback loop เกิดจากทั้ง product flow ไม่ได้อยู่เฉพาะใน training pipeline

### RAG: Retrieve Before You Generate

เมื่อ model ขาดข้อมูลที่เปลี่ยนบ่อยหรือข้อมูลภายใน เราอาจใช้ Retrieval-Augmented Generation หรือ RAG เพื่อค้น knowledge ที่เกี่ยวข้องมาให้ model ตอนรับ request

![RAG searches for relevant context before generating an answer](/assets/images/blogs/practical-ai-system-design/rag-retrieval-flow.png)

[RAG paper](https://arxiv.org/abs/2005.11401) เสนอการใช้ knowledge ภายใน model ร่วมกับ document ที่ retrieve มา วิธีนี้เหมาะกับ product ที่ knowledge เปลี่ยนบ่อย อยู่ใน private domain หรือต้องแสดง source ให้ user ตรวจได้

สำหรับ support assistant:

<MermaidDiagram chart={`
flowchart LR
    subgraph Indexing["Indexing path"]
        D["Approved documents"] --> C["Clean and chunk"]
        C --> E["Create embeddings"]
        E --> V["Vector and text indexes"]
    end

    subgraph Answering["Answer path"]
        U["User question"] --> Q["Query and access check"]
        Q --> V
        V --> K["Relevant passages"]
        K --> M["Model with context"]
        M --> A["Answer with sources"]
    end
`} />

#### The indexing path

1. อ่าน approved document
2. ลบ unsupported หรือ duplicate content
3. แบ่ง document เป็น chunk
4. เติม metadata และ access rule
5. สร้าง embedding
6. เขียน vector และ keyword index
7. บันทึก source version

#### The answer path

1. รับคำถาม
2. เช็ก user และ tenant
3. rewrite หรือ expand query เมื่อมีประโยชน์
4. retrieve candidate passage
5. rerank
6. ส่ง context ที่ดีที่สุดให้ model
7. validate answer และ citation
8. คืน result หรือ refuse

RAG มีจุดพังหลายช่วงครับ เช่น document ที่ต้องใช้ไม่เคยถูก index, chunk เล็กจน context หาย, retrieval เจอข้อความคล้ายแต่คนละเรื่อง, access filter ทำช้าเกินไป, model ไม่ทำตาม source หรือ policy version เก่ากับใหม่ถูกค้นขึ้นมาปนกัน

ให้วัด retrieval แยกจาก generation ถ้า passage ที่ต้องใช้ไม่เคยเข้ามาใน context ต่อให้แก้ prompt ก็อาจไม่ช่วย

Retrieval metric ที่ใช้ได้มี recall at K, precision at K, ranking quality, source freshness, access-filter correctness และสัดส่วน answer ที่มี support ถูกต้อง

### Vector Search Is One Retrieval Tool

Vector search ช่วยหา content ที่มีความหมายใกล้กัน จึงเหมาะกับ natural-language question และ semantic match แต่ไม่ได้เหมาะกับ query ทุกแบบ

Keyword search อาจดีกว่าเมื่อค้น product code, error message, name, date, legal phrase หรือ short identifier

RAG system จำนวนมากจึงใช้ hybrid search:

- vector search หา meaning
- inverted index หา exact term
- metadata filter แยก tenant, language, date และ policy
- reranking เลือกผลชุดสุดท้าย

เลือก index จาก query ที่ user ส่งเข้ามา ถ้าส่วนใหญ่ค้น exact identifier, keyword search อาจตอบโจทย์กว่า การใช้ LLM ใน product ไม่ได้บังคับว่าต้องมี vector database

## Part 3: Add Decisions and Actions

### LLM Workflows Before Autonomous Agents

บางงานต้องเรียก model หลาย step ครับ แต่หลาย step ไม่ได้แปลว่าต้องใช้ autonomous agent เสมอไป

![A workflow follows a fixed path while an agent chooses within limits](/assets/images/blogs/practical-ai-system-design/workflow-vs-agent.png)

Workflow pattern ที่มีประโยชน์ ได้แก่:

- **Prompt chaining:** step ก่อนหน้าเตรียม input ให้ step ถัดไป
- **Routing:** classifier เลือก path ที่รู้ไว้แล้ว
- **Parallel work:** งานอิสระรันพร้อมกัน
- **Evaluator-optimizer:** model ฝั่งสร้างส่ง output ให้ model ฝั่งตรวจ
- **Orchestrator-worker:** model หลักแบ่งงานให้ specialized worker

[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) ของ Anthropic แนะนำให้เริ่มจาก simple composable pattern ก่อน แล้วเพิ่ม complexity เมื่อวัดได้ว่าผลลัพธ์ดีขึ้น เพราะ agentic system ต้องแลก latency และ cost เพิ่มเพื่อให้ทำงานที่ยืดหยุ่นขึ้น

ผมใช้หลักนี้กับ System Design ได้เหมือนกัน fixed workflow test, debug และคาดเดาง่ายกว่า open-ended agent

สำหรับ support assistant แค่ routing อาจพอ:

- product question → RAG answer
- order status → deterministic order lookup
- suspicious activity → human handoff
- unsupported topic → refusal

Model ช่วยเลือก route ได้ โดยไม่ต้องยก ownership ของ workflow ทั้งก้อนให้ model

### Agents: Give the Model Tools and Limits

Agent ใช้ model เลือกว่าจะทำ step ไหนและเรียก tool อะไร แล้ววนต่อจนงานเสร็จ, ชน limit หรือส่งงานให้คน

[Practical guide to building agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/) ของ OpenAI อธิบาย agent ว่าเป็น system ที่จัดการ workflow execution ใช้ tool และทำงานภายใน guardrail

Flow พื้นฐานมีหน้าตาประมาณนี้:

<MermaidDiagram chart={`
flowchart TD
    G["User goal"] --> P["Plan next step"]
    P --> T{"Need a tool?"}
    T -->|"No"| O["Return result"]
    T -->|"Yes"| A["Authorize tool and arguments"]
    A --> X["Execute tool"]
    X --> R["Record result"]
    R --> P
    A -->|"High risk"| H["Human approval"]
    H --> X
`} />

[ReAct paper](https://arxiv.org/abs/2210.03629) เสนอ pattern ที่ผสาน reasoning กับ action ส่วน agent system ยุคนี้ใช้ loop ที่คล้ายกันเพื่อเลือก tool และตอบสนองต่อผลลัพธ์

Tool ทุกตัวควรมี contract แคบและตรวจสอบได้:

- name และ purpose ที่ชัด
- typed input/output schema
- authentication context
- authorization rule
- timeout
- idempotency behavior
- rate limit
- audit event
- safe error message

ถ้า business API เล็ก ๆ ทำงานได้ ก็ไม่ควรส่ง general database connection หรือ powerful shell ให้ model ยิ่ง tool ทำอะไรได้กว้าง เราก็ยิ่งต้องป้องกันและทดสอบมากขึ้น

[Model Context Protocol](https://modelcontextprotocol.io/docs/2026-07-28/getting-started/intro) เป็น standard สำหรับเชื่อม AI application กับ tool และ data source ตัว protocol ช่วยให้ integration ใช้รูปแบบร่วมกันได้ แต่ไม่ได้จัดการ permission ให้เรา Authorization และ policy ยังเป็นหน้าที่ของ product

#### State and memory

ก่อนบอกว่า agent ต้องมี memory ลองแยกก่อนว่าเราหมายถึงข้อมูลแบบไหน:

- **Conversation state:** message ใน session ปัจจุบัน
- **Workflow state:** step ที่จบแล้ว งานที่รอ และ tool result
- **User memory:** preference ที่ user อนุญาตให้เก็บข้าม session
- **Knowledge:** document ที่ retrieve จาก external store

อย่าโยน conversation เก่าทั้งหมดเข้า vector database แล้วเรียกว่า memory ให้ระบุว่าอะไรต้องเก็บ, เก็บเพื่ออะไร, อยู่ได้นานแค่ไหน และ user จะลบได้อย่างไร

ถ้างานใช้เวลานาน workflow state ควรเก็บแบบ durable เพราะ agent อาจต้อง resume หลัง process crash หรือหยุดรอ human approval

#### Single agent and multi-agent patterns

Agent เดียว trace, test และสั่งหยุดง่ายกว่าครับ ผมจะเริ่มแบบนี้ก่อน แล้วค่อยแยก role เมื่อมีปัญหาที่วัดได้รองรับ

Multi-agent system ใช้ pattern ได้หลายแบบ:

- **Orchestrator-worker:** controller แบ่ง bounded task ให้ worker
- **Router-specialist:** router ส่ง request ให้ specialist ที่เหมาะกับงาน
- **Parallel workers:** worker อิสระรันพร้อมกันแล้วรวมผล
- **Review loop:** agent ฝั่งสร้างส่งงานให้ agent ฝั่งตรวจ
- **Handoff:** agent ส่ง state และ ownership ให้อีก agent

จำนวน agent ที่มากขึ้นไม่ได้รับประกันว่าคำตอบจะดีขึ้น แต่จะเพิ่ม model call, latency, cost, state, permission และ failure path ถ้าผมยังอธิบายไม่ได้ว่า agent ตัวที่ 2 แก้ปัญหาอะไร ผมจะยังไม่เพิ่ม

Agent ทุกตัวควรมี goal, context ที่อ่านได้, tool ที่เรียกได้, budget, stop condition และ state ที่ตัวเองรับผิดชอบ รวมถึงเปิดให้ agent อื่นหรือคนเข้ามาตรวจงานได้

## Part 4: Run It in Production

### Model Serving: Latency, Throughput, and Cost

Hosted model API ช่วยซ่อนงานฝั่ง GPU ไว้ให้ครับ แต่ทีมเรายังต้องรับผิดชอบ latency, concurrency, rate limit และ cost ของ product อยู่ดี

#### Hosted API or self-hosted model?

คำถามคือเราจะใช้ hosted API หรือ self-host model เอง ลองเลือกจาก constraint ของ product:

- **Hosted API:** เริ่มได้เร็วและไม่ต้องดูแล GPU แต่ต้องรับ provider limit, data-location choice และการควบคุม model change ที่น้อยลง
- **Self-hosted model:** ควบคุม model, hardware และ data path ได้มากขึ้น แต่ทีมต้องรับ capacity, upgrade, security patch และ on-call เอง
- **Hybrid routing:** เลือก model ตาม task, risk, latency หรือ cost แต่จะมี routing และ evaluation เพิ่ม

บางครั้ง model เล็กก็พอสำหรับ classification หรือ routing แล้วค่อยส่งเฉพาะคำถามยากไป model ใหญ่ ให้เลือกจาก quality ที่วัดใน task นั้น ขนาด model อย่างเดียวตอบไม่ได้ว่าตัวไหนเหมาะกว่า

![Model serving batches requests while balancing wait time and cost](/assets/images/blogs/practical-ai-system-design/model-serving-batching.png)

ถ้าเลือก self-host งานจะเพิ่มตั้งแต่ model replica, GPU scheduling, request queue, dynamic batching, model loading/warm-up, autoscaling, token streaming ไปจนถึง memory limit

วิธีลด serving cost มีหลายแบบ:

- **Quantization** ลด precision เพื่อใช้ memory น้อยลงและมักเพิ่ม throughput
- **Distillation** train model เล็กให้เลียนแบบ behavior ที่ต้องการจาก model ใหญ่
- **Continuous หรือ dynamic batching** รวม request เข้า batch ระหว่างที่ traffic เข้ามา
- **Precomputed หรือ static inference** เตรียม result ล่วงหน้าเมื่อ freshness ยอมรับได้

แต่ละวิธีอาจกระทบ quality หรือ freshness เวลา benchmark จึงต้องวัดผ่าน product path ทั้งก้อน อย่าดูเฉพาะ token per second ส่วน [Quantization guide ของ NVIDIA](https://docs.nvidia.com/nemo-framework/user-guide/latest/model-optimization/quantization/quantization.html) อธิบายผลต่อ memory และ throughput ไว้เพิ่มเติม

[Dynamic batching guide](https://docs.nvidia.com/deeplearning/triton-inference-server/user-guide/docs/user_guide/batcher.html) ของ NVIDIA Triton อธิบายการรวม request เป็น batch เพื่อเพิ่ม throughput แต่ยิ่งรอให้ batch ใหญ่ request แรกก็ยิ่งรอนาน ขนาดที่เหมาะจึงขึ้นกับ latency budget และ performance ของ model

#### Control the latency budget

แยก request ออกเป็นส่วน ๆ:

```text
authentication
+ retrieval
+ reranking
+ model queue
+ model generation
+ tool calls
+ validation
= end-to-end latency
```

ถ้า retrieval หรือ tool call ช้า ต่อให้เร่ง model อย่างเดียว product ก็อาจไม่เร็วขึ้น

ถ้า stream คำตอบ ให้แยกวัด time to first token กับความเร็วของ token ที่ตามมาด้วย เพราะ first token อาจมาเร็ว แต่ user ต้องรอนานกว่าจะได้คำตอบครบ

#### Control cost per useful result

ฝั่ง cost ให้เก็บ input/output token, retrieval/reranking cost, tool call, retry count, model route, cache saving และ cost per completed task

อย่าดู cost per request อย่างเดียวครับ คำตอบราคาถูกที่ทำให้ user ต้องถามซ้ำ หรือสุดท้ายต้องส่งให้คนทำต่อ อาจแพงกว่าตั้งแต่แรกก็ได้

### Caching in AI Systems

AI system มีของให้ cache หลายชั้น และแต่ละชั้นช่วยคนละเรื่อง:

- **Document cache:** ไม่ต้องอ่าน source เดิมซ้ำ
- **Embedding cache:** ไม่สร้าง embedding ใหม่เมื่อ content ไม่เปลี่ยน
- **Retrieval cache:** ใช้ result ซ้ำเมื่อ query และ index version คงที่
- **Prompt prefix cache:** ใช้ repeated prompt input ซ้ำเมื่อ provider รองรับ
- **Response cache:** คืน approved answer เดิมให้ safe repeated request
- **Model cache:** เก็บ model weight ให้พร้อมใน memory

Semantic caching จับคู่ request ที่ความหมายคล้ายกัน แม้ข้อความจะไม่เหมือนกัน วิธีนี้ลด model call ได้ แต่เสี่ยงคืน answer จาก context ผิดด้วย

เพราะแบบนั้น cache key ต้องรวม dimension ที่เปลี่ยนคำตอบ เช่น tenant, user role, language, model version, prompt version, knowledge-base version และ policy version

ห้ามให้ tenant A ได้รับ cached private answer ของ tenant B

### Evaluation Is Part of the Architecture

Test ปกติใช้เช็ก deterministic behavior ส่วน AI evaluation ใช้ดู behavior ที่อาจเปลี่ยนได้แม้ input ใกล้เคียงกัน

![An AI release moves through tests, evaluation, canary rollout, monitoring, and improvement](/assets/images/blogs/practical-ai-system-design/evaluation-release-loop.png)

[Evaluation guide](https://developers.openai.com/api/docs/guides/evals) ของ OpenAI อธิบาย eval ว่าเป็น test ที่เทียบ model output กับ criteria ที่เรากำหนด สิ่งที่ต้องทำมี 3 ช่วง กำหนด expected behavior, สร้าง dataset ที่เป็นตัวแทนของงาน แล้วรันทั้ง system เพื่อ grade result

Evaluation ควรมีหลาย layer:

#### Unit and contract tests

ส่วนที่เป็น normal code ก็ test แบบเดิม เช่น tool schema, access filter, output parser, retry policy, state transition, redaction และ deterministic business rule

#### Offline evaluation

เก็บ versioned case set ให้มี common case, edge case, past failure, adversarial input, หลายภาษา, หลาย customer group, case ที่ต้อง refuse และ case ที่ต้อง human handoff

ให้ grade ทั้ง system อย่าดู final model text อย่างเดียว ถ้าเป็น RAG ให้ตรวจ retrieval กับ grounding ถ้ามี tool ให้ตรวจ selection และ argument ส่วน agent ต้องดูทั้ง path กับ final state

#### Online evaluation

วัด production signal เช่น user correction, task completion, escalation rate, tool failure, refusal rate, latency, cost, safety event และ human review result

อย่าใช้ thumbs-up เป็น quality metric ทั้งหมด เพราะ user จำนวนมากไม่เคยกด

#### Human evaluation

คนยังจำเป็นเมื่อ quality ขึ้นกับ context, policy หรือ harm ให้ reviewer ใช้ rubric ที่ชัด ไม่งั้นคำตอบเดียวกันอาจได้ grade คนละแบบ

### Deploy Prompts and Models Like Code

แต่ละ AI release อาจเปลี่ยนทั้ง model, prompt, tool description, retrieval logic, chunking, embedding, safety policy, system code และ source data ดังนั้นต้องบันทึก version เหล่านี้เป็นชุดเดียวกัน

เวลาปล่อย version ใหม่ เราอาจค่อย ๆ เปิดตามลำดับนี้:

1. offline evaluation
2. shadow traffic
3. internal user
4. production group เล็ก
5. A/B หรือ canary test
6. wider rollout
7. rollback เมื่อ quality หรือ safety ลดลง

Google อธิบาย automation หลายระดับไว้ใน [MLOps architecture guide](https://cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning) ตั้งแต่ manual training ไปจน automated pipeline และ CI/CD

Automation ต้องมี gate model ที่ train เสร็จไม่ควรเข้า production ต่อทันทีเพียงเพราะ job จบโดยไม่มี error

### Reliability: Plan for Poor Answers and Failed Dependencies

ตอนออกแบบ failure ผมจะแยกเป็น 2 กลุ่มก่อนครับ:

- **System failure:** timeout, provider outage, rate limit, broken tool หรือ missing index
- **Quality failure:** wrong answer, weak retrieval, unsafe output หรือ bad action

ระบบต้องรับมือทั้ง 2 แบบ เพราะ health check ปกติอาจมองเห็นแค่กลุ่มแรก

<MermaidDiagram chart={`
flowchart TD
    R["AI request"] --> P["Primary path"]
    P -->|"Good result"| O["Return result"]
    P -->|"Timeout or overload"| F["Smaller model or fixed workflow"]
    P -->|"Low confidence or missing source"| H["Human handoff"]
    P -->|"Unsafe or forbidden"| X["Block and audit"]
    F --> O
    H --> O
`} />

Fallback ไม่จำเป็นต้องตอบด้วย AI เสมอไป เราอาจคืน search result, ใช้ model เล็กลง, กลับไปใช้ fixed rule/workflow, คืน cached approved answer, ขอข้อมูลเพิ่ม, handoff ให้คน หรือหยุดโดยไม่ทำ action

ส่วน agent ต้องมี limit อย่างน้อยในเรื่อง total model call, total tool call, workflow duration, token use, cost, failed step ที่เกิดซ้ำ และจำนวน workflow ที่รันพร้อมกัน

Agent ที่ตัดสินใจหยุดไม่ได้ คือ operational incident ที่รอวันเกิด

### Security: Treat Model Input and Output as Untrusted

LLM รับ natural language จากหลายทาง ทั้ง user, document, website และ tool result ปัญหาคือข้อความจากทุกทางอาจแฝง instruction ที่เราไม่ควรทำตาม

[OWASP Top 10 for LLM applications](https://owasp.org/www-project-top-10-for-large-language-model-applications/) ครอบคลุม prompt injection, insecure output handling, sensitive information disclosure, excessive agency และ overreliance

Input validation ชั้นเดียวหยุด prompt injection ไม่ได้ครับ ต้องแยกการป้องกันเป็นหลายชั้น:

- แยก system policy ออกจาก untrusted content
- authorize ทุก tool call นอก model
- ใช้ allowlist กับ tool และ argument
- จำกัด retrieval ตาม user และ tenant
- มอง model output เป็น untrusted input ของ component ถัดไป
- ขอ approval สำหรับ high-impact action
- redact secret และ sensitive data
- isolate code execution
- log action โดยไม่ทำ private content รั่ว
- test adversarial case

สมมุติว่าเป็น support agent การอ่าน order กับการ refund order ต้องเป็นคนละ permission Model ไม่ควรได้ write access เพียงเพราะอธิบาย refund policy ได้

[NIST AI Risk Management Framework](https://www.nist.gov/itl/ai-risk-management-framework) แบ่งงานด้าน AI risk เป็น govern, map, measure และ manage สิ่งที่เอามาใช้กับ architecture ได้คือ safety ต้องอยู่ตลอด lifecycle ใส่ model filter ตัวเดียวไว้ท้าย flow ยังไม่พอ

### Privacy, Compliance, and Data Governance

AI system อาจพา sensitive data ไปอยู่หลายจุดกว่าที่เราคิด ทั้ง training dataset, feature store, vector index, prompt, trace, evaluation set และ model artifact

ก่อนเลือก control ให้ไล่ data lifecycle ให้ครบก่อน:

1. collection
2. consent และ allowed purpose
3. storage และ access
4. training หรือ retrieval use
5. logging และ evaluation
6. retention และ deletion

จากนั้นค่อยเลือก control เช่น collect เฉพาะ data ที่ต้องใช้, แยก tenant และ role, encrypt in transit/at rest, mask หรือ tokenize identifier, ลบ secret ก่อนส่ง prompt และ log, เก็บ dataset lineage, test private-data leakage, รองรับ retention/deletion request และ review ว่า provider process data ที่ไหน

Predictive system บางแบบอาจใช้ differential privacy หรือ federated learning เพื่อลด risk เฉพาะด้าน แต่แต่ละวิธีอาจลด model utility หรือเพิ่ม cost ต้องเลือกจาก threat และ requirement ไม่ได้ใส่แล้วผ่าน compliance อัตโนมัติ

Governance ต้องมีคนรับผิดชอบด้วย ระบุให้ได้ว่าใคร approve dataset, model, prompt, tool และ policy change แล้วเก็บ audit trail ให้ตาม production result กลับไปยัง version ต้นทางได้

### Human Approval Is a System State

ถ้าต้องรอ human approval อย่าจบด้วยการส่ง message หาใครสักคนแล้วหวังว่าจะมีคนกลับมาทำต่อครับ Workflow ต้องเก็บ durable state ไว้ชัด ๆ:

```text
RUNNING
WAITING_FOR_APPROVAL
APPROVED
REJECTED
EXPIRED
COMPLETED
FAILED
```

เก็บ proposed action, input และ evidence, model/prompt/policy version, approver, approval time, final tool result และ audit event

ระหว่างรอ approval สถานะของ action อาจ expire หรือ business data เปลี่ยนไปแล้ว ก่อน execute จึงต้องเช็ก permission และ current state อีกรอบ

Human approval เหมาะกับ high-impact action แต่ถ้าทุก low-risk request ต้องรอคน ระบบก็จะมี hidden queue และสุดท้ายคนกลายเป็น bottleneck

### Observability for AI Products

Metric ของระบบปกติยังต้องมี ทั้ง request rate, error rate, latency, saturation, queue depth และ dependency health

![AI observability traces the whole request and its quality, latency, cost, failures, and feedback](/assets/images/blogs/practical-ai-system-design/ai-observability.png)

จากนั้นค่อยเพิ่มคำถามที่เฉพาะกับ AI:

- model และ prompt version ไหนรัน?
- retrieve document อะไรมาบ้าง?
- agent เลือก tool ไหน?
- request ถูก block หรือ handoff เพราะอะไร?
- ใช้ token และ tool call เท่าไร?
- quality เปลี่ยนหลัง release ไหม?
- tenant เดียวสร้าง cost ผิดปกติหรือเปล่า?
- input หรือ output drift ไหม?

ผูก workflow ทั้งก้อนด้วย request หรือ task ID เดียว เพื่อให้ตาม model call, retrieval, tool call, approval และ fallback ของงานเดียวกันได้

แต่ log เองก็เป็น data risk Prompt, retrieved document และ tool result อาจมี PII, credential หรือ confidential data ให้เก็บเฉพาะส่วนที่ทีมต้องใช้และตั้ง retention rule ไว้ด้วย

## Part 5: Put It Together

### A Practical Support Assistant Design

ถึงช่วงนี้ลองเอาทุกส่วนมาประกอบเป็น customer support assistant ตัวเดิม

![A practical support assistant routes work to an answer, a human, or an approval gate](/assets/images/blogs/practical-ai-system-design/support-assistant-routing.png)

Requirement ของ support assistant มีดังนี้:

- ตอบ product question จาก approved document
- แสดง source
- lookup order หลัง authenticate user
- สร้าง support ticket
- ส่ง sensitive หรือ unclear case ให้คน
- ห้ามเปลี่ยน payment หรือ account state โดยไม่มี approval

<MermaidDiagram chart={`
flowchart LR
    U["Customer"] --> G["Support API"]
    G --> A["Auth and policy"]
    A --> R["Router"]

    R -->|"Product question"| K["RAG retrieval"]
    K --> M["Model"]

    R -->|"Order question"| O["Read-only order tool"]
    O --> M

    R -->|"Create ticket"| T["Ticket tool"]
    T --> M

    R -->|"Sensitive or unclear"| H["Human support"]
    M --> V["Grounding and safety checks"]
    V --> U

    G --> L["Trace and audit store"]
    K --> L
    M --> L
    O --> L
    T --> L
`} />

#### Request flow

1. Authenticate user
2. Apply tenant, customer และ data policy
3. Route request
4. Retrieve document หรือเรียก narrow tool
5. Generate response
6. เช็ก grounding, policy และ tool result
7. Return, refuse หรือ handoff
8. บันทึก trace และ evaluation signal

#### Why the router matters

Router ช่วยแยกงานที่มีคำตอบแน่นอนออกจากงานที่ต้องใช้ model อย่าง order lookup ไม่ต้องใช้ autonomous agent ระบบเรียก read-only API ด้วย typed order ID แล้วค่อยให้ model อธิบาย result ก็พอ

#### Why human support remains

บาง request อาจไม่มี source รองรับ, เป็น sensitive case หรือเจอ data ขัดกัน การ handoff ให้คนจึงเป็นผลลัพธ์ที่ product ตั้งใจรองรับ ไม่ได้แปลว่าระบบล้มเหลว

#### What to Test First

- unsupported question
- private data ของ customer อื่น
- old policy document
- prompt injection ใน document
- provider timeout
- ticket tool ถูกเรียกซ้ำ
- order API คืน partial data
- user permission เปลี่ยนระหว่าง long task
- answer ไม่มี supporting passage
- expensive loop ที่เรียก model ซ้ำ

สุดท้าย design ใหญ่กว่า model call เดียว เพราะ requirement กับ failure ที่เราค่อย ๆ เจอเป็นตัวผลักให้ระบบโตขึ้น

## Part 6: Use It to Coach

### A Coaching Method for AI System Design

ถ้าผมเอาเรื่องนี้ไปใช้ coach ผมจะเริ่มจาก product ก่อน model ครับ เพราะชื่อ model บอกไม่ได้ว่า user ต้องการผลลัพธ์อะไร หรือถ้าตอบผิดแล้วใครได้รับผลกระทบ

1. กำหนด user และ useful outcome
2. ระบุ AI system type
3. เลือก quality, latency, safety และ cost goal
4. สร้าง smallest useful version
5. แยก deterministic rule จาก model decision
6. วาด data และ request path
7. เพิ่ม evaluation ก่อนเพิ่ม autonomy
8. เพิ่ม tool พร้อม narrow permission
9. วาง failure, fallback และ human handoff
10. บันทึก version และ ownership

คำถามที่ผมจะใช้ไล่กับคนออกแบบมีประมาณนี้:

- Step นี้ต้องใช้ AI เพราะอะไร?
- Model ผิดแล้วเกิดอะไรขึ้น?
- เรารู้ได้อย่างไรว่า quality เปลี่ยน?
- ตอนตัดสินมี data อะไรให้ใช้บ้าง?
- User ดูหรือลบ stored memory ได้ไหม?
- Tool call นี้รันซ้ำอย่างปลอดภัยได้หรือเปล่า?
- Action ไหนต้อง human approval?
- Cost per successful task เท่าไร?
- Fixed workflow แก้ได้ปลอดภัยกว่าไหม?
- จะ rollback model, prompt, data หรือ index อย่างไร?

## Final Thoughts

สุดท้าย AI System Design ก็ยังเป็น System Design

เรายังต้องมี requirement, API, data ownership, failure handling, security, monitoring, cost control และทีมที่ operate ระบบต่อได้

สิ่งที่เพิ่มเข้ามาคือ uncertainty อีกชั้น:

- data เปลี่ยนได้
- model behavior เปลี่ยนได้
- retrieval พลาดได้
- output ผิดทั้งที่อ่านดูมั่นใจ
- agent เลือก unsafe action ได้
- quality ลดลงได้โดยไม่มี server error

เพราะแบบนั้นเราไม่จำเป็นต้องใส่ AI component ทุกตัว เริ่มจาก product เล็กที่สุดที่มีประโยชน์ เพิ่ม retrieval เมื่อ knowledge ขาด เพิ่ม workflow เมื่อ call เดียวไม่พอ แล้วค่อยเพิ่ม agent เมื่อความยืดหยุ่นที่ได้คุ้มกับ cost และ risk

ไม่ว่าจะหยุดที่ขั้นไหน ให้ใส่ evaluation, safety, fallback และ ownership เข้า architecture ตั้งแต่วันแรก

Model call ทำให้ demo เริ่มได้ ส่วนระบบรอบ model ทำให้ product อยู่ต่อใน production ได้ครับ
