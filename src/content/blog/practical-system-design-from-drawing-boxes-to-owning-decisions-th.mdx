## Why This Guide Exists

เวลาเริ่มเรียน System Design ภาพที่เราเจอมักเป็น diagram มีทั้ง load balancer, cache, queue, database, worker, region แล้วก็ลูกศรเต็มไปหมด

ดูดีนะ แต่คำถามสำคัญ **ทำไมระบบถึงต้องมีไอ box พวกนี้ด้วย?**

การบอกว่าจะเพิ่ม component อะไรนั้นไม่ยาก ส่วนที่ยากกว่าคืออธิบายว่า component นี้แก้ปัญหาอะไร มีอะไรพังได้บ้าง และเมื่อขึ้น production แล้วใครจะดูแลต่อ

บทความนี้จะตัดเรื่อง interview process ออก ผมอยากเรียงเนื้อหาให้ทุกคนใช้ฝึกด้วยตัวเอง หรือหยิบไปใช้ coach และ mentor คนที่กำลังพัฒนาเรื่อง System Design ได้ง่ายขึ้น

แกนหลักมี 1 ประโยคครับ:

**System Design คือการเปลี่ยนปัญหาให้เป็นระบบที่ทีมสร้าง รัน แก้ไข และดูแลต่อได้**

เราจะเริ่มจากระบบเล็ก ๆ แล้วโยน constraint เข้าไปทีละข้อ ระหว่างทางก็จะเจอทั้ง data, scaling, failure, security, operations และ engineering judgment

บทความนี้คงครอบคลุมระบบทุกแบบไม่ได้ครับ ผมแค่อยากช่วยให้ทุกคนตั้งคำถามได้ดีขึ้น ต่อให้ระบบถัดไปไม่เหมือนตัวอย่างนี้ เราก็ควรอธิบายเหตุผลของ design ได้โดยไม่ต้องจำ diagram สำเร็จรูป

## Start with the Problem, Not the Components

สมมุติว่าเรากำลังออกแบบ E-commerce marketplace ครับ

ลูกค้าเข้ามาดูสินค้า ใส่ของลง cart แล้ววาง order จากนั้นระบบต้องเช็ก inventory, รับ payment, ส่ง order ไป fulfillment และติดตาม status จนส่งของสำเร็จ ส่วน seller ก็ต้องจัดการสินค้า ราคา และ stock ได้

ก่อนวาด diagram ลองตอบคำถามง่าย ๆ ก่อนครับ ระบบต้องทำอะไร?

### Functional requirements

Functional requirements มีประมาณนี้:

- browse และ search สินค้า
- เพิ่ม แก้ และลบสินค้าใน cart
- วาง order และจ่ายเงิน
- reserve inventory โดยไม่ขายเกิน stock
- ส่ง paid order ไป fulfillment
- แสดง order และ delivery progress

### Non-functional requirements

Non-functional requirements บอกคุณภาพและข้อจำกัดที่ระบบต้องรักษา:

- **Correctness:** ห้ามสร้าง order ซ้ำ ห้ามตัดเงินซ้ำ และห้ามขายสินค้าที่หมดแล้ว
- **Availability:** ลูกค้าควรดูสินค้าและวาง order ได้แม้ server บางตัวล้ม
- **Durability:** order ที่รับแล้วต้องไม่หาย
- **Scale:** product read อาจมากกว่า order write หลายเท่า และ traffic เปลี่ยนเร็วได้
- **Security:** ลูกค้า seller และ service ต้องเข้าถึงเฉพาะ data กับ action ที่ตัวเองมีสิทธิ์
- **Auditability:** ทีมต้องรู้ว่าใครเปลี่ยนอะไร เมื่อไหร่

ยังไม่ต้องเขียน requirement ทุกอย่างที่นึกออกครับ ให้เริ่มจากข้อที่มีผลกับ design ก่อน

สมมุติว่า product view counter อัปเดตช้าไป 1 นาที ผลกระทบอาจน้อย แต่ inventory กับ payment status ตอน checkout ต้องใช้ correctness guarantee ที่เข้มกว่า ทั้งหมดอยู่ใน product เดียวกัน แต่มี quality goal คนละแบบ

ก่อนเลือก technology ลองถาม 6 ข้อนี้:

1. ใครเป็นคนใช้ระบบ?
2. Failure scenario ไหนยอมรับไม่ได้?
3. งานไหนย้ายไปทำแบบ asynchronous ได้?
4. ระบบยอมรับ data loss ได้แค่ไหน?
5. ถ้า dependency ใช้งานไม่ได้จะเกิดอะไรขึ้น?
6. action ไหนสร้างต้นทุนให้ธุรกิจหรือลูกค้า?

ถ้าตอบคำถามพวกนี้ได้ ทุก box บน diagram ก็ควรมีเหตุผลของมันครับ

![Customer needs become requirements and system constraints](/assets/images/blogs/practical-system-design/requirements-first.png)

## Core Quality Goals Pull the Design in Different Directions

ระบบ 1 ตัวดันทุก quality ให้สุดพร้อมกันไม่ได้ครับ ต้องเลือกว่าข้อไหนสำคัญกว่า และข้อไหนยอมลดได้

- **Scalability** คือความสามารถในการรับ user, data หรืองานที่เพิ่มขึ้น
- **Performance** พูดถึงความเร็วและ resource ที่ใช้ โดยมักดู latency กับ throughput
- **Availability** บอกว่าระบบพร้อมรับงานที่มีประโยชน์บ่อยแค่ไหน
- **Reliability** บอกว่าระบบยังให้ผลลัพธ์ที่ถูกต้องต่อเนื่องหรือเปล่า
- **Consistency** บอกว่า reader หลายคนเห็น data state เดียวกันเมื่อไหร่
- **Security** กำหนดว่าใครเข้าถึง data และ action อะไรได้

Availability กับ reliability เกี่ยวข้องกัน แต่คนละเรื่อง ตัวอย่างเช่น service อาจตอบกลับทุก request ได้ ทั้งที่ข้อมูลเก่าหรือผิด แบบนี้ระบบยัง available แต่ผลลัพธ์เชื่อถือไม่ได้

เปลี่ยนคำกว้าง ๆ ให้เป็น measurable target เช่น:

- p95 และ p99 latency
- request หรือ job ต่อวินาที
- queue age สูงสุด
- error rate ที่รับได้
- recovery time objective หรือ RTO
- recovery point objective หรือ RPO
- data freshness
- monthly availability

ถ้าตั้งเป้า monthly availability ไว้ที่ 99.9% downtime จะอยู่ที่ประมาณ 43 นาทีต่อเดือนครับ หากอยากได้สูงกว่านี้ ทีมก็ต้องลงทุนกับ redundancy, testing, automation และ cost เพิ่มขึ้น เลือกตัวเลขจาก business impact อย่าเลือกเพราะเห็นทีมอื่นใช้เลขเดียวกัน

## Estimate Only What Can Change the Design

Estimation มีประโยชน์เมื่อเลขนั้นเปลี่ยน decision ครับ ถ้าไม่เปลี่ยนก็ไม่ต้องเสียเวลาทายให้เป๊ะทุกหลัก

สมมุติ marketplace มีลูกค้า 10,000,000 คนต่อวัน แต่ละคนเปิด product page เฉลี่ย 20 หน้า และลูกค้า 2% วาง order

คำถามที่ควรถามมีประมาณนี้:

- ระบบต้องรับ product read กี่ครั้ง?
- แต่ละวันมี order ใหม่กี่รายการ?
- inventory, payment และ fulfillment service รับ peak rate ไหวหรือเปล่า?
- ต้องเก็บ order กับ event history เท่าไร?
- peak traffic สูงกว่าค่าเฉลี่ยต่อวันแค่ไหน?

ตัวเลขชุดนี้ได้ product view ประมาณ 200,000,000 ครั้ง และ order 200,000 รายการต่อวัน ฝั่ง product เป็น read-heavy ส่วน order 1 รายการสร้างทั้ง write และ call ไป service อื่นอีกหลายครั้ง

```text
10,000,000 customers x 20 product views = 200,000,000 product views/day
10,000,000 customers x 2% conversion = 200,000 orders/day
```

ตัวเลข 2 ชุดพา design ไปคนละทาง โดยฝั่ง product browsing อาจต้องใช้ cache, CDN และ read scaling ส่วน order processing ต้องมี durable write, idempotency, queue และ recovery tool

ให้เวลาเฉพาะเลขที่มีผลต่อ design:

- **Request rate** สำคัญเมื่อ service หรือ dependency อาจรับไม่ไหว
- **Record size** สำคัญเมื่อ storage หรือ network cost สูง
- **Read-to-write ratio** สำคัญเมื่อต้องตัดสินใจเรื่อง cache
- **Peak traffic** สำคัญเมื่อ average ซ่อน burst ไว้
- **Recovery time** สำคัญเมื่อ outage กระทบธุรกิจ

ถ้าเลขไหนไม่เปลี่ยน design ก็ข้ามไปก่อนได้ครับ

![Estimation connects traffic, storage, peak load, and system capacity](/assets/images/blogs/practical-system-design/estimate-for-decisions.png)

Version 1 เริ่มเล็กกว่าที่หลายคนคิดได้ครับ

![A small useful system with room to grow](/assets/images/blogs/practical-system-design/start-small.png)

Application เก็บ product, cart และ order ไว้ใน database 1 ตัว แล้วเรียก payment กับ shipping service ตอนลูกค้าวาง order

ถ้าทีมยังเล็กและ volume ยังไม่มาก design นี้อาจพอแล้ว ทั้งเข้าใจง่าย deploy ง่าย และ debug ง่าย

Naive ไม่ได้แปลว่าแย่ครับ ถ้าปัญหายังเล็ก ระบบเล็กอาจเหมาะกว่า architecture ก้อนใหญ่

ก่อนเพิ่ม component ทำ version นี้ให้ปลอดภัยก่อน:

- เก็บเงินด้วยหน่วยย่อยสุดของ currency แทน floating-point number
- order ที่รับแล้วต้องอยู่ใน durable database ไม่ใช่ process memory
- บันทึก payment และ fulfillment attempt
- ทำ checkout กับ integration call ให้ idempotent
- ป้องกัน action ของ customer และ seller ด้วย authentication กับ authorization

### Protect and Observe Version One

Security กับ observability อย่ารอให้ระบบใหญ่ครับ เพราะ version 1 ก็แตะทั้ง customer data, เงิน และ external service แล้ว

ฝั่ง security เริ่มจาก boundary ที่จำเป็นก่อน:

- authenticate ทุก action ของ customer และ seller
- เช็ก authorization กับ order หรือ product ที่กำลังแก้
- แยก secret ออกจาก code และ log
- เก็บ audit trail สำหรับ sensitive action

![ระบบเล็กป้องกัน identity, access, secret, audit record และ sensitive data ตั้งแต่ version 1](/assets/images/blogs/practical-system-design/security-boundary-basics.png)

ฝั่ง observability ให้เริ่มจากคำถามพื้นฐานที่ทีมต้องตอบเวลาเกิดปัญหา:

- request สำเร็จหรือ fail?
- ใช้เวลานานแค่ไหน?
- เกี่ยวข้องกับ order และ payment attempt ไหน?
- dependency ตัวไหน fail ซ้ำ?

สำหรับ version 1 มี structured log, correlation ID, latency/error metric และ alert ที่บอกว่าทีมควรทำอะไรต่อก็พอ ยังไม่ต้องรีบสร้าง observability platform ก้อนใหญ่

![Log, metric, trace และ alert ช่วยให้ทีมมองเห็นการทำงานของระบบ version 1](/assets/images/blogs/practical-system-design/observability-basics.png)

เดี๋ยวช่วงท้ายจะกลับมาดู boundary, control, metric และ recovery อีกทีครับ ตอนนี้จำไว้ก่อนว่า security กับ observability ต้องโตไปพร้อมระบบ

จากนั้นรอให้ constraint เป็นตัวบอกว่า design ต้องโตไปทางไหน

### Scale up or scale out

เพิ่ม capacity ได้ 2 ทางหลัก:

- **Vertical scaling:** เพิ่ม CPU, memory, disk หรือ network ให้เครื่องเดิม
- **Horizontal scaling:** เพิ่มจำนวนเครื่อง แล้วกระจายงานออกไป

Vertical scaling เริ่มง่ายกว่า แต่ติดเพดาน hardware และเครื่องเดิมยังเป็น failure point อยู่ ส่วน horizontal scaling โตต่อได้ไกลกว่าและแยก failure ได้ดีขึ้น แต่ทีมต้องดูแล load distribution, partitioning, coordination และ operational tools เพิ่ม

![Vertical scaling เพิ่ม capacity ให้ 1 เครื่อง ส่วน horizontal scaling กระจายงานไปหลายเครื่อง](/assets/images/blogs/practical-system-design/scale-up-vs-scale-out.png)

ระบบจำนวนมากใช้ทั้ง 2 แบบ เช่น database อาจเริ่มจากขยับไปเครื่องใหญ่ขึ้น ส่วน application server scale out ได้ง่ายกว่าเพราะทำให้ stateless ได้

### CDN and edge delivery

CDN เก็บ content ที่ cache ได้ไว้ใกล้ user เหมาะกับ image, video, JavaScript, download และ public API response ที่กำหนด cache rule ได้อย่างปลอดภัย

CDN ลด origin traffic และ latency ได้ แต่เพิ่มเรื่องที่ต้องตัดสินใจ:

- cache key
- cache duration
- invalidation
- private กับ public content
- regional rule
- behavior ตอน origin ใช้งานไม่ได้

อย่า cache private content ด้วย key ที่ไม่สนใจ user หรือ tenant ครับ

### Load balancer: when one application is not enough

Load balancer ช่วยกระจาย traffic ไปยัง application instance หลายตัว เหมาะกับสถานการณ์เหล่านี้:

![Load balancer ส่ง traffic ไป healthy instance และหยุดส่งไป unhealthy instance](/assets/images/blogs/practical-system-design/load-balancer-health-routing.png)

- instance 1 ตัวรับ traffic ไม่ไหว
- ต้อง deploy โดยไม่หยุด traffic ทั้งหมด
- ต้องเอา unhealthy instance ออกจากระบบ
- อยากส่ง request ไป region หรือ zone ที่ใกล้กว่า

พอมี load balancer ก็มีคำถามเพิ่ม:

- application stateless หรือยัง?
- session state อยู่ไหน?
- health check รู้ได้อย่างไรว่า instance พร้อมรับงาน?
- ถ้าทุก instance overload จะทำอย่างไร?

Health check ควรเช็กว่า instance พร้อมรับงานหรือยังครับ เพราะ process อาจตอบ HTTP ได้ ทั้งที่ database pool เต็มจนทำงานต่อไม่ได้แล้ว

### API gateway and rate limiting

API gateway เป็น entry point กลางสำหรับ authentication, routing, request limit, protocol conversion และ shared logging เหมาะเมื่อ client หลายแบบเรียก service หลายตัว

แต่ gateway อาจกลายเป็น shared failure point ก้อนใหญ่ได้ จำกัดหน้าที่ให้พอดีและรันแบบมี redundancy

![API gateway ใช้ shared control ก่อน route request จาก client ไป backend service](/assets/images/blogs/practical-system-design/api-gateway-entry-point.png)

Rate limiting ช่วยป้องกันระบบจาก traffic ที่เกิน capacity และแบ่ง usage ให้แต่ละ user หรือ tenant ได้อย่างเป็นธรรม

Policy ที่พบบ่อยมี:

- fixed หรือ sliding time window
- token bucket ที่ยอมให้ burst ได้ตามขอบเขต
- leaky bucket ที่ทำ traffic ให้ไหลสม่ำเสมอ
- concurrency limit สำหรับงานแพง
- quota แยกตาม user, tenant, API key หรือ region

เวลา request ชน limit ให้ตอบ error พร้อม retry time ครับ ถ้าบอกแค่ว่าถูกจำกัด client อาจ retry ถี่ขึ้นแล้วเพิ่ม load ให้ระบบอีก

### Database: choose from the access pattern

เวลาเลือก database ให้เริ่มจาก read/write pattern ของระบบ

![Different access patterns lead to different data designs](/assets/images/blogs/practical-system-design/choose-for-access-pattern.png)

สำหรับ E-commerce system เราอาจมี record หลักดังนี้:

- product
- inventory
- cart
- order และ order item
- payment attempt
- fulfillment
- audit event

Relational database เป็น default choice ที่ดี เมื่อระบบต้องใช้ transaction, relationship ที่ชัด และ operational query ที่ยืดหยุ่น

Key-value หรือ wide-column store ช่วยได้เมื่อ access pattern เรียบง่ายและ volume สูงมาก แต่ data model ยังต้องออกแบบตาม query อยู่ดี Distributed database ไม่ได้ทำให้ data modeling หายไป กลับทำให้ access pattern สำคัญขึ้นกว่าเดิม

Storage แต่ละตระกูลเหมาะกับงานคนละทรง:

- **Relational:** transaction, relationship, constraint และ query ที่ยืดหยุ่น
- **Key-value:** lookup เร็วจาก key ที่รู้ล่วงหน้า
- **Document:** record ที่มี nested field และ schema ยืดหยุ่น
- **Wide-column:** data ปริมาณมากที่จัดกลุ่มด้วย partition key
- **Time-series:** metric และ event ตามเวลา พร้อม retention rule
- **Graph:** เดิน relationship หลายชั้น
- **Object storage:** file ใหญ่หรือ immutable data ในต้นทุนต่ำ
- **Search index:** text search, ranking, filtering และ aggregation
- **Vector index:** similarity search จาก embedding

#### How each storage type is queried

Syntax ของแต่ละแบบต่างกัน แต่หลักคิดเหมือนกันครับ เราต้องออกแบบ data ให้เข้ากับ read และ write ที่ product ต้องใช้ ตัวอย่างต่อไปนี้ยึด E-commerce ระบบเดียวและตั้งใจให้สั้น

**Relational — PostgreSQL**

SQL เหมาะกับงานที่ต้องใช้ condition, relationship, constraint และ transaction Query นี้ดึง active product ล่าสุดใน category เดียว

```sql
SELECT id, name, price
FROM product
WHERE category_id = 42
  AND status = 'ACTIVE'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Table นี้อาจต้องมี index `(category_id, status, created_at DESC, id DESC)` และถ้าใช้ `LIMIT` เพื่อแบ่งหน้า `ORDER BY` ต้องให้ลำดับที่แน่นอน อ่านต่อได้ใน [PostgreSQL LIMIT documentation](https://www.postgresql.org/docs/current/queries-limit.html)

**Key-value — Redis**

Key-value เริ่มจาก key ที่เรารู้อยู่แล้ว Command นี้อ่าน field ทั้งหมดของ SKU 1 ตัว

```text
HGETALL product:sku:SKU-123
```

วิธีนี้ง่ายและเร็วเมื่อรู้ key แต่ถ้าจะหา active product ทั้ง category เราต้องมี structure อีกชุดรองรับ access pattern นั้น อ่านต่อได้ใน [Redis HGETALL documentation](https://redis.io/docs/latest/commands/hgetall/)

**Document — MongoDB**

Document query ใช้ filter แล้วดึง nested product data กลับมาเป็นก้อนได้

```javascript
db.products.find(
  { categoryId: 42, status: "ACTIVE" },
  { name: 1, price: 1, attributes: 1 }
).sort({ createdAt: -1, _id: -1 }).limit(20)
```

เราสามารถเก็บ flexible attribute ไว้ใกล้ product ได้ แต่ query ยังต้องมี index ที่รองรับทั้ง filter และ sort อ่านต่อได้ใน MongoDB documentation ของ [`find()`](https://www.mongodb.com/docs/manual/reference/method/db.collection.find/) และ [`sort()`](https://www.mongodb.com/docs/manual/reference/method/cursor.sort/)

**Wide-column — Cassandra**

Cassandra มักออกแบบ table ตาม query ที่รู้ล่วงหน้า สมมุติว่า `products_by_category` ใช้ `category_id` เป็น partition key และเริ่ม clustering column ด้วย `status`

```sql
SELECT product_id, name, price
FROM products_by_category
WHERE category_id = 42
  AND status = 'ACTIVE'
LIMIT 20;
```

Query นี้อ่าน partition ที่ระบุไว้ หากต้องหา product ตาม seller เรามักต้องสร้างอีก table เพราะ CQL ไม่มี join แบบ relational หรือ query ข้าม table ได้อิสระ อ่านต่อได้ใน [Cassandra CQL SELECT documentation](https://cassandra.apache.org/doc/latest/cassandra/developing/cql/dml.html)

**Time-series — Prometheus**

PromQL ใช้ query metric ตามช่วงเวลา ตัวอย่างนี้คำนวณ failed checkout ต่อวินาทีจากช่วง 5 นาทีล่าสุด

```text
sum(rate(checkout_requests_total{status="failed"}[5m]))
```

`rate()` ใช้กับ counter ส่วน label ต้องคุมจำนวนค่าให้ดี หากเอา `customer_id` หรือ `order_id` มาเป็น label เราอาจสร้าง time series เยอะเกินไป อ่านต่อได้ใน Prometheus documentation ของ [PromQL basics](https://prometheus.io/docs/prometheus/latest/querying/basics/) และ [`rate()`](https://prometheus.io/docs/prometheus/latest/querying/functions/#rate)

**Graph — Neo4j**

ถ้าพูดแบบสั้น Query นี้ถามว่า **ลูกค้าคนอื่นที่เคยซื้อ product เหมือนลูกค้าคนนี้ เขาซื้ออะไรเพิ่มอีกบ้าง?**

```cypher
MATCH (customer:Customer {id: $customerId})-[:BOUGHT]->(shared:Product)
      <-[:BOUGHT]-(other:Customer)-[:BOUGHT]->(candidate:Product)
WHERE NOT EXISTS {
  MATCH (customer)-[:BOUGHT]->(candidate)
}
RETURN candidate.id, candidate.name, count(*) AS score
ORDER BY score DESC
LIMIT 10;
```

Graph database ไล่ relationship จาก customer ไป shared product ต่อไปยัง customer คนอื่น แล้วหา candidate product เหมาะกับงานที่ traversal เป็นแกนหลัก ถ้า lookup product จาก ID อย่างเดียว เราไม่จำเป็นต้องใช้ model นี้ อ่านต่อได้ใน [Neo4j Cypher MATCH documentation](https://neo4j.com/docs/cypher-manual/current/clauses/match/)

**Object storage — files by key**

Object storage ไม่ได้ query แบบ row ใน database Application จะเก็บ file แต่ละตัวด้วย object key แล้วเก็บ metadata ขนาดเล็กที่ค้นหาได้ไว้ใน database

![Product image, catalog file, invoice และ export อยู่ใน object storage ส่วน database เก็บ metadata](/assets/images/blogs/practical-system-design/object-storage-file-flow.png)

File แต่ละแบบถูกนำไปใช้คนละงาน:

- CDN อ่าน product image แล้วส่งให้ลูกค้า
- worker อ่าน catalog file เพื่อนำ product data เข้า system
- invoice เก็บไว้ให้ download และใช้ตอน audit
- export เก็บ batch result ขนาดใหญ่

เวลาอ่าน file 1 ตัว Application ดึงจาก bucket และ object key หากต้องหาตาม seller, date หรือ status ให้ query metadata database ก่อน แล้วค่อย fetch object ที่ match กัน Database ช่วยเรื่อง search ส่วน object storage รับหน้าที่เก็บ file ขนาดใหญ่

**Search index — OpenSearch**

OpenSearch รวม analyzed text, relevance และ exact filter ไว้ใน query เดียวได้

```json
GET /products/_search
{
  "size": 20,
  "query": {
    "bool": {
      "must": {
        "multi_match": {
          "query": "wireless keyboard",
          "fields": ["name^3", "description"]
        }
      },
      "filter": [
        { "term": { "status": "ACTIVE" } },
        { "term": { "category_id": 42 } }
      ]
    }
  }
}
```

Search index อาจคืน product data ที่เก่าไปบ้าง ตอน checkout จึงต้องอ่านราคาและ inventory ล่าสุดจาก source of truth อ่านต่อได้ใน [OpenSearch multi-match documentation](https://docs.opensearch.org/latest/query-dsl/full-text/multi-match/)

**Vector index — pgvector**

Vector query เรียงผลจาก distance แทนการหา exact value โดย `$1` คือ embedding จาก search text หรือ product ที่ลูกค้าเลือก

```sql
SELECT id,
       name,
       1 - (embedding <=> $1) AS similarity
FROM product_embeddings
WHERE status = 'ACTIVE'
ORDER BY embedding <=> $1
LIMIT 10;
```

Operator `<=>` ใช้คำนวณ cosine distance ผลที่ใกล้ที่สุดในเชิงคณิตศาสตร์อาจไม่ใช่ product ที่เหมาะกับลูกค้าเสมอครับ เรายังต้องมี business filter และวัดคุณภาพของผลลัพธ์ อ่านต่อได้ใน [pgvector query documentation](https://github.com/pgvector/pgvector#querying)

Product 1 ตัวใช้หลาย store ได้ แต่ data 1 ชุดควรมี source of truth ที่ชัด แล้วต้องรู้ด้วยว่า derived store จะ update หรือ repair ยังไงเมื่อ data ไม่เหมือนกัน

Discord เขียนเรื่องนี้ไว้ในบทความ [storing trillions of messages](https://discord.com/blog/how-discord-stores-trillions-of-messages) ช่วงต้นปี 2022 ระบบมี Cassandra 177 nodes แล้วเจอทั้ง hot partition, read cost, compaction และ operational toil สุดท้าย Discord เปลี่ยน database พร้อมเพิ่ม data service เพื่อลดการเข้าถึง database จาก product service แบบ direct access

เรื่องนี้ไม่ได้บอกว่า Cassandra แย่ หรือ ScyllaDB ชนะทุกกรณีครับ เวลาเลือก database ต้องดู data shape, access pattern, hotspot และความสามารถในการ operate ของทีมพร้อมกัน

### Cache: save work that repeats

Cache เก็บ data ไว้ในจุดที่อ่านได้เร็วกว่าเป็นเวลาจำกัด

![Cache hit คืน data ได้ทันที ส่วน cache miss อ่าน database แล้ว fill cache](/assets/images/blogs/practical-system-design/cache-hit-miss.png)

Cache ช่วยได้กับ:

- product และ category page ที่ถูกอ่านซ้ำบ่อย
- seller และ shipping policy ที่หลาย request ใช้
- inventory summary ที่กำหนด freshness limit ไว้แล้ว
- query ราคาแพงที่ยอมรับ stale data ได้

Cache ไม่ได้ช่วยทุก read ก่อนเพิ่มลองถาม:

- data ถูกอ่านบ่อยพอหรือยัง?
- เก่าได้แค่ไหน?
- cache miss แล้วเกิดอะไรขึ้น?
- invalidation ทำอย่างไร?
- popular key จะกลายเป็น hotspot ไหม?
- ถ้า cache ทั้งก้อน cold พร้อมกัน ระบบรับไหวหรือเปล่า?

Meta สร้าง TAO เพราะ social graph เป็น read-heavy workload ขนาดใหญ่ที่ simple database cache รับได้ไม่ดี [TAO engineering article](https://engineering.fb.com/2013/06/25/core-infra/tao-the-power-of-the-graph/) อธิบายการสร้าง graph-focused data abstraction บน MySQL และ distributed cache

Abstraction นี้ช่วยให้ product engineer ไม่ต้องรู้รายละเอียดของ cache กับ database ทุกชั้น Platform ที่ดีต้องช่วยให้ระบบ scale และทำให้ทางที่ปลอดภัยใช้งานง่ายด้วย

### Queue and workers: move slow work off the request path

ถ้าทำ payment, inventory, fulfillment, email และ analytics ใน HTTP request 1 ครั้ง request จะผูกกับ dependency หลายตัวเกินไปครับ แค่ service 1 ตัวช้าก็ timeout ได้ และการ retry อาจทำให้งานที่สำเร็จไปแล้วถูกรันซ้ำ

Queue แยกการรับงานออกจากการทำงาน

    D --> P["Event publisher"]

Design นี้ช่วยรับ burst, scale worker และ retry งานเป็นก้อนเล็กได้ ทีมยัง pause fulfillment ได้โดยไม่ทำ accepted order หาย และ track progress แยกตาม order ได้ด้วย

พอเพิ่ม queue ทีมก็มี operational responsibilities เพิ่ม:

- task เดิมอาจรันมากกว่า 1 ครั้ง
- message อาจมาไม่ตามลำดับ
- poison task อาจ fail ทุกครั้ง
- งานเก่าอาจค้างอยู่หลังงานใหม่
- queue อาจโตเร็วกว่า worker ระบายออก

Queue ไม่ได้ทำให้ระบบ reliable ขึ้นมาเองครับ producer, consumer, data model และ recovery process ต้องใช้ processing rule ชุดเดียวกัน

### Real-time connections and offline clients

Polling เริ่มต้นง่าย แต่เปลือง request ถ้า update ไม่ได้เกิดบ่อย ส่วน WebSocket หรือ server-sent events เปิดให้ server push update ผ่าน long-lived connection ได้

Connection แบบนี้เพิ่มแรงกดดันคนละแบบ:

- จำนวน connection
- heartbeat และ timeout
- connection routing
- reconnect storm
- delivery order
- slow client
- regional failover

Typing indicator ใช้แบบ best-effort ได้ เพราะ update หายไป 1 ครั้งก็มีผลกระทบน้อย แต่ message หรือ payment status ต้องมี durable storage และ acknowledgment

Offline client ต้องมี sync rule ที่ชัด วิธีที่ใช้ได้คือเก็บ cursor หรือ version แยกต่อ client หลัง reconnect ให้ client ขอเฉพาะ update หลังจุดนั้น

กรณีที่ต้องวางแผนไว้มี duplicate update, out-of-order event, deleted record, user 1 คนหลาย device, cursor เก่าเกินไป และ full snapshot ตอน delta sync ต่อไม่ได้

### Object storage: keep large immutable data outside the database

สมมุติ seller อัปโหลด product catalog ก้อนใหญ่พร้อมรูปและ specification file การยัด file ทั้งก้อนไว้ใน database row 1 แถวคงใช้งานลำบาก

เราเก็บ original catalog file, product image, invoice หรือ generated export ไว้ใน object storage ได้ ส่วน database เก็บ object key, checksum, size, version และ processing status

วิธีนี้เหมาะเมื่อ data มีขนาดใหญ่, worker อ่านเป็น batch, object ไม่เปลี่ยนหลังสร้าง หรือ audit ต้องย้อนกลับไปใช้ file version เดิมในภายหลัง

### Distributed files and chunk size

File ขนาดใหญ่มักถูกแบ่งเป็น chunk แล้วกระจายเก็บหลายเครื่องหรือหลาย object ขนาดของ chunk เปลี่ยน behavior ของระบบ:

- chunk ใหญ่ทำให้ metadata และ network call น้อยลง
- chunk เล็กทำ parallel work ได้มากและ retry งานก้อนเล็กลง
- ใหญ่เกินไปอาจสร้าง hotspot และ recovery ช้า
- เล็กเกินไปอาจทำ metadata service overload

Distributed file service ยังต้องดู chunk placement, replication, checksum, garbage collection, re-replication, metadata backup, repair และ rebalancing

เลือก chunk size จาก file size, read/write pattern, retry cost และ metadata capacity ไม่มี default ที่เหมาะกับทุก workload

Trade-off คือ object storage ไม่ได้ออกแบบมาให้ query เหมือน database การแก้ข้อมูล user 1 คนใน file ใหญ่จะแพง และ point lookup อาจต้องมี index หรือ membership store แยก

### Search index: support queries the main database cannot serve well

Search engine ช่วยเมื่อ user ต้องการ full-text search, filtering หลาย field, relevance ranking หรือ fast aggregation

กำหนด source of truth ให้ชัด ส่วน search index มักเป็น derived read model ที่รับ update จาก main database ผ่าน outbox หรือ change stream

ถ้า indexing เป็น asynchronous UI อาจเห็น product detail เก่าได้ ช้า 2–3 วินาทีอาจรับได้ใน search result แต่ checkout ต้องอ่านราคาและ inventory ล่าสุดจาก source of truth

## Correctness: Idempotency, Ordering, and Consistency

Distributed system มีโอกาสทำงานซ้ำได้เสมอครับ สาเหตุอาจมาจาก network timeout, worker crash หลังเรียก external service สำเร็จ หรือ client retry เพราะไม่รู้ว่า request ก่อนหน้าจบแบบไหน

### Idempotency

Idempotent operation คือ operation ที่รันซ้ำแล้ว final result ยังเหมือนเดิม

ตอน checkout client ส่ง idempotency key มาได้ โดย server จะเก็บ key พร้อมผลลัพธ์ของ request ครั้งที่ 1 หาก client retry ด้วย key เดิม server ก็คืนผลเดิมแทนการสร้าง order หรือตัด payment ซ้ำ

[Stripe ใช้ idempotency key](https://docs.stripe.com/api/idempotent_requests) กับ POST request เพื่อให้ client retry หลัง network error ได้อย่างปลอดภัย แนวคิดเดียวกันใช้ได้ทั้ง API, queue และ integration boundary

Deduplication key ที่ใช้ได้ เช่น:

- `checkout_id`
- `order_id + operation_type`
- request key จาก client
- payment หรือ fulfillment request key

Idempotency ต้องพึ่ง durable state เพราะ in-memory set จะหายทันทีเมื่อ process restart

### Ordering

Event ทุกตัวไม่ต้องเรียงแบบ global order คำถามคืออะไรต้องมี ordering กันแน่:

- order ทั้ง marketplace
- order ของ customer 1 คน
- state change ของ 1 order
- event ของ inventory item 1 ตัว

การรักษา ordering ภายใน key เล็ก ๆ เช่น order หรือ inventory item ทำได้ง่ายกว่าการบังคับทั้งระบบให้มี global sequence

ถ้า order สำคัญ ให้ partition message ด้วย key นั้นและป้องกัน state transition ใน database ถึงอย่างนั้นก็ยังต้องรองรับ delayed และ duplicate message อยู่ดี

### Consistency

Consistency ไม่ได้มี switch กลางที่เลือกเพียง strong หรือ eventual แล้วจบ เพราะข้อมูลแต่ละแบบใช้กติกาต่างกันได้:

- order status อาจต้องใช้ transaction
- product view counter ใช้ eventual consistency ได้
- product search result เก่าได้ 2–3 วินาที
- inventory กับราคาต้องอ่านค่าล่าสุดก่อน confirm checkout
- financial settlement ต้องการ guarantee สูงกว่า analytics dashboard

Google สร้าง [Spanner](https://research.google/pubs/spanner-googles-globally-distributed-database-2/) เพื่อรองรับ globally distributed data และ externally consistent transaction ความสามารถนี้มีประโยชน์มาก แต่แลกมากับความซับซ้อนและ trade-off ของมันเอง ก่อนเลือกต้องถามว่า operation ไหนต้องการ consistency ระดับนั้น

### Replication, CAP, and PACELC

Replication คือการ copy data ไปหลาย node เพื่อช่วย read หรือ recover หลัง failure Pattern ที่พบบ่อยมี:

- leader 1 ตัวรับ write แล้ว follower copy ตาม
- หลาย leader รับ write จากคนละ region
- leaderless replica ใช้ quorum rule สำหรับ read และ write

![Replication แบบ leader, multi-leader และ leaderless quorum](/assets/images/blogs/practical-system-design/replication-patterns.png)

Synchronous replication ปกป้องข้อมูลล่าสุดได้ดี แต่เพิ่ม write latency และอาจลด availability ตอน network มีปัญหา ส่วน asynchronous replication เร็วกว่า แต่ recent write อาจหายหลัง failover

CAP theorem มีผลตอนเกิด network partition ระบบต้องเลือกว่า operation จะรอเพื่อรักษา consistency หรือทำงานต่อพร้อมความเสี่ยงที่ data state แยกกัน

ถ้าหลายเครื่องต้องคุยผ่าน network เราตัด partition tolerance ออกจากโจทย์ไม่ได้

![ตอน network partition ระบบต้องเลือกระหว่าง consistency กับ availability](/assets/images/blogs/practical-system-design/cap-network-partition.png)

PACELC ชวนให้เราถามต่อในช่วงที่ network ยังทำงานปกติด้วย เพราะระบบมักต้องเลือกระหว่าง latency ที่ต่ำกับ consistency ที่สูงกว่า

![PACELC เทียบ consistency กับ availability ตอน partition และเทียบ latency กับ consistency ตอน network ปกติ](/assets/images/blogs/practical-system-design/pacelc-tradeoff.png)

อย่าใช้ guarantee เดียวกับทุก record ครับ cart edit, access check, progress counter และ search result ต้องการคำตอบคนละแบบ ถ้าเลือก strong consistency ให้ทุกอย่าง cost กับ latency ก็เพิ่มตาม

### Coordination and consensus

งานบางอย่างต้องใช้ coordination เพื่อให้หลาย node ตกลงค่าเดียวหรือมี owner 1 คน เช่น leader election, partition assignment, cluster membership และ shared configuration

Consensus system ช่วยให้ตกลงกันได้ แต่เพิ่ม latency กับ operational cost พยายามเก็บ coordinated state ให้เล็ก อย่าส่ง business event ทุกตัวผ่าน global lock หาก database constraint, partition owner หรือ idempotency key แก้ปัญหาเฉพาะจุดได้

### Conflict detection and resolution

Multi-writer system อาจรับ update 2 ชุดก่อนที่แต่ละฝั่งจะเห็นอีกฝั่ง Policy ที่เลือกได้มี:

- reject 1 ฝั่งด้วย optimistic concurrency control
- เลือกค่าล่าสุดจาก version หรือ timestamp ที่เชื่อถือได้
- merge field ที่เป็นอิสระจากกัน
- เก็บทั้ง 2 version เพื่อให้คนหรือ application ตัดสิน
- ใช้ convergent data type กับ counter, set หรือ data shape ที่รองรับ

Last-write-wins เรียบง่าย แต่ลบ valid update แบบเงียบ ๆ ได้ Merge policy ต้องเข้าใจ business meaning ด้วย การบวก like 2 ครั้งไม่เหมือนการเปลี่ยน account owner

## Failure Is a Normal Input

ตอนออกแบบ production system เราต้องคิดเรื่อง failure ตั้งแต่ต้นครับ ให้ความสำคัญกับ failure พอ ๆ กับ business requirement

![Reliability comes from several controls along the request path](/assets/images/blogs/practical-system-design/failure-controls.png)

ทุก dependency ต้องคิด failure mode ไว้ก่อน ทั้ง slow response, timeout, connection failure, partial success, stale response, invalid response และ outage เต็มรูปแบบ

### Timeouts

Remote call ทุกครั้งต้องมี time budget หากปล่อยให้รอโดยไม่มีขอบเขต thread, connection และ memory อาจหมดได้

ใช้ end-to-end deadline เมื่อทำได้ สมมุติ request ทั้งก้อนมีเวลา 2 วินาที dependency 1 ตัวไม่ควรกินครบ 2 วินาทีจนไม่มีเวลาเหลือให้ recovery

### Retries

Retry เมื่อการลองใหม่มีโอกาสทำให้ request สำเร็จ

กรณีที่เหมาะ:

- network ขาดช่วงสั้น ๆ
- dependency error ชั่วคราว
- rate limit ที่บอก retry time มาให้

กรณีที่ไม่ควร retry:

- input ไม่ถูกต้อง
- authorization fail
- business rule ปฏิเสธแบบถาวร
- operation ที่ทำซ้ำไม่ปลอดภัย

ใช้ exponential backoff และ jitter โดย backoff เพิ่มเวลารอหลัง fail แต่ละครั้ง ส่วน jitter เติมความต่างเล็กน้อยเพื่อไม่ให้ client จำนวนมาก retry พร้อมกัน

### Retry storms and cascading failure

Retry อาจเพิ่ม load หลายเท่าในช่วงที่ service กำลังมีปัญหา

<MermaidDiagram chart={`
flowchart TD
    C["Many clients"] --> S["Slow service"]
    S --> E["Timeouts"]
    E --> R["Immediate retries"]
    R --> M["More load"]
    M --> S

    E --> B["Bounded retry\nwith backoff and jitter"]
    B --> L["Load stays controlled"]

Google SRE อธิบายว่า overload เป็นสาเหตุสำคัญของ [cascading failure](https://sre.google/sre-book/addressing-cascading-failures/) เมื่อ replica 1 ตัวล้ม load จะย้ายไปตัวที่เหลือ ทำให้ช้าลง client เริ่ม retry แล้ว failure ก็ขยายวง

Control ที่ช่วยป้องกันมี:

- retry limit
- retry เพียง 1 layer แทนการ retry ทุก layer
- circuit breaker
- queue limit
- load shedding
- per-customer quota
- graceful degradation

[Handling overload](https://sre.google/sre-book/handling-overload/) ของ Google เตือนว่า request แต่ละแบบมี cost ไม่เท่ากัน ดูแค่ requests per second อาจไม่เห็นว่า CPU, memory, concurrency หรือ resource ตัวไหนกำลังชน limit แต่ละระบบจึงใช้ capacity signal คนละแบบได้

### Backpressure

Backpressure ให้ consumer เป็นฝ่ายบอกว่าตัวเองรับงานได้มากแค่ไหน

![Backpressure controls a large incoming flow before workers are overloaded](/assets/images/blogs/practical-system-design/backpressure-valve.png)

ใน E-commerce system worker ไม่ควรดึง order แบบไม่จำกัดเมื่อ warehouse หรือ shipping integration ช้า แม้ queue จะช่วย buffer burst ได้ แต่ต้องมี limit และแผนรับมือของทีม operation

Control ที่ใช้ได้มี worker concurrency, batch size, queue prefetch, integration rate limit, delay ระหว่าง batch และ maximum queue age

ถ้า queue age โตต่อเนื่อง อย่าเพิ่งสรุปว่าต้องเพิ่ม worker ครับ เพราะ dependency อาจรับ load หนักกว่าเดิม ทีมอาจต้องลด concurrency, pause fulfillment route บางเส้น หรือย้าย blocked order ไป manual review แทน

## Partitioning and Hotspots

พอระบบใหญ่ขึ้น data และงานอาจต้องกระจายไปหลายเครื่อง partition key จะเป็นตัวตัดสินว่า item แต่ละชิ้นไปอยู่ที่ไหน

![A partition rule spreads marketplace work into balanced groups](/assets/images/blogs/practical-system-design/partition-hotspots.png)

Key ที่พบบ่อย ได้แก่ user ID, account ID, order ID, seller ID, time bucket และ geographic region

Key ที่ดีต้องกระจาย load ได้ และยังรองรับ query หลักของระบบ ส่วน key ที่เลือกไม่ดีจะสร้าง hotspot

สมมุติ seller รายใหญ่มี order 1,000,000 รายการ ขณะที่ seller ส่วนใหญ่มี 1,000 รายการ ถ้า partition ด้วย `seller_id` อย่างเดียว งานของ seller รายใหญ่จะลง partition เดียว การเพิ่ม order ID hash หรือ time bucket ช่วยกระจายงานได้

แต่ partition มากขึ้นก็เพิ่ม cross-partition query, rebalancing, transaction ที่ซับซ้อนขึ้น, operational tool ที่ทำยากขึ้น และ migration ที่ลำบากขึ้น

Partition เมื่อ access pattern ตอนนี้ต้องใช้ และอย่าเพิ่มความซับซ้อนเพียงเพราะวันหนึ่งระบบอาจใหญ่

## Multi-Region Is a Business Decision

Multi-region architecture ช่วยเรื่อง availability และ latency ได้ แต่เมื่อเลือกใช้แล้ว data, operations และ cost จะเปลี่ยนตามไปพร้อมกัน

![A system choice should be reviewed through several business and operational constraints](/assets/images/blogs/practical-system-design/decision-lens.png)

ก่อนเลือกระหว่าง active-active กับ active-passive ให้ถาม:

- ระบบต้องรอดจาก outage แบบไหน?
- ธุรกิจรับ recovery time ได้เท่าไร?
- ยอมเสีย data ได้มากแค่ไหน?
- 2 region แก้ record เดียวกันได้หรือเปล่า?
- network partition แล้วจะทำอย่างไร?
- ทีมทดสอบ regional recovery ได้บ่อยแค่ไหน?

Product recommendation ช้าลงช่วงสั้น ๆ อาจรับได้ แต่ payment authorization หรือ inventory reservation อาจต้องการ guarantee ที่เข้มกว่า

ถ้ารัน 2 region แต่ไม่เคยทดสอบ failover ทีมจะจ่าย cost ของ multi-region เต็ม ๆ โดยยังไม่รู้ว่า recovery path ใช้งานได้หรือเปล่าครับ

## APIs and Contracts Are Part of the Design

API คือ contract ที่ให้กับ caller ต้องกำหนด resource name และ ID, request/response shape, error model, idempotency, pagination, rate limit, versioning, authentication และ authorization ให้ครบ

ถ้าเป็น asynchronous work ให้คืน order หรือ job ID เพื่อให้ caller เช็ก status หรือรับ webhook

```http
POST /orders
Idempotency-Key: 2d3817...

202 Accepted
{
  "orderId": "ord_123",
  "status": "accepted"
}
```

อย่าเปิด internal database model ผ่าน API เพราะ table ภายในเปลี่ยนได้เสมอ ส่วน contract ที่ไม่ผูกกับ table จะเปิดพื้นที่ให้ทีมแก้ implementation ภายหลังได้

Event ก็เป็น contract เช่นกัน ควรมี schema version, owner และ compatibility rule เพราะการลบหรือเปลี่ยน field อาจทำ consumer ที่เราไม่รู้จักพังได้

## Security Starts with Boundaries

Version 1 มี authentication, authorization, secret handling และ audit trail ขั้นพื้นฐานแล้ว พอระบบโตแต่ละ boundary ต้องละเอียดขึ้น เพราะ Security ไม่ได้จบที่ box 1 ใบข้าง diagram

ลองถามระบบว่า:

- ใครเรียก API นี้ได้?
- customer หรือ seller คนนี้ดูหรือแก้ order ไหนได้บ้าง?
- service ไหนอ่าน customer หรือ payment data ได้?
- data ใดต้อง encrypt?
- action ไหนต้องสร้าง audit event?
- worker แต่ละตัวเข้าถึง secret อะไรได้?
- tenant data แยกกันอย่างไร?

Control ที่ควรพิจารณามีหลายชั้น:

- authentication และ role/attribute-based authorization
- least-privilege service identity
- encryption in transit และ at rest
- secret rotation และ network boundary
- immutable audit log
- data retention และ deletion policy

ตรวจ authorization ที่ resource boundary ตัวอย่างเช่น seller ที่แก้ product ของตัวเองได้ ไม่ควรเข้าถึง product ของ seller รายอื่นเพียงเปลี่ยน ID ใน URL

สำหรับ sensitive flow การแยก account, cloud profile, database หรือ payment worker อาจคุ้มกับ cost ที่เพิ่ม เพราะช่วยลดทั้ง failure surface และ access surface

## Observability Must Answer Operational Questions

Version 1 มี log, metric, correlation ID และ alert ขั้นพื้นฐานแล้ว พอ flow โต คำถามที่ทีมต้องตอบก็ละเอียดขึ้นตาม

Log, metric และ trace เป็นเครื่องมือ ก่อนเลือกลองเริ่มจากคำถามที่ทีมต้องตอบ:

- order ถูก accept และจ่ายเงินแล้วหรือยัง?
- มี order รอ fulfillment กี่รายการ?
- order เก่าสุดรอนานเท่าไร?
- payment, warehouse หรือ shipping integration ตัวไหนช้า?
- order สำเร็จ fail หรือต้อง manual review กี่รายการ?
- seller 1 รายใช้ capacity ส่วนใหญ่หรือเปล่า?
- pause fulfillment route 1 เส้นอย่างปลอดภัยได้ไหม?
- replay failed order step ได้หรือเปล่า?

Metric ที่ควรมีต้องครอบคลุม traffic, dependency และ business flow เช่น:

- request rate, error rate และ latency
- queue depth และ queue age
- worker throughput และ retry count
- integration response code
- database connection usage และ cache hit rate
- order และ fulfillment progress

ใช้ correlation ID เช่น order ID, customer ID, payment attempt ID และ fulfillment request ID เพื่อให้เวลามีปัญหา ทีมตาม 1 flow ข้ามหลาย service ได้ง่ายขึ้น

Alert ที่ดีต้องนำไปสู่ action ได้ Queue depth สูงยังพอรับได้ถ้า worker ระบายทัน แต่ถ้า queue age เริ่มทำให้ส่งของช้ากว่าที่รับปากลูกค้า metric นี้สำคัญกว่า

## Ownership Changes the Design

Technology 2 ตัวอาจแก้ technical problem เดียวกันได้ แต่แต่ละทีมอาจเลือกไม่เหมือนกัน เพราะ operational readiness ต่างกัน

![Owning a decision means explaining why, trade-offs, failure, and ownership](/assets/images/blogs/practical-system-design/own-the-decision.png)

เช็กมุมพวกนี้ด้วย:

- **Skills:** ทีม debug และ upgrade เป็นไหม?
- **Operations:** ใคร on-call ให้ระบบนี้?
- **Cost:** traffic โต 10 เท่าแล้วค่าใช้จ่ายเป็นอย่างไร?
- **Security:** เพิ่ม data หรือ access boundary ใหม่ไหม?
- **Delivery:** setup และ migration ใช้เวลานานแค่ไหน?
- **Reversal:** ถ้าจะเปลี่ยนออกยากเพียงใด?
- **Organization:** boundary ของระบบเข้ากับ team ownership หรือเปล่า?

เรื่อง storage ของ Discord มีทั้ง benchmark, unpredictable latency และ operational toil ส่วน TAO ของ Meta ก็ไม่ได้หยุดที่การเพิ่ม cache แต่สร้าง abstraction เพื่อให้ product team ไม่ต้องดูแลรายละเอียดทุกชั้น

เพราะแบบนี้ architecture ที่เล็กกว่าอาจสะท้อน engineering judgment ที่ดีกว่า เพราะ design จะมีประโยชน์ก็ต่อเมื่อทีมดูแลให้มันทำงานต่อไปได้

## Migration Is Part of System Design

ระบบส่วนใหญ่ไม่ได้เริ่มจากพื้นที่ว่าง เราต้องออกแบบ migration path จาก design เดิมไปหา design ใหม่ด้วย

Safe migration อาจใช้ขั้นตอนเหล่านี้:

1. **Shadow reads:** อ่านจากระบบใหม่ แต่ยังไม่ใช้คำตอบ
2. **Dual writes:** เขียนลง old และ new store ในช่วงจำกัด
3. **Backfill:** copy data เก่าพร้อม checksum และ progress tracking
4. **Small rollout:** ย้าย tenant, region หรือ traffic percentage เล็ก ๆ ก่อน
5. **Compare:** เทียบ data, latency, error และ business result
6. **Cut over:** ย้าย new path ขึ้นเป็น primary
7. **Keep rollback:** เก็บทางกลับไว้จนมั่นใจพอ

Dual write อาจ fail แค่ 1 ฝั่ง ต้องวางแผน reconciliation ก่อนเปิดใช้

Migration tool เองก็ต้องมี idempotency, monitoring, pause, resume และ audit support เพราะ temporary system มักถูกใช้งานนานกว่าที่ทีมวางแผนไว้

## A Coaching Method for System Design

เวลา coach ผมจะไม่เริ่มด้วยการขอ complete architecture ครับ ผมจะช่วยย่อปัญหาให้เล็กพอที่เราจะคุยกันได้ก่อน แล้วค่อยชวนคุณเพิ่ม constraint ทีละข้อ

Coaching loop ทำได้แบบนี้:

1. ให้ engineer อธิบาย user และเป้าหมาย
2. หา requirement ที่ทำให้ design เปลี่ยน
3. วาด version เล็กที่สุดที่ทำงานได้
4. เพิ่ม constraint 1 ข้อ
5. ถามว่าอะไรจะพังก่อน
6. เทียบ 2 หรือ 3 option
7. หา deciding factor ของแต่ละ option
8. ระบุ trade-off และ owner
9. เติม failure และ recovery path
10. กำหนด revisit condition ว่าเมื่อไหร่ทีมควรกลับมาเปลี่ยนคำตอบ

คำถามที่ใช้คุยต่อได้ เช่น:

- source of truth อยู่ไหน?
- อะไรอยู่บน hot path?
- งานไหนย้ายไป asynchronous ได้?
- อะไรรันซ้ำได้บ้าง?
- data หายที่ไหนได้?
- key ไหนอาจ hot?
- ถ้า dependency ช้าแต่ยังไม่ล้มจะเกิดอะไรขึ้น?
- ทีมรู้ได้อย่างไรว่าระบบกำลังป่วย?
- ส่วนไหนเปลี่ยนยากที่สุด?
- ถ้ามีทีม 3 คน คุณยังเลือกแบบเดิมไหม?

Mentor ไม่จำเป็นต้องซ่อนคำตอบ เพราะเป้าหมายคือช่วยให้ engineer เชื่อมคำตอบแต่ละข้อเข้ากับเหตุผล จนวันหนึ่งเขาถามคำถามเหล่านี้ได้ด้วยตัวเอง

ตอนเริ่ม design ใหม่ ลองจดข้อมูลชุดนี้:

## Final Thoughts

System Design มีทั้ง database, cache, queue, load balancer, API, partition, region และเครื่องมืออีกมาก และการเรียนว่าแต่ละตัวทำอะไรยังสำคัญอยู่

แต่เป้าหมายสุดท้ายไม่ใช่การจำชื่อ component ให้ครบ

ทักษะที่ควรฝึกคือการอธิบายให้ได้ว่า:

- ปัญหาคืออะไร
- design เล็กที่สุดที่ทำงานได้เป็นแบบไหน
- constraint ข้อไหนบังคับให้ design เปลี่ยน
- option นี้เข้ากับ data, traffic และทีมอย่างไร
- อะไรพังได้
- เรายอมรับ trade-off อะไร
- ใครเป็น owner
- เมื่อไหร่ควรกลับมาทบทวน

เมื่อฝึกแบบนี้ การวาด box เป็นแค่จุดเริ่มต้นครับ สิ่งที่ตามมาคือการอธิบายและรับผิดชอบทุก decision ใน design ที่เลือก
