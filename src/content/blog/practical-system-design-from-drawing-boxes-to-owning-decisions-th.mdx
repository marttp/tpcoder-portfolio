## Why This Guide Exists

เวลาเราเรียน System Design ภาพแรกที่เจอมักเป็น diagram ใหญ่ ๆ ครับ มี load balancer, cache, queue, database, worker, region แล้วก็ลูกศรเต็มไปหมด

ภาพแบบนั้นดูครบดี แต่คำถามสำคัญกลับหายไปว่า **ทำไมระบบถึงต้องมีกล่องแต่ละใบ?**

การบอกว่าเพิ่ม component อะไรเข้าไปนั้นง่ายครับ ส่วนที่ยากกว่าคืออธิบายให้ได้ว่า component นี้แก้ปัญหาอะไร อะไรพังได้ แล้วหลังจากขึ้น production ใครจะดูแลต่อ

บทความนี้ต่อยอดจาก [complete System Design guide](https://www.systemdesignhandbook.com/guides/system-design-interview/) และ [senior engineer questions](https://www.systemdesignhandbook.com/guides/system-design-interview-questions-for-senior-software-engineer/) ซึ่งครอบคลุม principles, building blocks และคำถามของระบบขนาดใหญ่ไว้กว้างมาก

ส่วนบทความของผมจะตัดเรื่อง interview process ออก แล้วเรียงเนื้อหาให้ใช้ coach หรือ mentor คนที่กำลังฝึก System Design ได้ง่ายขึ้น

แกนหลักมีประโยคเดียวครับ:

**System Design คือการเปลี่ยนปัญหาให้เป็นระบบที่ทีมสร้าง รัน แก้ และรับผิดชอบต่อได้**

เราจะเริ่มจากระบบเล็ก ๆ หนึ่งตัว จากนั้นค่อยใส่ constraint ทีละข้อ ระหว่างทางคุณจะได้เจอทั้ง data, scaling, failure, security, operations และ engineering judgment

บทความเดียวคงครอบคลุมระบบทุกแบบไม่ได้ครับ เป้าหมายของผมคือช่วยให้คุณตั้งคำถามได้ดีขึ้น เมื่อระบบถัดไปมีหน้าตาไม่เหมือนตัวอย่างนี้ และให้คุณอธิบายเหตุผลของ design ได้โดยไม่ต้องจำ diagram สำเร็จรูป

## Start with the Problem, Not the Components

สมมุติว่าเรากำลังออกแบบ multi-tenant employee onboarding platform

HR จะสร้าง onboarding case เลือก role กับ location ของพนักงาน ใส่ onboarding plan และกำหนด start date ระบบต้อง schedule งานให้ HR, IT, payroll และ integration ที่ได้รับอนุญาต พร้อมบอกได้ว่าแต่ละขั้นตอนไปถึงไหนแล้ว

ก่อนวาด diagram ลองถามก่อนครับว่าระบบต้องทำอะไร

### Functional requirements

สิ่งที่ user ต้องใช้งานได้มีประมาณนี้:

- สร้างและแก้ onboarding case
- ลงทะเบียนพนักงานและเลือก onboarding plan ให้ถูกคน
- schedule task จาก start date
- pause หรือ cancel case ก่อน automated task เริ่ม
- assign task ให้คนหรือ integration ที่ได้รับอนุญาต
- แสดง progress ของแต่ละ onboarding step

### Non-functional requirements

ส่วนนี้บอกว่าระบบต้องทำงานได้ดีแค่ไหน:

- **Correctness:** พนักงานต้องอยู่ใน tenant ที่ถูก และได้ plan ที่ถูก
- **Availability:** scheduled work ยังต้องเริ่มได้แม้ server บางตัวล้ม
- **Durability:** schedule ที่รับแล้วต้องไม่หาย
- **Scale:** ต้องรองรับ seasonal hiring ก้อนใหญ่จากหลาย tenant
- **Security:** เฉพาะ HR และ service ที่ได้รับอนุญาตเท่านั้นจึงจะเข้าถึงข้อมูลหรือเริ่ม sensitive task ได้
- **Auditability:** ทีมต้องรู้ว่าใครเปลี่ยนอะไร เมื่อไหร่

อย่าเพิ่งเขียน requirement ทุกอย่างที่นึกออกครับ ให้หาเฉพาะข้อที่ทำให้ design เปลี่ยน

ตัวอย่างเช่น welcome checklist ช้าไปหนึ่งนาทีอาจไม่เป็นไร แต่ถ้าเป็นการ revoke access ของพนักงานที่ออกจากบริษัท หนึ่งนาทีก็อาจนานเกินไป ทั้งคู่เป็น HR workflow เหมือนกัน แต่ quality goal คนละแบบ

ก่อนเลือก technology ลองถามหกข้อนี้:

1. ใครเป็นคนใช้ระบบ?
2. เหตุการณ์อะไรห้ามเกิด?
3. งานไหนทำทีหลังได้?
4. ข้อมูลอะไรเสียได้บ้าง?
5. ถ้า dependency ใช้งานไม่ได้จะเกิดอะไรขึ้น?
6. action ไหนสร้างต้นทุนให้ธุรกิจหรือลูกค้า?

คำถามพวกนี้ทำให้ทุกกล่องบน diagram มีเหตุผลรองรับครับ

## Core Quality Goals Pull the Design in Different Directions

ระบบหนึ่งตัวทำทุก quality ให้สูงสุดพร้อมกันไม่ได้ เราต้องรู้ก่อนว่าข้อไหนสำคัญกว่า

- **Scalability** คือความสามารถในการรับ user, data หรืองานที่เพิ่มขึ้น
- **Performance** พูดถึงความเร็วและ resource ที่ใช้ โดยมักดู latency กับ throughput
- **Availability** บอกว่าระบบพร้อมรับงานที่มีประโยชน์บ่อยแค่ไหน
- **Reliability** บอกว่าระบบยังให้ผลลัพธ์ที่ถูกต้องต่อเนื่องหรือเปล่า
- **Consistency** บอกว่า reader หลายคนเห็น data state เดียวกันเมื่อไหร่
- **Security** กำหนดว่าใครเข้าถึง data และ action อะไรได้

Availability กับ reliability เกี่ยวข้องกัน แต่ไม่เท่ากันครับ service อาจตอบกลับได้ทุก request ทั้งที่ข้อมูลเก่าหรือผิด แบบนี้ available แต่ไม่น่าเชื่อถือ

เปลี่ยนคำกว้าง ๆ ให้เป็นเป้าหมายที่วัดได้ เช่น:

- p95 และ p99 latency
- request หรือ job ต่อวินาที
- queue age สูงสุด
- error rate ที่รับได้
- recovery time objective หรือ RTO
- recovery point objective หรือ RPO
- data freshness
- monthly availability

99.9% monthly availability ยอมให้ระบบหยุดได้ประมาณ 43 นาทีต่อเดือน หากอยากได้สูงกว่านี้ก็ต้องแลกด้วย redundancy, testing, automation และ cost มากขึ้น เลือกจาก business impact ครับ อย่าเลือกเพราะทุกทีมเขียนเลขเดียวกัน

## Estimate Only What Can Change the Design

Estimation มีประโยชน์เมื่อเลขนั้นเปลี่ยนการตัดสินใจ ไม่ต้องแข่งกันทายให้เป๊ะทุกหลัก

สมมุติลูกค้ารายใหญ่ import พนักงานตามฤดูกาล 100,000 คน แต่ละ onboarding plan สร้าง task เฉลี่ย 50 รายการ และ task record หนึ่งรายการมีขนาด 2 KB

คำถามที่ควรถามมีประมาณนี้:

- onboarding run จะสร้าง task กี่รายการ?
- งานทั้งหมดจบช้าได้แค่ไหน?
- identity, payroll และ equipment integration รับ peak rate ไหวหรือเปล่า?
- execution history ต้องเก็บมากแค่ไหน?
- traffic เข้ามาเรื่อย ๆ หรือกระแทกเข้ามาเป็นก้อน?

เราจะได้ task ประมาณ 5 ล้านรายการ ถ้า queue message หนึ่งก้อนมี 500 task ก็จะมีประมาณ 10,000 message

```text
100,000 employees x 50 tasks / 500 tasks per chunk = 10,000 chunks
```

เลข 10,000 ช่วยคิดต่อเรื่อง queue size, worker concurrency, progress tracking, retry scope และ operational tools ได้มากกว่า total user count เสียอีก

ให้เวลาเฉพาะเลขที่มีผลต่อ design:

- **Request rate** สำคัญเมื่อ service หรือ dependency อาจรับไม่ไหว
- **Record size** สำคัญเมื่อ storage หรือ network cost สูง
- **Read-to-write ratio** สำคัญเมื่อต้องตัดสินใจเรื่อง cache
- **Peak traffic** สำคัญเมื่อ average ซ่อน burst ไว้
- **Recovery time** สำคัญเมื่อ outage กระทบธุรกิจ

ถ้าเลขไหนไม่เปลี่ยน design ก็ข้ามไปก่อนได้ครับ

Application เก็บ onboarding case กับ schedule ลง database แล้วใช้ timer ตรวจ task ที่ถึงเวลา ก่อนเรียก integration ที่เกี่ยวข้อง

สำหรับทีมเล็กและ volume ยังน้อย แค่นี้อาจพอแล้วครับ เข้าใจง่าย deploy ง่าย และ debug ง่าย

อย่าใช้คำว่า naive เพื่อดูถูก design เล็ก ๆ ระบบเล็กมักเป็นคำตอบที่เหมาะกับปัญหาเล็ก

ก่อนเพิ่ม component ทำเวอร์ชันนี้ให้ปลอดภัยก่อน:

- เก็บ timestamp ด้วย time zone ที่ตกลงกัน ส่วนมากคือ UTC
- schedule ที่รับแล้วต้องอยู่ใน durable database ไม่ใช่ process memory
- บันทึก task attempt
- ทำ integration call ให้ idempotent เมื่อทำได้
- ป้องกันการสร้าง onboarding case ด้วย authentication และ authorization

จากนั้นรอให้ constraint เป็นตัวบอกว่า design ต้องโตไปทางไหน

### Scale up or scale out

เพิ่ม capacity ได้สองทางหลัก:

- **Vertical scaling:** เพิ่ม CPU, memory, disk หรือ network ให้เครื่องเดิม
- **Horizontal scaling:** เพิ่มจำนวนเครื่อง แล้วกระจายงานออกไป

Vertical scaling เริ่มง่ายกว่า แต่มีเพดาน hardware และยังเหลือ failure point ขนาดใหญ่หนึ่งจุด ส่วน horizontal scaling โตต่อได้และแยก failure ได้ดีขึ้น แต่ต้องมี load distribution, partitioning, coordination และ operational tools

ระบบจำนวนมากใช้ทั้งสองแบบ เช่น database อาจเริ่มจากขยับไปเครื่องใหญ่ขึ้น ส่วน application server scale out ได้ง่ายกว่าเพราะทำให้ stateless ได้

### CDN and edge delivery

CDN เก็บ content ที่ cache ได้ไว้ใกล้ user เหมาะกับ image, video, JavaScript, download และ public API response ที่ cache ได้อย่างปลอดภัย

CDN ลด origin traffic และ latency ได้ แต่เพิ่มเรื่องที่ต้องตัดสินใจ:

- cache key
- cache duration
- invalidation
- private กับ public content
- regional rule
- behavior ตอน origin ใช้งานไม่ได้

อย่า cache private content ด้วย key ที่ไม่สนใจ user หรือ tenant ครับ

### Load balancer: when one application is not enough

Load balancer กระจาย traffic ไปหลาย application instance มีประโยชน์เมื่อ:

- instance เดียวรับ traffic ไม่ไหว
- ต้อง deploy โดยไม่หยุด traffic ทั้งหมด
- ต้องเอา unhealthy instance ออกจากระบบ
- อยากส่ง request ไป region หรือ zone ที่ใกล้กว่า

พอมี load balancer ก็มีคำถามเพิ่ม:

- application stateless หรือยัง?
- session state อยู่ไหน?
- health check รู้ได้อย่างไรว่า instance พร้อมรับงาน?
- ถ้าทุก instance overload จะทำอย่างไร?

Health check ควรเช็ก readiness ที่ใช้งานได้ครับ process อาจตอบ HTTP ได้ทั้งที่ database pool เต็มไปแล้ว

### API gateway and rate limiting

API gateway เป็น entry point กลางสำหรับ authentication, routing, request limit, protocol conversion และ shared logging เหมาะเมื่อ client หลายแบบเรียก service หลายตัว

ข้อควรระวังคือ gateway อาจกลายเป็น shared failure point ขนาดใหญ่ จึงควรจำกัดงานของมันและรันแบบมี redundancy

Rate limiting ช่วยป้องกัน capacity และแบ่ง usage ให้เป็นธรรม policy ที่พบบ่อยมี:

- fixed หรือ sliding time window
- token bucket ที่ยอมให้ burst ได้ตามขอบเขต
- leaky bucket ที่ทำ traffic ให้ไหลสม่ำเสมอ
- concurrency limit สำหรับงานแพง
- quota แยกตาม user, tenant, API key หรือ region

เวลาชน limit ควรตอบ error และ retry time ให้ client เข้าใจ หากบอกเพียงว่าโดนจำกัด client อาจยิ่ง retry ถี่กว่าเดิม

### Database: choose from the access pattern

การเลือก database เริ่มจากวิธีที่ระบบอ่านและเขียน data

![Different access patterns lead to different data designs](/assets/images/blogs/practical-system-design/choose-for-access-pattern.png)

สำหรับ onboarding system เราอาจมี record หลักดังนี้:

- onboarding case
- employee profile reference
- onboarding plan
- scheduled task
- task attempt
- audit event

Relational database เป็นตัวเลือกแรกที่ดี เมื่อระบบต้องใช้ transaction, relationship ที่ชัด และ operational query ที่ยืดหยุ่น

Key-value หรือ wide-column store ช่วยได้เมื่อ access pattern เรียบง่ายและ volume สูงมาก แต่ data model ต้องออกแบบตาม query อยู่ดี distributed database ไม่ได้ทำให้ data modeling หายไป กลับยิ่งบังคับให้ access pattern สำคัญขึ้น

Storage แต่ละตระกูลเหมาะกับงานคนละทรง:

- **Relational:** transaction, relationship, constraint และ query ที่ยืดหยุ่น
- **Key-value:** lookup เร็วจาก key ที่รู้ล่วงหน้า
- **Document:** record ที่มี nested field และ schema ยืดหยุ่น
- **Wide-column:** data ปริมาณมากที่จัดกลุ่มด้วย partition key
- **Time-series:** metric และ event ตามเวลา พร้อม retention rule
- **Graph:** เดิน relationship หลายชั้น
- **Object storage:** file ใหญ่หรือ immutable data ในต้นทุนต่ำ
- **Search index:** text search, ranking, filtering และ aggregation
- **Vector index:** similarity search จาก embedding

Product หนึ่งตัวใช้หลาย store ได้ครับ แต่ fact หนึ่งเรื่องควรมี source of truth หนึ่งแห่ง พร้อมระบุให้ได้ว่า derived store อัปเดตและ repair อย่างไร

Discord เขียนเรื่องนี้ไว้ในบทความ [storing trillions of messages](https://discord.com/blog/how-discord-stores-trillions-of-messages) ช่วงต้นปี 2022 ระบบมี Cassandra 177 nodes แล้วเจอทั้ง hot partition, read cost, compaction และ operational toil สุดท้าย Discord เปลี่ยน database พร้อมเพิ่ม data service เพื่อลดการเข้าถึง database จาก product service แบบ direct access

บทเรียนไม่ใช่ว่า Cassandra แย่ หรือ ScyllaDB ชนะทุกกรณีครับ ประเด็นคือ data shape, access pattern, hotspot และความสามารถในการ operate ของทีมต้องอยู่ในการตัดสินใจเดียวกัน

### Cache: save work that repeats

Cache เก็บ data ไว้ในจุดที่อ่านได้เร็วกว่าเป็นเวลาจำกัด เช่น:

- onboarding plan ที่ถูกอ่านซ้ำบ่อย
- role และ location policy ที่ worker หลายตัวใช้
- integration credential หรือ routing rule
- query ราคาแพงที่ยอมรับ stale data ได้

Cache ไม่ได้ช่วยทุก read ก่อนเพิ่มลองถาม:

- data ถูกอ่านบ่อยพอหรือยัง?
- เก่าได้แค่ไหน?
- cache miss แล้วเกิดอะไรขึ้น?
- invalidation ทำอย่างไร?
- popular key จะกลายเป็น hotspot ไหม?
- ถ้า cache ทั้งก้อน cold พร้อมกัน ระบบรับไหวหรือเปล่า?

Meta สร้าง TAO เพราะ social graph เป็น read-heavy workload ขนาดใหญ่ที่ simple database cache รับได้ไม่ดี [TAO engineering article](https://engineering.fb.com/2013/06/25/core-infra/tao-the-power-of-the-graph/) อธิบายการสร้าง graph-focused data abstraction บน MySQL และ distributed cache

Abstraction นี้ยังลดภาระให้ product engineer ไม่ต้องรู้รายละเอียด cache กับ database ทุกชั้นด้วย Platform ที่ดีควรช่วย scale พร้อมทำให้ทางเลือกที่ปลอดภัยเป็นทางที่เดินง่ายครับ

### Queue and workers: move slow work off the request path

การประมวลผล onboarding task หลายล้านรายการใน HTTP request เดียวไปไม่รอดแน่ request จะ timeout และ failure ครั้งเดียวอาจทำให้เริ่มงานก้อนใหญ่อีกครั้ง

Queue แยกการรับงานออกจากการทำงาน

<MermaidDiagram chart={`
flowchart LR
    A["Onboarding API"] --> D["Onboarding DB"]
    S["Scheduler"] --> D
    S --> Q["Task queue"]
    Q --> W1["Worker 1"]
    Q --> W2["Worker 2"]
    Q --> W3["Worker N"]
    W1 --> P["HR and IT integrations"]
    W2 --> P
    W3 --> P
    W1 --> R["Task results"]
    W2 --> R
    W3 --> R
`} />

Design นี้ช่วยรับ burst, scale worker, retry งานก้อนเล็ก, pause processing โดยไม่ทำ onboarding run หาย และ track progress แยกตาม chunk

แต่ queue ก็สร้างสิ่งที่ทีมต้องรับผิดชอบเพิ่ม:

- task เดิมอาจรันมากกว่าหนึ่งครั้ง
- message อาจมาไม่ตามลำดับ
- poison task อาจ fail ทุกครั้ง
- งานเก่าอาจค้างอยู่หลังงานใหม่
- queue อาจโตเร็วกว่า worker ระบายออก

Queue ไม่ได้เสก reliability ขึ้นมาเอง producer, consumer, data model และ recovery process ต้องตกลง processing rule ชุดเดียวกัน

### Real-time connections and offline clients

Polling เรียบง่าย แต่เปลือง request เมื่อ update ไม่ได้เกิดบ่อย WebSocket หรือ server-sent events ให้ server push update ผ่าน long-lived connection ได้

Connection แบบนี้เพิ่มแรงกดดันคนละแบบ:

- จำนวน connection
- heartbeat และ timeout
- connection routing
- reconnect storm
- delivery order
- slow client
- regional failover

Typing indicator เป็น best-effort ได้เพราะพลาดแล้วต้นทุนต่ำ ส่วน message หรือ payment status ต้องมี durable storage และ acknowledgment

Offline client ต้องมีกติกา sync ที่ชัด วิธีหนึ่งคือเก็บ cursor หรือ version แยกต่อ client หลัง reconnect ให้ client ขอเฉพาะการเปลี่ยนแปลงหลังจุดนั้น

กรณีที่ต้องวางแผนไว้มี duplicate update, out-of-order event, deleted record, user คนเดียวหลาย device, cursor เก่าเกินไป และ full snapshot ตอน delta sync ต่อไม่ได้

### Object storage: keep large immutable data outside the database

สมมุติ onboarding run หนึ่ง import พนักงาน 100,000 คน พร้อม document และ task input การยัด import ทั้งก้อนไว้ใน database row เดียวคงใช้งานลำบากครับ

Object storage เก็บ original import, employee document หรือ task chunk ที่เตรียมไว้ล่วงหน้า ส่วน database เก็บ object key, checksum, size, version และ processing status

เหมาะเมื่อ data มีขนาดใหญ่ worker อ่านเป็น batch object ไม่เปลี่ยนหลังสร้าง และ audit อาจต้องใช้ import version เดิมในภายหลัง

### Distributed files and chunk size

File ขนาดใหญ่มักถูกแบ่งเป็น chunk แล้วกระจายเก็บหลายเครื่องหรือหลาย object ขนาดของ chunk เปลี่ยน behavior ของระบบ:

- chunk ใหญ่ทำให้ metadata และ network call น้อยลง
- chunk เล็กทำ parallel work ได้มากและ retry งานก้อนเล็กลง
- ใหญ่เกินไปอาจสร้าง hotspot และ recovery ช้า
- เล็กเกินไปอาจทำ metadata service overload

Distributed file service ยังต้องดู chunk placement, replication, checksum, garbage collection, re-replication, metadata backup, repair และ rebalancing

เลือก chunk size จาก file size, read/write pattern, retry cost และ metadata capacity ไม่มีค่า default เดียวที่เหมาะกับทุก workload

ส่วน trade-off คือ object storage ไม่ใช่ database ปกติ การแก้ user คนเดียวใน file ใหญ่มีต้นทุนสูง และ point lookup อาจต้องใช้ index หรือ membership store แยก

### Search index: support queries the main database cannot serve well

Search engine ช่วยเมื่อ user ต้องการ full-text search, filtering หลาย field, relevance ranking หรือ fast aggregation

กำหนด source of truth ให้ชัดครับ search index มักเป็น derived read model ซึ่งรับ update จาก main database ผ่าน outbox หรือ change stream

ถ้า indexing เป็น asynchronous UI อาจเห็นผลลัพธ์เก่าได้ ช้าสองสามวินาทีอาจรับได้สำหรับ onboarding case search แต่ใช้กับ access หรือ security policy check ไม่ได้

## Correctness: Idempotency, Ordering, and Consistency

Distributed system มีโอกาสทำงานซ้ำเสมอ network timeout, worker crash หลังเรียก external service สำเร็จ หรือ client retry เพราะไม่รู้ว่า request ก่อนหน้าจบแบบไหน

### Idempotency

Idempotent operation รันมากกว่าหนึ่งครั้งแล้ว final result ยังเหมือนเดิม

ตอนสร้าง onboarding run client อาจส่ง idempotency key มา server จะเก็บ key พร้อมผลลัพธ์ของ request แรก หาก retry ด้วย key เดิมก็คืนผลเดิมแทนการสร้าง run ใหม่

[Stripe ใช้ idempotency key](https://docs.stripe.com/api/idempotent_requests) กับ POST request เพื่อให้ client retry หลัง network error ได้อย่างปลอดภัย แนวคิดเดียวกันใช้ได้ทั้ง API, queue และ integration boundary

Deduplication key ที่ใช้ได้ เช่น:

- `onboarding_run_id + employee_id + task_type`
- `onboarding_run_id + chunk_id`
- request key จาก client
- integration request key

Idempotency ต้องพึ่ง durable state ครับ in-memory set จะหายทันทีเมื่อ process restart

### Ordering

Event ทุกตัวไม่ต้องมี global order ลองถามก่อนว่าอะไรต้องเรียงลำดับกันแน่:

- onboarding run ทั้งบริษัท
- task ของ employee คนเดียว
- state change ของ onboarding case เดียว
- event ภายใน task chunk เดียว

การรักษาลำดับต่อ key เล็ก ๆ เช่น case หรือ employee ง่ายกว่าบังคับทั้งระบบให้เรียงเป็นเส้นเดียว

ถ้า order สำคัญ ให้ partition message ด้วย key นั้นและป้องกัน state transition ใน database ถึงอย่างนั้นก็ยังต้องรองรับ delayed และ duplicate message อยู่ดี

### Consistency

Consistency ไม่ใช่ switch ที่เลือกเพียง strong หรือ eventual ข้อมูลแต่ละแบบใช้กติกาต่างกันได้:

- onboarding case status อาจต้องใช้ transaction
- progress counter ใช้ eventual consistency ได้
- search result เก่าได้สองสามวินาที
- employee access state ต้องอ่านค่าล่าสุดก่อน provisioning
- financial settlement ต้องการ guarantee สูงกว่า analytics dashboard

Google สร้าง [Spanner](https://research.google/pubs/spanner-googles-globally-distributed-database-2/) เพื่อรองรับ globally distributed data และ externally consistent transaction ความสามารถนี้มีประโยชน์มาก แต่ก็มาจากระบบที่ซับซ้อนและ trade-off เฉพาะตัว ระบบส่วนใหญ่ควรถามก่อนว่า operation ไหนต้องการ consistency ระดับนั้น

### Replication, CAP, and PACELC

Replication copy data ไปหลาย node เพื่อให้ node อื่นช่วย read หรือ recover หลัง failure ได้ รูปแบบที่พบบ่อยมี:

- leader หนึ่งตัวรับ write แล้ว follower copy ตาม
- หลาย leader รับ write จากคนละ region
- leaderless replica ใช้ quorum rule สำหรับ read และ write

Synchronous replication ปกป้องข้อมูลล่าสุดได้ดี แต่เพิ่ม write latency และอาจลด availability ตอน network มีปัญหา ส่วน asynchronous replication เร็วกว่า แต่ recent write อาจหายหลัง failover

CAP theorem มีผลตอน network partition ระบบต้องเลือกว่า operation จะรอเพื่อรักษา consistency หรือทำต่อพร้อมความเสี่ยงที่ data state แยกกัน เมื่อเครื่องต้องคุยผ่าน network เราตัด partition tolerance ออกจากโจทย์ไม่ได้

PACELC เพิ่มคำถามของช่วงปกติด้วย ต่อให้ network ไม่ขาด ระบบก็มักแลก latency ที่ต่ำกับ consistency ที่สูงกว่า

อย่าใช้ guarantee เดียวกับทุก record ครับ case edit, access check, progress counter และ search result อาจต้องการคำตอบคนละแบบ ถ้าคุณเลือก strong consistency ให้ทุกอย่าง cost กับ latency ก็จะตามมาด้วย

### Coordination and consensus

งานบางอย่างต้องให้หลาย node ตกลงค่าเดียวหรือ owner คนเดียว เช่น leader election, partition assignment, cluster membership และ shared configuration

Consensus system ช่วยให้ตกลงกันได้ แต่เพิ่ม latency กับ operational cost พยายามเก็บ coordinated state ให้เล็ก อย่าส่ง business event ทุกตัวผ่าน global lock หาก database constraint, partition owner หรือ idempotency key แก้ปัญหาเฉพาะจุดได้

### Conflict detection and resolution

Multi-writer system อาจรับ update สองชุดก่อนที่แต่ละฝั่งจะเห็นอีกฝั่ง Policy ที่เลือกได้มี:

- reject ฝั่งหนึ่งด้วย optimistic concurrency control
- เลือกค่าล่าสุดจาก version หรือ timestamp ที่เชื่อถือได้
- merge field ที่เป็นอิสระจากกัน
- เก็บทั้งสอง version เพื่อให้คนหรือ application ตัดสิน
- ใช้ convergent data type กับ counter, set หรือ data shape ที่รองรับ

Last-write-wins เรียบง่าย แต่ลบ valid update แบบเงียบ ๆ ได้ Merge policy ต้องเข้าใจ business meaning ด้วย การบวก like สองครั้งไม่เหมือนการเปลี่ยน account owner

## Failure Is a Normal Input

Production system เจอ failure เป็น input ปกติพอ ๆ กับ business requirement ครับ

![Reliability comes from several controls along the request path](/assets/images/blogs/practical-system-design/failure-controls.png)

สำหรับ dependency ทุกตัว ลองคิดให้ครบทั้ง slow response, timeout, connection failure, partial success, stale response, invalid response และ outage เต็มรูปแบบ

### Timeouts

Remote call ทุกครั้งต้องมี time budget ถ้าไม่มี request อาจรอจน thread, connection และ memory หมด

ใช้ end-to-end deadline เมื่อทำได้ สมมุติ request ทั้งก้อนมีเวลาสองวินาที dependency ตัวเดียวไม่ควรกินครบสองวินาทีจนไม่มีเวลาเหลือให้ recovery

### Retries

Retry เฉพาะกรณีที่ลองอีกครั้งแล้วมีโอกาสดีขึ้น

กรณีที่เหมาะ:

- network ขาดช่วงสั้น ๆ
- dependency error ชั่วคราว
- rate limit ที่บอก retry time มาให้

กรณีที่ไม่ควร retry:

- input ไม่ถูกต้อง
- authorization fail
- business rule ปฏิเสธแบบถาวร
- operation ที่ทำซ้ำไม่ปลอดภัย

ใช้ exponential backoff และ jitter ครับ backoff เพิ่มเวลารอหลัง fail แต่ละครั้ง ส่วน jitter เติมความต่างเล็กน้อยเพื่อไม่ให้ client หลายพันตัว retry พร้อมกัน

### Retry storms and cascading failure

Retry สามารถคูณ load ตอน service กำลังป่วยได้

<MermaidDiagram chart={`
flowchart TD
    C["Many clients"] --> S["Slow service"]
    S --> E["Timeouts"]
    E --> R["Immediate retries"]
    R --> M["More load"]
    M --> S

    E --> B["Bounded retry\nwith backoff and jitter"]
    B --> L["Load stays controlled"]
`} />

Google SRE อธิบายว่า overload เป็นสาเหตุสำคัญของ [cascading failure](https://sre.google/sre-book/addressing-cascading-failures/) เมื่อ replica หนึ่งตัวล้ม load จะย้ายไปตัวที่เหลือ ทำให้ช้าลง client เริ่ม retry แล้ว failure ก็ขยายวง

Control ที่ช่วยป้องกันมี:

- retry limit
- retry เพียง layer เดียว แทนการ retry ทุก layer
- circuit breaker
- queue limit
- load shedding
- per-customer quota
- graceful degradation

[Handling overload](https://sre.google/sre-book/handling-overload/) ของ Google เตือนด้วยว่า request แต่ละแบบมี cost ไม่เท่ากัน requests per second จึงอาจซ่อน pressure ที่ระบบเจอ CPU, memory, concurrency หรือ resource อื่นอาจเป็น capacity signal ที่ดีกว่า

### Backpressure

Backpressure เปิดทางให้ consumer ควบคุมว่ารับงานได้มากแค่ไหน

![Backpressure controls a large incoming flow before workers are overloaded](/assets/images/blogs/practical-system-design/backpressure-valve.png)

ใน onboarding system worker ไม่ควรดึง chunk ไม่จำกัดเมื่อ identity, payroll หรือ equipment integration ช้า Queue ช่วย buffer burst ได้ แต่ต้องมี limit และแผนรับมือเชิง operation

Control ที่ใช้ได้มี worker concurrency, batch size, queue prefetch, integration rate limit, delay ระหว่าง batch และ maximum queue age

ถ้า queue age โตต่อเนื่อง การเติม task เข้าไปอีกไม่ใช่ recovery ทีมอาจต้อง pause onboarding run, ลด concurrency หรือย้าย blocked work ไป manual review

## Partitioning and Hotspots

ระบบใหญ่แบ่ง data และงานไปหลายเครื่อง โดย partition key เป็นตัวตัดสินว่า item แต่ละชิ้นจะไปไหน

![A partition rule spreads onboarding work into balanced groups](/assets/images/blogs/practical-system-design/partition-hotspots.png)

Key ที่พบบ่อย ได้แก่ user ID, account ID, onboarding run ID, tenant ID, time bucket และ geographic region

Key ที่ดีต้องกระจาย load และรองรับ main query ส่วน key ที่เลือกไม่ดีจะสร้าง hotspot

สมมุติ tenant หนึ่ง import พนักงานตามฤดูกาล 1 ล้านคน ขณะที่ tenant ส่วนใหญ่มีเพียง 1,000 คน ถ้า partition ด้วย `tenant_id` อย่างเดียว import ก้อนใหญ่จะลง partition เดียว การเพิ่ม onboarding run, chunk หรือ hash suffix ช่วยกระจายงานได้

แต่ partition มากขึ้นก็เพิ่ม cross-partition query, rebalancing, transaction ที่ซับซ้อนขึ้น, operational tool ที่ทำยากขึ้น และ migration ที่ลำบากขึ้น

Partition เมื่อ access pattern ปัจจุบันต้องใช้ครับ อย่าทำเพราะวันหนึ่งระบบอาจใหญ่

## Multi-Region Is a Business Decision

Multi-region architecture ช่วย availability และ latency ได้ แต่เปลี่ยน data, operations และ cost พร้อมกัน

![A system choice should be reviewed through several business and operational constraints](/assets/images/blogs/practical-system-design/decision-lens.png)

<MermaidDiagram chart={`
flowchart LR
    U1["Users in region A"] --> G["Global routing"]
    U2["Users in region B"] --> G
    G --> A["Application region A"]
    G --> B["Application region B"]
    A <--> D["Replicated data"]
    B <--> D
`} />

ก่อนเลือกระหว่าง active-active กับ active-passive ให้ถาม:

- ระบบต้องรอดจาก outage แบบไหน?
- ธุรกิจรับ recovery time ได้เท่าไร?
- ยอมเสีย data ได้มากแค่ไหน?
- สอง region แก้ record เดียวกันได้หรือเปล่า?
- network partition แล้วจะทำอย่างไร?
- ทีมทดสอบ regional recovery ได้บ่อยแค่ไหน?

Scheduled onboarding checklist ช้าสั้น ๆ อาจรับได้ แต่ payment authorization หรือ urgent access removal อาจต้องการอีกคำตอบหนึ่ง

รันสอง region โดยไม่เคยทดสอบ failover อาจได้ cost ของ multi-region มาเต็ม ๆ โดยยังไม่ได้ safety ครับ

## APIs and Contracts Are Part of the Design

API คือสัญญาที่เรามอบให้ caller จึงควรกำหนด resource name และ ID, request/response shape, error model, idempotency, pagination, rate limit, versioning, authentication และ authorization ให้ครบ

ถ้าเป็น asynchronous work ให้คืน job หรือ onboarding run ID เพื่อให้ caller เช็ก status หรือรับ webhook

```http
POST /onboarding-runs
Idempotency-Key: 2d3817...

202 Accepted
{
  "onboardingRunId": "onb_123",
  "status": "scheduled"
}
```

อย่าเปิด internal database model ผ่าน API เพราะ table ภายในจะเปลี่ยน Stable contract ช่วยให้ทีมแก้ implementation ภายหลังได้

Event ก็เป็น contract เช่นกัน ต้องมี schema version, owner และ compatibility rule การลบหรือเปลี่ยน field อาจทำ consumer ที่เราไม่รู้จักพังได้

## Security Starts with Boundaries

Security ไม่ใช่กล่องหนึ่งใบที่ขอบ diagram ลองถาม:

- ใครเรียก API นี้ได้?
- คนนี้ดูหรือแก้ onboarding case ไหนได้บ้าง?
- service ไหนอ่าน employee data ได้?
- data ใดต้อง encrypt?
- action ไหนต้องสร้าง audit event?
- worker แต่ละตัวเข้าถึง secret อะไรได้?
- tenant data แยกกันอย่างไร?

Control ที่ควรพิจารณามี authentication, role/attribute-based authorization, least-privilege service identity, encryption in transit และ at rest, secret rotation, network boundary, immutable audit log รวมถึง data retention และ deletion policy

ตรวจ authorization ที่ resource boundary ครับ user ที่แก้ case หนึ่งได้ ไม่ควรเข้าถึง case ของทุก tenant เพียงเปลี่ยน ID ใน URL

สำหรับ sensitive flow การแยก account, cloud profile, database หรือ worker อาจคุ้มกับ cost ที่เพิ่ม เพราะช่วยลด failure และ access surface

## Observability Must Answer Operational Questions

Log, metric และ trace เป็นเครื่องมือ เริ่มจากคำถามที่ทีมต้องตอบก่อน:

- scheduled onboarding run เริ่มหรือยัง?
- มี chunk รออยู่กี่ก้อน?
- chunk เก่าสุดรอนานเท่าไร?
- integration ไหนช้า?
- task สำเร็จ fail หรือ skip กี่รายการ?
- tenant เดียวใช้ capacity ส่วนใหญ่หรือเปล่า?
- หยุด onboarding run เดียวอย่างปลอดภัยได้ไหม?
- replay failed chunk ได้หรือเปล่า?

Metric ที่มีประโยชน์ ได้แก่ request rate/error/latency, queue depth และ age, worker throughput, retry count, integration response code, database connection usage, cache hit rate รวมถึง onboarding progress และ final result

ใช้ correlation ID เช่น onboarding run ID, employee ID, chunk ID และ integration request ID เพื่อให้ทีมตามหนึ่ง flow ข้ามหลาย service ได้

Alert ควรพาไปสู่ action queue depth สูงอาจปกติในช่วง bulk import ที่วางแผนไว้ แต่ queue age ที่เสี่ยงทำให้พนักงานเริ่มงานไม่ทันให้ข้อมูลกับทีมมากกว่า

## Ownership Changes the Design

Technology สองตัวอาจแก้ technical problem เดียวกันได้ แต่ทีมยังเลือกไม่เหมือนกัน เพราะความสามารถในการ operate ต่างกัน

![Owning a decision means explaining why, trade-offs, failure, and ownership](/assets/images/blogs/practical-system-design/own-the-decision.png)

ลองเช็กมุมเหล่านี้:

- **Skills:** ทีม debug และ upgrade เป็นไหม?
- **Operations:** ใคร on-call ให้ระบบนี้?
- **Cost:** traffic โตสิบเท่าแล้วค่าใช้จ่ายเป็นอย่างไร?
- **Security:** เพิ่ม data หรือ access boundary ใหม่ไหม?
- **Delivery:** setup และ migration ใช้เวลานานแค่ไหน?
- **Reversal:** ถ้าจะเปลี่ยนออกยากเพียงใด?
- **Organization:** boundary ของระบบเข้ากับ team ownership หรือเปล่า?

เรื่อง storage ของ Discord ไม่ได้มีเฉพาะ benchmark speed ยังมี unpredictable latency และ operational toil ส่วน TAO ของ Meta ก็ไม่ได้หยุดที่การเพิ่ม cache แต่สร้าง abstraction เพื่อให้ product team ไม่ต้องรับรายละเอียดทุกชั้น

เพราะแบบนี้ architecture ที่เล็กกว่าจึงอาจเป็นตัวเลือกที่ mature กว่า Design จะมีประโยชน์ได้เมื่อทีมดูแลให้มันมีประโยชน์ต่อไปไหวครับ

## Migration Is Part of System Design

ระบบส่วนใหญ่ไม่ได้เริ่มบนพื้นที่ว่าง เราต้องพา design ใหม่ออกมาจากของเดิมด้วย

Safe migration อาจใช้ขั้นตอนเหล่านี้:

1. **Shadow reads:** อ่านจากระบบใหม่ แต่ยังไม่ใช้คำตอบ
2. **Dual writes:** เขียนลง old และ new store ในช่วงจำกัด
3. **Backfill:** copy data เก่าพร้อม checksum และ progress tracking
4. **Small rollout:** ย้าย tenant, region หรือ traffic percentage เล็ก ๆ ก่อน
5. **Compare:** เทียบ data, latency, error และ business result
6. **Cut over:** ย้าย new path ขึ้นเป็น primary
7. **Keep rollback:** เก็บทางกลับไว้จนมั่นใจพอ

Dual write อาจ fail เพียงฝั่งเดียว วางแผน reconciliation ก่อนเปิดใช้ครับ

Migration tool เองก็ต้องมี idempotency, monitoring, pause, resume และ audit support เพราะ temporary system มักอยู่นานกว่าที่คิด

## A Coaching Method for System Design

เวลา coach ผมจะไม่เริ่มด้วยการขอ complete architecture ครับ ผมจะช่วยย่อปัญหาให้เล็กพอที่จะคุยกันก่อน แล้วค่อยให้คุณเพิ่ม constraint ทีละข้อ

Coaching loop ทำได้แบบนี้:

1. ให้ engineer อธิบาย user และเป้าหมาย
2. หา requirement ที่ทำให้ design เปลี่ยน
3. วาดเวอร์ชันเล็กที่สุดที่ทำงานได้
4. เพิ่ม constraint หนึ่งข้อ
5. ถามว่าอะไรจะพังก่อน
6. เทียบสองหรือสาม option
7. หาเหตุผลหลักที่ใช้ตัดสิน
8. ระบุ trade-off และ owner
9. เติม failure และ recovery path
10. ทบทวนว่าเงื่อนไขไหนจะทำให้ทีมกลับมาเปลี่ยนคำตอบ

คำถามที่ใช้คุยต่อได้ เช่น:

- source of truth อยู่ไหน?
- อะไรอยู่บน hot path?
- งานไหนย้ายไป asynchronous ได้?
- อะไรรันซ้ำได้บ้าง?
- data หายที่ไหนได้?
- key ไหนอาจ hot?
- ถ้า dependency ช้าแต่ยังไม่ล้มจะเกิดอะไรขึ้น?
- ทีมรู้ได้อย่างไรว่าระบบกำลังป่วย?
- ส่วนไหนเปลี่ยนยากที่สุด?
- ถ้ามีทีมสามคน คุณยังเลือกแบบเดิมไหม?

Mentor ไม่จำเป็นต้องซ่อนคำตอบ เป้าหมายคือช่วยให้ engineer เชื่อมทุกคำตอบเข้ากับเหตุผลของมัน

## Final Thoughts

System Design มีทั้ง database, cache, queue, load balancer, API, partition, region และเครื่องมืออีกเยอะ การเรียนว่าแต่ละตัวทำอะไรยังสำคัญครับ

แต่เป้าหมายสุดท้ายไม่ใช่การจำชื่อ component ให้ครบ

ทักษะที่ควรฝึกคือการอธิบายให้ได้ว่า:

- ปัญหาคืออะไร
- design เล็กที่สุดที่ทำงานได้เป็นแบบไหน
- constraint ข้อไหนบังคับให้ design เปลี่ยน
- option นี้เข้ากับ data, traffic และทีมอย่างไร
- อะไรพังได้
- เรายอมรับ trade-off อะไร
- ใครเป็น owner
- เมื่อไหร่ควรกลับมาทบทวน

นี่คือเส้นทางจากการวาดกล่อง ไปสู่การรับผิดชอบการตัดสินใจครับ
