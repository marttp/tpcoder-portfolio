I’m happy that models are getting better and agents can do more with them. I can hand an agent a task that spans a few files and come back to a diff with tests. On a good day, I spend less time setting things up and more time thinking about what the product should do. I like working this way.

The moment I think about is when something feels off. The agent can explain the code, write a test for it, and tell me everything passes. If I still feel unsure, do I know where to look, or will I just ask the same agent whether it’s sure?

## What happens to the first payment when the customer moves?

I worked on a payment flow that tied billing details to the user account. Say the first transaction used billing address A. If the customer moves and uses address B for the next payment, what should the first transaction show?

If the customer enters their billing address for each payment and we only use it for that payment, there’s no saved address to update for next time. Once we let the customer save an address for future payments, we have two things to keep track of. There’s the address to suggest next time, and there’s the address each transaction used.

![An engineer studies a flow that splits into two paths](/assets/images/blogs/when-your-ai-agent-gets-confused/trace.webp)

The Agent proposed adding a PATCH operation that followed the existing design. It would update the billing details on the account. That makes sense if you start from how the code stores the data today. From the customer’s side, they’ve moved and want to use B on their next payment. When an older transaction reads its billing details from that same account record, it now sees B too. The PATCH worked. It changed every transaction that used that reference.

## The part I had to decide

We changed the flow so each transaction could carry its own billing details. The check I care about is simple. Take one account, make a payment with A, then make another with B. Look at both transactions again. The first should still show A and the second should show B. A test that only checks whether the account now has B can pass while missing the effect on the first payment.

This is the kind of thing I want to catch when reviewing an Agent’s proposal. It could see where the current code reads and writes the address. I had to think about what the customer meant by changing it, and what that change should do to a payment they’d already made.

![An engineer makes the final call at his desk](/assets/images/blogs/when-your-ai-agent-gets-confused/decision.webp)

What if the Agent starts returning HTTP 500s or the provider goes down? Do I stop working? I still ship the work. I open the code, trace the problem, and write the test myself, like I used to. It’s just a little less convenient.

**Once I choose to ship what the Agent produced, it’s my work.** If someone asks why an old payment shows a new address, I need to be able to trace it myself and explain what happened.
