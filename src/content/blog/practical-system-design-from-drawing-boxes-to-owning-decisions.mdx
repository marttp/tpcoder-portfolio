## Why This Guide Exists

When people learn System Design, they often see a large diagram first. It has load balancers, caches, queues, databases, workers, regions, and many arrows.

The diagram may look impressive. But it does not explain the most important part: **why did the system need each box?**

Adding a component is easy to explain. The harder part is explaining why the component belongs there, what can fail, and who must care for it later.

This guide does not cover the interview process or provide a list of answers to remember. It is a practical way to coach someone through System Design knowledge.

The main idea is simple:

**System Design is the work of turning a problem into a system that people can build, run, change, and own.**

We will start with one small system. Then we will add real constraints one at a time. Along the way, we will cover the main building blocks, data decisions, failure handling, security, operations, and engineering judgment.

This guide cannot cover every type of system. No guide can. Its goal is to help you ask better questions when the next system looks different.

## Start with the Problem, Not the Components

Let us use one running example: an E-commerce marketplace.

A customer browses products, adds items to a cart, and places an order. The system checks inventory, accepts payment, sends the order to fulfillment, and tracks each step until delivery. Sellers also manage products, prices, and available stock.

Before drawing anything, ask what the system must do.

### Functional requirements

These describe user-visible behavior:

- browse and search for products;
- add, update, and remove cart items;
- place an order and pay for it;
- reserve inventory without overselling;
- send paid orders to fulfillment;
- show order and delivery progress.

### Non-functional requirements

These describe how well the system must work:

- **Correctness:** do not create duplicate orders, charge twice, or sell stock that is gone.
- **Availability:** customers should still browse and place orders if one server fails.
- **Durability:** an accepted order should not disappear.
- **Scale:** product reads may be far higher than order writes, and traffic can change quickly.
- **Security:** customers, sellers, and services should access only the data and actions they need.
- **Auditability:** the team must know who changed what and when.

Do not write every possible requirement. Find the ones that change the design.

For example, a product view counter may be a minute behind. Inventory and payment status need a stronger rule during checkout. Both belong to the same product, but their quality goals are different.

Ask these questions before choosing technology:

1. Who uses the system?
2. What must never happen?
3. What can happen later?
4. What data can we lose?
5. What happens if a dependency is unavailable?
6. Which action has a real business or customer cost?

These questions give the diagram a reason to exist.

## Core Quality Goals Pull the Design in Different Directions

A system cannot maximize every quality at the same time. The requirements must say which goals matter most.

- **Scalability** is the ability to handle more users, data, or work.
- **Performance** describes speed and resource use. Latency and throughput are common measures.
- **Availability** describes how often the service can accept useful work.
- **Reliability** describes whether the service keeps producing the correct result over time.
- **Consistency** describes when different readers see the same data state.
- **Security** controls who can access data and actions.

Availability and reliability are related, but they are not equal. A service can respond while returning stale or wrong data. That service is available, but it is not reliable.

Turn broad goals into measurable targets:

- p95 and p99 latency;
- requests or jobs per second;
- maximum queue age;
- accepted error rate;
- recovery time objective, or RTO;
- recovery point objective, or RPO;
- data freshness;
- monthly availability target.

For example, 99.9% monthly availability allows about 43 minutes of downtime. A higher target needs more redundancy, testing, automation, and cost. Choose the target from business impact, not from habit.

## Estimate Only What Can Change the Design

Estimation is useful when it changes a decision. It is not a contest to produce a perfect number.

Suppose the marketplace has 10 million daily customers. Each customer opens an average of 20 product pages, and 2% of customers place an order.

We can ask:

- How many product reads must the system serve?
- How many orders will it create each day?
- Can inventory, payment, and fulfillment services accept the peak request rate?
- How much order and event history must we store?
- How far can peak traffic rise above the daily average?

This produces about 200 million product views and 200,000 orders per day. Product traffic is read-heavy, while each order creates several writes and calls to other services.

```text
10,000,000 customers x 20 product views = 200,000,000 product views/day
10,000,000 customers x 2% conversion = 200,000 orders/day
```

These numbers show two different workloads. Product browsing may need caching, a CDN, and read scaling. Order processing needs durable writes, idempotency, queues, and recovery tools.

Not every number needs the same attention:

- **Request rate matters** when it may overload a service or dependency.
- **Record size matters** when storage or network cost is large.
- **Read-to-write ratio matters** when caching may help.
- **Peak traffic matters** when averages hide bursts.
- **Recovery time matters** when a long outage has business impact.

If a number does not change the design, keep moving.

For a small team and low volume, this may be enough. It is easy to understand, deploy, and debug.

Do not call it naive as an insult. A small design is often the right design for a small problem.

Before adding anything, make this version safe:

- store money in the smallest currency unit, not a floating-point number;
- use a durable database, not process memory, for accepted orders;
- record payment and fulfillment attempts;
- make checkout and integration calls idempotent;
- protect customer and seller actions with authentication and authorization.

### Protect and Observe Version One

Security and observability do not wait for scale. A small system still handles customer data, money, and calls to other services.

Start with a small security boundary:

- authenticate every customer and seller action;
- check authorization on the order or product being changed;
- keep secrets outside the code and logs;
- record sensitive actions in an audit trail.

### Scale up or scale out

There are two basic ways to add capacity:

- **Vertical scaling:** give one machine more CPU, memory, disk, or network capacity.
- **Horizontal scaling:** add more machines and spread the work between them.

Vertical scaling is often simpler. It has a hardware limit and can leave one large failure point. Horizontal scaling can grow further and isolate failures, but it needs load distribution, partitioning, coordination, and operational tools.

![Vertical scaling grows one machine while horizontal scaling distributes work across machines](/assets/images/blogs/practical-system-design/scale-up-vs-scale-out.png)

Many systems use both. A database may first move to a larger machine. Application servers may scale out because they are easier to keep stateless.

### CDN and edge delivery

A content delivery network, or CDN, stores cacheable content close to users. It is useful for images, video, JavaScript, downloads, and public API responses that can be cached safely.

A CDN can reduce origin traffic and user latency. It also adds decisions:

- cache key;
- cache duration;
- invalidation;
- private versus public content;
- regional rules;
- behavior when the origin is unavailable.

Do not cache private content with a key that ignores the user or tenant.

### Load balancer: when one application is not enough

A load balancer sends traffic across several application instances.

{/* IMAGE PROMPT (load-balancer-health-routing.png): Wide modern green 2D cartoon infographic on a warm-white and pale-mint background. Show customer traffic entering one load balancer, routing to a group of two healthy servers, and skipping one separate unhealthy server. Render each exact label once: TRAFFIC, LOAD BALANCER, HEALTHY, UNHEALTHY. Spell exactly. No other text, duplicate labels, arrow to the unhealthy server, dark background, photorealism, glossy 3D, logos, or watermarks. */}

![A load balancer routes traffic to healthy instances and removes an unhealthy instance](/assets/images/blogs/practical-system-design/load-balancer-health-routing.png)

It helps when:

- one instance cannot handle the traffic;
- you need to deploy without stopping all traffic;
- one unhealthy instance must be removed;
- requests should go to a nearby region or zone.

It also creates new questions:

- Is the application stateless?
- Where does session state live?
- How does the load balancer know an instance is healthy?
- What happens when all instances are overloaded?

A health check should test useful readiness, not only whether the process is alive. A server can answer HTTP while its database pool is exhausted.

### API gateway and rate limiting

An API gateway can provide one entry point for authentication, routing, request limits, protocol changes, and shared logging. It is useful when many clients call many services. It can also become a large shared failure point, so keep its work bounded and run it with redundancy.

{/* IMAGE PROMPT (api-gateway-entry-point.png): Wide modern green 2D cartoon infographic on a warm-white and pale-mint background. Render each exact label once: CLIENTS, API GATEWAY, AUTH, LIMIT, ROUTE, SERVICES. Spell exactly. No other text, duplicate labels, dark background, photorealism, glossy 3D, logos, or watermarks. */}

![An API gateway applies shared controls before routing clients to backend services](/assets/images/blogs/practical-system-design/api-gateway-entry-point.png)

Rate limiting protects capacity and fair use. Common policies include:

- a fixed or sliding time window;
- a token bucket that allows a controlled burst;
- a leaky bucket that smooths traffic;
- concurrency limits for expensive work;
- quotas per user, tenant, API key, or region.

Return a clear error and retry time when possible. A limit without client guidance often creates aggressive retries.

### Database: choose from the access pattern

The database choice starts with how the system reads and writes data.

{/* IMAGE PROMPT (choose-for-access-pattern.png): Wide modern green 2D cartoon infographic on a light background. Show query and access-pattern icons leading to tabular, document, key-value, graph, time-series, and file-shaped data, then to matching storage families. Render only these labels once: QUERY, DATA SHAPE, STORAGE. */}

![Different access patterns lead to different data designs](/assets/images/blogs/practical-system-design/choose-for-access-pattern.png)

For the E-commerce system, the main records may include:

- product;
- inventory;
- cart;
- order and order item;
- payment attempt;
- fulfillment;
- audit event.

A relational database is a good first choice when the system needs transactions, clear relationships, and flexible operational queries.

A key-value or wide-column store can help when access is simple and volume is very large. But the data model must match the query. A distributed database does not remove data modeling. It makes the access pattern even more important.

Different storage families solve different shapes of work:

- **Relational:** transactions, relationships, constraints, and flexible queries.
- **Key-value:** fast lookup through a known key.
- **Document:** records with flexible nested fields.
- **Wide-column:** very large data grouped around known partition keys.
- **Time-series:** timestamped metrics and events with retention rules.
- **Graph:** deep relationship traversal.
- **Object storage:** large files and immutable data at low cost.
- **Search index:** text search, ranking, filtering, and aggregation.
- **Vector index:** similarity search over embeddings.

#### How each storage type is queried

The syntax changes, but the larger lesson is the same: design the data around the reads and writes the product needs. These examples use one E-commerce system. They are small on purpose.

**Relational — PostgreSQL**

Use SQL when you need conditions, relationships, constraints, and transactions. This query returns the newest active products in one category.

```sql
SELECT id, name, price
FROM product
WHERE category_id = 42
  AND status = 'ACTIVE'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

The table may need an index on `(category_id, status, created_at DESC, id DESC)`. PostgreSQL also needs a stable `ORDER BY` when `LIMIT` returns one page of a larger result. See the [PostgreSQL LIMIT documentation](https://www.postgresql.org/docs/current/queries-limit.html).

**Key-value — Redis**

A key-value query starts from the exact key. This command loads the fields stored for one SKU.

```text
HGETALL product:sku:SKU-123
```

This is simple and fast for a known key. It cannot find every active product in a category unless the application maintains another structure for that access pattern. See the [Redis HGETALL documentation](https://redis.io/docs/latest/commands/hgetall/).

**Document — MongoDB**

A document query can filter and return nested product data together.

```javascript
db.products.find(
  { categoryId: 42, status: "ACTIVE" },
  { name: 1, price: 1, attributes: 1 }
).sort({ createdAt: -1, _id: -1 }).limit(20)
```

The document can keep flexible attributes close to the product. The query still needs an index that supports its filter and sort. See the MongoDB documentation for [`find()`](https://www.mongodb.com/docs/manual/reference/method/db.collection.find/) and [`sort()`](https://www.mongodb.com/docs/manual/reference/method/cursor.sort/).

**Wide-column — Cassandra**

Cassandra tables are often built for a known query. Suppose `products_by_category` uses `category_id` as its partition key and starts its clustering columns with `status`.

```sql
SELECT product_id, name, price
FROM products_by_category
WHERE category_id = 42
  AND status = 'ACTIVE'
LIMIT 20;
```

This query reads one known partition. A different access pattern, such as products by seller, often needs another table. CQL does not provide normal joins or free queries across tables. See the [Cassandra CQL SELECT documentation](https://cassandra.apache.org/doc/latest/cassandra/developing/cql/dml.html).

**Time-series — Prometheus**

PromQL works with metrics over time. This query calculates the failed checkout rate per second over the last 5 minutes.

```text
sum(rate(checkout_requests_total{status="failed"}[5m]))
```

`rate()` is for counters. The labels must stay bounded; using `customer_id` or `order_id` as a label can create too many time series. See the Prometheus documentation for [PromQL basics](https://prometheus.io/docs/prometheus/latest/querying/basics/) and [`rate()`](https://prometheus.io/docs/prometheus/latest/querying/functions/#rate).

**Graph — Neo4j**

In simple words, this query asks: Which products did similar customers buy that this customer has not bought yet?

```cypher
MATCH (customer:Customer {id: $customerId})-[:BOUGHT]->(shared:Product)
      <-[:BOUGHT]-(other:Customer)-[:BOUGHT]->(candidate:Product)
WHERE NOT EXISTS {
  MATCH (customer)-[:BOUGHT]->(candidate)
}
RETURN candidate.id, candidate.name, count(*) AS score
ORDER BY score DESC
LIMIT 10;
```

A graph database follows the relationships from one customer to shared products, other customers, and candidate products. It helps when this traversal is the main work. A product lookup by ID does not need this model. See the [Neo4j Cypher MATCH documentation](https://neo4j.com/docs/cypher-manual/current/clauses/match/).

**Object storage — files by key**

Object storage is not queried like a row database. The application puts each file under an object key and keeps small searchable metadata in a database.

Show four file cards flowing into one central storage bucket: a product photo, catalog spreadsheet, invoice PDF, and export archive. Show the product photo flowing to a CDN, the other files flowing to a worker, and small metadata flowing to a separate database. Render each exact label once and spell exactly: PRODUCT IMAGE, CATALOG FILE, INVOICE, EXPORT, OBJECT STORAGE, METADATA DB, CDN, WORKER. No other text, duplicate labels or boxes, dark background, blue-led palette, photorealism, glossy 3D, company logos, or watermarks. */}

![Product images, catalog files, invoices, and exports use object storage while a database keeps their metadata](/assets/images/blogs/practical-system-design/object-storage-file-flow.png)

The files can serve different jobs:

- a CDN reads product images and sends them to customers;
- a worker reads catalog files and imports product data;
- invoices stay available for download and audit;
- exports hold large batch results.

To read one file, the application gets it by bucket and object key. To find files by seller, date, or status, query the metadata database first, then fetch the matching objects. The database supports search. Object storage holds the large file content.

**Search index — OpenSearch**

OpenSearch can combine analyzed text, relevance, and exact filters.

```json
GET /products/_search
{
  "size": 20,
  "query": {
    "bool": {
      "must": {
        "multi_match": {
          "query": "wireless keyboard",
          "fields": ["name^3", "description"]
        }
      },
      "filter": [
        { "term": { "status": "ACTIVE" } },
        { "term": { "category_id": 42 } }
      ]
    }
  }
}
```

The index may return stale product data, so checkout must read the current price and inventory from their sources of truth. See the [OpenSearch multi-match documentation](https://docs.opensearch.org/latest/query-dsl/full-text/multi-match/).

**Vector index — pgvector**

A vector query sorts by distance instead of an exact value. `$1` is the embedding for the customer's search text or selected product.

```sql
SELECT id,
       name,
       1 - (embedding <=> $1) AS similarity
FROM product_embeddings
WHERE status = 'ACTIVE'
ORDER BY embedding <=> $1
LIMIT 10;
```

The `<=>` operator calculates cosine distance. The nearest result has a close vector score, but it may still be a poor product match. Keep business filters and measure result quality. See the [pgvector query documentation](https://github.com/pgvector/pgvector#querying).

One product may use several stores. Keep one source of truth for each fact, and state how derived stores are updated and repaired.

Discord described this lesson in its article about [storing trillions of messages](https://discord.com/blog/how-discord-stores-trillions-of-messages). The company had 177 Cassandra nodes in early 2022. Hot partitions, read cost, compaction, and operational toil became serious problems. Discord changed the database and also added a data service that reduced direct database access from product services.

The lesson is not that Cassandra is bad or ScyllaDB is always better. The lesson is that data shape, access pattern, hotspots, and team operations belong in the same decision.

### Cache: save work that repeats

A cache keeps data in a faster place for a limited time.

{/* IMAGE PROMPT (cache-hit-miss.png): Wide modern green 2D cartoon infographic on a warm-white and pale-mint background. Show one product request checking one cache. A cache hit returns immediately. A cache miss reads one database, then fills the same cache. Render each exact label once: REQUEST, CACHE, HIT, MISS, DATABASE, FILL. Spell exactly. No other text, duplicate labels or boxes, dark background, photorealism, glossy 3D, logos, or watermarks. */}

![A cache hit returns data quickly while a cache miss reads the database and fills the cache](/assets/images/blogs/practical-system-design/cache-hit-miss.png)

It can help with:

- product and category pages read many times;
- seller and shipping policies used by many requests;
- inventory summaries with a clear freshness limit;
- expensive read queries with acceptable staleness.

It does not help every read. Ask:

- Is the data read often enough?
- How stale may it be?
- What happens on a cache miss?
- How is the cache invalidated?
- Can a popular key become a hotspot?
- What happens when the whole cache is cold?

#### Cache eviction and expiration

A cache has limited memory. When it is full, an **eviction policy** decides which item leaves. This is different from expiration. A TTL controls how long an item may stay before it becomes too old.

{/* IMAGE PROMPT (cache-eviction-policies.png): Wide modern green 2D cartoon infographic on a warm-white and pale-mint background. Use four equal panels to compare cache removal choices. TTL shows an item expiring beside a clock. LRU removes the item that has not been used for the longest time. LFU removes the item with the lowest access count. FIFO removes the oldest inserted item. Render each exact label once: TTL, LRU, LFU, FIFO, EVICT. Spell exactly. No other text, duplicate labels or panels, dark background, blue-led palette, photorealism, glossy 3D, logos, or watermarks. */}

![TTL controls age while LRU, LFU, and FIFO choose which cached item leaves](/assets/images/blogs/practical-system-design/cache-eviction-policies.png)

The common choices solve different problems:

- **TTL** removes data after a time limit. Use it when freshness has a clear limit.
- **LRU** removes the least recently used item. It works well when recent items are likely to be read again.
- **LFU** removes the least frequently used item. It can protect items that stay popular for a long time, but it may adapt slowly when traffic changes.
- **FIFO** removes the oldest inserted item. It is simple, but it does not know which item is useful.

Many caches use TTL together with a capacity policy such as LRU or LFU. Also plan for a large number of keys expiring together. TTL jitter, request coalescing, and stale-while-revalidate can reduce that sudden load.

Measure hit rate, miss latency, evictions, and source load. A policy name is only a starting point. Redis, for example, uses approximate LRU and LFU algorithms to reduce memory cost. Its [key eviction documentation](https://redis.io/docs/latest/develop/reference/eviction/) explains the available policies and their trade-offs.

Meta built TAO because its social graph had a large, read-heavy workload that did not fit a simple database cache well. The [TAO engineering article](https://engineering.fb.com/2013/06/25/core-infra/tao-the-power-of-the-graph/) explains how Meta created a graph-focused data abstraction over MySQL and distributed caching. The abstraction also reduced the amount of cache and database knowledge each product engineer needed.

That last part matters. A platform can improve scale and make the safer path easier for other teams.

### Queue and workers: move slow work off the request path

Completing payment, inventory, fulfillment, email, and analytics inside one HTTP request will not work well. A slow dependency can time out the whole request, and one failure may repeat work that already succeeded.

A queue separates accepting work from doing work.

<MermaidDiagram chart={`
flowchart LR
    A["Order API"] --> D["Order DB"]
    D --> P["Event publisher"]
    P --> Q["Order queue"]
    Q --> W1["Worker 1"]
    Q --> W2["Worker 2"]
    Q --> W3["Worker N"]
    W1 --> F["Fulfillment services"]
    W2 --> F
    W3 --> F
    W1 --> R["Task results"]
    W2 --> R
    W3 --> R
`} />

This design helps with:

- burst absorption;
- worker scaling;
- retrying a small unit of work;
- pausing fulfillment without losing accepted orders;
- tracking progress for each order.

But the queue adds ownership:

- the same task may run more than once;
- queue items may arrive out of order;
- poison tasks may fail every time;
- old work may sit behind new work;
- the queue may grow faster than workers can drain it.

The queue does not create reliability by itself. The producer, consumer, data model, and recovery process must agree on the processing rules.

#### Queue, pub-sub, or stream?

These words are often mixed because one product may support more than one model. Start with the delivery rule you need.

{/* IMAGE PROMPT (queue-pubsub-stream.png): Wide modern green 2D cartoon infographic on a warm-white and pale-mint background. Compare three equal columns. ![A queue distributes work, pub-sub fans an event out, and a stream keeps records for offset-based replay](/assets/images/blogs/practical-system-design/queue-pubsub-stream.png)

- **Queue:** one job is normally handled by one worker from a competing group. Use it to distribute work, such as packing an order.
- **Pub-sub:** each subscription receives its own copy of an event. Use it when inventory, shipping, and analytics must react independently to the same order event.
- **Stream:** records stay in an ordered log for a retention period. Consumers track an offset and may replay old records. Ordering is usually guaranteed inside one partition, not across the whole stream.

Durability depends on the product and subscription settings. Do not assume that every pub-sub system keeps an event when no subscriber is ready.

The product does not decide the model by itself. Kafka stores a stream, while a consumer group can distribute records in a queue-like way. RabbitMQ can support work queues, pub-sub, and streams. Define acknowledgment, retention, ordering, and replay before choosing the product. The [RabbitMQ tutorials](https://www.rabbitmq.com/tutorials) show the competing-consumer and pub-sub models, while the [Kafka distribution documentation](https://kafka.apache.org/43/implementation/distribution/) explains consumer offsets.

#### Dead-letter queues and replay

Some messages will keep failing after a safe number of retries. A dead-letter queue, or DLQ, isolates them so one poison message does not block normal work.

{/* IMAGE PROMPT (dead-letter-replay.png): Wide modern green 2D cartoon infographic on a warm-white and pale-mint background. Show exactly one left-to-right path: QUEUE to RETRY to DLQ to INSPECT to FIX to REPLAY to WORKER. RETRY is bounded. DLQ is isolated. REPLAY is a deliberate operator action. Render each exact label once: QUEUE, RETRY, DLQ, INSPECT, FIX, REPLAY, WORKER. Spell exactly. No other text, bypass path, automatic loop, duplicate labels or boxes, dark background, blue-led palette, photorealism, glossy 3D, logos, or watermarks. */}

![A failed message moves to a DLQ, is inspected and fixed, then returns through controlled replay](/assets/images/blogs/practical-system-design/dead-letter-replay.png)

A useful DLQ record should keep enough context to diagnose the failure:

- message payload or a safe reference to it;
- message key and source;
- schema or event version;
- error reason and attempt count;
- first and latest failure time;
- correlation or trace ID.

The DLQ is isolation, not resolution. Alert when messages enter it. Give a team clear ownership. Fix the cause, test the handler, and replay at a controlled rate through the normal idempotent path. Do not build an automatic infinite loop between the main queue and DLQ.

Retention, encryption, and access control still apply because failed messages may contain customer data. AWS documents the same inspect-and-redrive flow in its [SQS dead-letter queue guide](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html).

### Real-time connections and offline clients

Polling is simple, but it can waste requests when updates are rare. WebSockets or server-sent events let the server push updates over a long-lived connection.

Long-lived connections add different pressure:

- connection count;
- heartbeat and timeout handling;
- connection routing;
- reconnect storms;
- delivery order;
- slow clients;
- regional failover.

Typing indicators can be best-effort because a missed signal has low cost. A message or payment status needs durable storage and acknowledgment.

Offline clients need a synchronization rule. A common design stores a cursor or version per client. After reconnecting, the client asks for changes after that point instead of downloading everything again.

Plan for:

- duplicate updates;
- events that arrive out of order;
- deleted records;
- one user with several devices;
- a cursor that is too old;
- a full snapshot when delta sync cannot continue.

### Object storage: keep large immutable data outside the database

Suppose a seller uploads a large product catalog with images and specification files. Storing the full upload inside one database row is not useful.

An object store can hold the original catalog file, product images, invoices, or generated exports. The database stores the object key, checksum, size, version, and processing status.

This works well when:

- the data is large;
- workers read it in batches;
- the object is immutable after creation;
- a later audit may need the exact file version.

### Distributed files and chunk size

Very large files are often split into chunks and stored across machines or objects. Chunk size changes the system.

- Larger chunks create less metadata and fewer network calls.
- Smaller chunks allow more parallel work and reduce the retry size.
- Very large chunks can create hotspots and slow recovery.
- Very small chunks can overload the metadata service.

A distributed file service also needs:

- chunk placement;
- replication;
- checksums;
- garbage collection;
- re-replication after failure;
- metadata backup;
- repair and rebalancing tools.

Choose chunk size from file size, read pattern, write pattern, retry cost, and metadata capacity. There is no useful default for every workload.

The trade-off is that object storage is not a normal database. Updating one user in a large file is expensive. Point lookups may need a separate index or membership store.

### Search index: support queries the main database cannot serve well

A search engine can help when users need full-text search, filtering across many fields, relevance ranking, or fast aggregation.

Keep the source of truth clear. The search index is often a derived read model. Updates flow from the main database through an outbox or change stream.

If indexing is asynchronous, the UI may show stale product details. That can be acceptable in search results. The checkout path must read the current price and inventory from their sources of truth.

## Correctness: Idempotency, Ordering, and Consistency

Distributed systems often repeat work. Networks time out. Workers crash after completing an external call. Clients retry because they do not know what happened.

### Idempotency

An idempotent operation can run more than once without creating a different final result.

For checkout, the client may send an idempotency key. The server stores the key with the result of the first accepted request. A retry with the same key returns that result instead of creating another order or payment.

[Stripe uses idempotency keys](https://docs.stripe.com/api/idempotent_requests) for POST requests so clients can retry safely after a network error. A local system can use the same idea at API, queue, and integration boundaries.

Useful deduplication keys include:

- `checkout_id`;
- `order_id + operation_type`;
- a client-provided request key;
- a payment or fulfillment request key.

Idempotency needs durable state. An in-memory set disappears when the process restarts.

### Ordering

Not every event needs global order.

Ask what must be ordered:

- all orders in the marketplace;
- orders for one customer;
- state changes for one order;
- events for one inventory item.

Ordering a small key, such as one order or inventory item, is easier than ordering the whole system.

If order matters, partition messages by that key and protect state transitions in the database. Still plan for delayed and duplicate messages.

### Consistency

Consistency is not one switch between strong and eventual. Different data can need different rules.

- Order status may need a transaction.
- Product view counters may be eventually consistent.
- Product search results may be a few seconds stale.
- Inventory and price need a fresh check before checkout is confirmed.
- Financial settlement may need stronger guarantees than an analytics dashboard.

Google built [Spanner](https://research.google/pubs/spanner-googles-globally-distributed-database-2/) to support globally distributed data with externally consistent transactions. That is a valuable capability, but it comes from a complex system and specific trade-offs. Most systems should first ask which operations need that level of consistency.

### Replication, CAP, and PACELC

Replication copies data so another node can serve reads or recover after failure.

Common choices include:

- one leader accepts writes and followers copy them;
- several leaders accept writes in different regions;
- leaderless replicas accept reads and writes through quorum rules.

{/* IMAGE PROMPT (replication-patterns.png): Wide modern green 2D cartoon infographic on a warm-white and pale-mint background. Use arrows and small request or data symbols to make each flow self-explanatory. Render only these labels: LEADER, FOLLOWER, MULTI-LEADER, QUORUM. No title, sentences, dark background, blue-led palette, photorealism, glossy 3D, logos, or watermarks. */}

![Leader, multi-leader, and leaderless quorum replication patterns](/assets/images/blogs/practical-system-design/replication-patterns.png)

Synchronous replication can protect fresh data, but it adds write latency and may reduce availability during a network problem. Asynchronous replication is faster, but a recent write may be missing after failover.

The CAP theorem matters when the network splits. A distributed system must decide whether an operation should wait to protect consistency or continue with a risk of different data states. Partition tolerance is not an optional feature when machines communicate over a network.

{/* IMAGE PROMPT (cap-network-partition.png): Wide modern green 2D cartoon infographic on a warm-white and pale-mint background. Show database nodes separated by a broken network connection. ![During a network partition, a system balances consistency and availability](/assets/images/blogs/practical-system-design/cap-network-partition.png)

PACELC adds the normal case: even when there is no partition, a system often trades lower latency against stronger consistency.

{/* IMAGE PROMPT (pacelc-tradeoff.png): Wide modern green 2D cartoon infographic on a warm-white and pale-mint background. ![PACELC compares consistency and availability during a partition, then latency and consistency during normal operation](/assets/images/blogs/practical-system-design/pacelc-tradeoff.png)

Do not choose one rule for every record. An order update, an inventory check, a product view counter, and a search result may need different guarantees.

### Coordination and consensus

Some work needs nodes to agree on one value or one owner. Examples include choosing a leader, assigning a partition, storing cluster membership, or changing shared configuration.

Consensus systems can provide that agreement, but they add latency and operational cost. Keep the coordinated state small. Do not run every business event through a global lock when a database constraint, partition owner, or idempotency key can solve the smaller problem.

### Conflict detection and resolution

Multi-writer systems can accept two updates before either side sees the other.

Possible policies include:

- reject one update with optimistic concurrency control;
- choose the latest value using a trusted version or timestamp;
- merge independent fields;
- keep both versions for a person or application to resolve;
- use a convergent data type for counters, sets, or other supported shapes.

Last-write-wins is simple, but it can silently remove a valid update. A merge policy must match the business meaning. Adding two likes is different from changing an account owner.

## Failure Is a Normal Input

A production system receives failures as often as it receives business requirements.

{/* IMAGE PROMPT (failure-controls.png): Wide modern green 2D cartoon infographic on a light background. Show a stressed request path protected by a timeout, spaced retry, load-shedding gate, and healthy recovery path. Render only these labels once: TIMEOUT, RETRY, SHED, RECOVER. */}

![Reliability comes from several controls along the request path](/assets/images/blogs/practical-system-design/failure-controls.png)

Think about each dependency:

- slow response;
- timeout;
- connection failure;
- partial success;
- stale response;
- invalid response;
- complete outage.

### Timeouts

Every remote call needs a time budget. Without one, requests can wait until threads, connections, and memory are exhausted.

Use an end-to-end deadline when possible. If the whole request has two seconds, one dependency should not use all two seconds and leave no time for recovery.

### Retries

Retry only when another attempt may help.

Good retry candidates:

- a short network failure;
- a temporary dependency error;
- a rate limit with a clear retry time.

Poor retry candidates:

- invalid input;
- failed authorization;
- a permanent business rule rejection;
- an operation that is not safe to repeat.

Use exponential backoff and jitter. Backoff increases the wait after each failure. Jitter adds a small random difference so thousands of clients do not retry at the same moment.

### Retry storms and cascading failure

Retries can multiply load when a service is already unhealthy.

<MermaidDiagram chart={`
flowchart TD
    C["Many clients"] --> S["Slow service"]
    S --> E["Timeouts"]
    E --> R["Immediate retries"]
    R --> M["More load"]
    M --> S

    E --> B["Bounded retry\nwith backoff and jitter"]
    B --> L["Load stays controlled"]
`} />

Google SRE describes overload as a common cause of [cascading failures](https://sre.google/sre-book/addressing-cascading-failures/). One failed replica moves load to the remaining replicas. They become slower, clients retry, and the failure grows.

Protect the system with:

- a retry limit;
- one retry layer instead of retries at every layer;
- circuit breakers;
- queue limits;
- load shedding;
- per-customer quotas;
- graceful degradation.

Google's guide to [handling overload](https://sre.google/sre-book/handling-overload/) also warns that requests can have very different costs. Requests per second may hide the real pressure. CPU, memory, concurrency, or another resource can be a better capacity signal.

### Backpressure

Backpressure lets a consumer control how much work it can accept.

{/* IMAGE PROMPT (backpressure-valve.png): Wide modern green 2D cartoon infographic on a light background. Show a burst of events entering a bounded buffer, a visible capacity limit, a controllable valve, and a stable worker pool. Render only these labels once: INCOMING, BUFFER, LIMIT, WORKERS. */}

![Backpressure controls a large incoming flow before workers are overloaded](/assets/images/blogs/practical-system-design/backpressure-valve.png)

In the E-commerce system, workers should not pull unlimited orders when a warehouse or shipping integration is slow. The queue may buffer a burst, but it must have a limit and an operational response.

Useful controls include:

- worker concurrency;
- batch size;
- queue prefetch;
- integration rate limit;
- delay between batches;
- maximum queue age.

If the queue age keeps growing, adding more workers may overload the dependency. The team may need to reduce concurrency, pause one fulfillment route, or move blocked orders to manual review.

## Partitioning and Hotspots

Large systems split data and work across machines. The partition key decides where each item goes.

{/* IMAGE PROMPT (partition-hotspots.png): Wide modern green 2D cartoon infographic on a light background. Show records passing through a partition key and splitter into balanced shards, plus a contrasting bad key that creates one hot shard. Render only these labels once: KEY, SPLIT, BALANCE, HOTSPOT. */}

![A partition rule spreads marketplace work into balanced groups](/assets/images/blogs/practical-system-design/partition-hotspots.png)

Common keys include:

- user ID;
- account ID;
- order ID;
- tenant ID;
- time bucket;
- geographic region.

A good key spreads load and supports the main query. A bad key creates hotspots.

Suppose one large seller receives 1 million orders while most sellers receive 1,000. Partitioning only by `seller_id` sends the large seller to one partition. Adding an order ID hash or time bucket can spread the work.

### Consistent hashing: move fewer keys when nodes change

The simple rule `hash(key) % number_of_nodes` spreads keys while the node count stays fixed. When a node is added or removed, the result changes for many keys. That can cause a large cache refill or data movement.

Consistent hashing places nodes and keys on the same hash ring. A key belongs to the next node around the ring. When a node joins, only a nearby key range moves to it.

{/* IMAGE PROMPT (consistent-hashing-ring.png): Wide modern green 2D cartoon infographic on a warm-white and pale-mint background. Render each exact label once: HASH RING, KEYS, NODES, ADD NODE, MOVE FEWER KEYS, VIRTUAL NODES. Spell exactly. No other text, duplicate rings or labels, dark background, blue-led palette, photorealism, glossy 3D, logos, or watermarks. */}

![Consistent hashing moves a nearby key range when a node joins the ring](/assets/images/blogs/practical-system-design/consistent-hashing-ring.png)

Production designs often give each physical node several **virtual nodes**. They spread the ranges more evenly and make recovery load easier to share.

Consistent hashing still has limits:

- one popular key can still overload its owner;
- virtual nodes improve balance but add routing metadata;
- replicas and zone-aware placement are still needed for availability;
- a poor partition key stays poor after hashing.

It is useful for distributed caches, sharded stores, and stable worker ownership. The original [consistent hashing paper](https://people.csail.mit.edu/karger/Papers/web.pdf) introduced the technique for distributed caching. Amazon later described consistent hashing and virtual nodes in the [Dynamo paper](https://www.amazon.science/publications/dynamo-amazons-highly-available-key-value-store).

Consistent hashing does not remove the wider cost of partitioning:

- cross-partition queries;
- rebalancing;
- more complex transactions;
- harder operational tools;
- more difficult migrations.

Partition because the current access pattern needs it, not because the system may become large one day.

Multi-region architecture can improve availability and latency. It also changes data, operations, and cost.

## APIs and Contracts Are Part of the Design

An API makes promises to callers.

Define:

- resource names and identifiers;
- request and response shape;
- error model;
- idempotency behavior;
- pagination;
- rate limits;
- versioning;
- authentication and authorization.

For asynchronous work, return an order or job ID. Let the caller check status or receive a webhook.

```http
POST /orders
Idempotency-Key: 2d3817...

202 Accepted
{
  "orderId": "ord_123",
  "status": "accepted"
}
```

Avoid leaking an internal database model through the API. Internal tables will change. A stable contract gives the team room to change the implementation later.

Events are contracts too. Add schema versions, clear ownership, and compatibility rules. Removing or changing a field can break consumers you do not know about.

## Security Starts with Boundaries

The first version already had authentication, authorization, secret handling, and an audit trail. As the system grows, make every boundary explicit. Security is not one box at the edge of the diagram.

Ask:

- Who can call this API?
- Which order can this customer or seller view or change?
- Which service can read customer or payment data?
- Which data must be encrypted?
- Which action needs an audit event?
- Which secret can each worker access?
- How is tenant data separated?

Useful controls include:

- authentication;
- role- or attribute-based authorization;
- least-privilege service identities;
- encryption in transit and at rest;
- secret rotation;
- network boundaries;
- immutable audit logs;
- data retention and deletion policies.

Validate authorization at the resource boundary. A seller who can edit one product should not gain access to another seller's products by changing an ID in the URL.

For sensitive flows, isolation may be worth the extra cost. A separate account, cloud profile, database, or payment worker can reduce the failure and access surface.

## Observability Must Answer Operational Questions

The first version already had basic logs, metrics, a correlation ID, and an alert. As the flow grows, the questions become more specific. Logs, metrics, and traces are tools. Start from the questions the team must answer.

For the E-commerce system:

- Was the order accepted and paid?
- How many orders are waiting for fulfillment?
- How old is the oldest waiting order?
- Which payment, warehouse, or shipping integration is slow?
- How many orders succeeded, failed, or need review?
- Is one seller using most of the capacity?
- Can we pause one fulfillment route safely?
- Can we replay a failed order step?

Useful metrics include:

- request rate, error rate, and latency;
- queue depth and queue age;
- worker throughput;
- retry count;
- integration response codes;
- database connection use;
- cache hit rate;
- order and fulfillment progress.

Use correlation IDs such as order ID, customer ID, payment attempt ID, and fulfillment request ID. They help the team follow one flow across services.

An alert should describe an action. A high queue depth may be fine if workers are draining it fast enough. A queue age that may break the promised delivery time is more useful.

## Ownership Changes the Design

Two technologies may solve the same technical problem. The team may still prefer one because it can operate it safely.

{/* IMAGE PROMPT (own-the-decision.png): Wide modern green 2D cartoon coaching infographic on a light background. Show a constructive team design review where an engineer explains a choice, accepted compromise, expected failure, and responsible owner. Render only these labels once: WHY, TRADE-OFF, FAILURE, OWNER. */}

![Owning a decision means explaining why, trade-offs, failure, and ownership](/assets/images/blogs/practical-system-design/own-the-decision.png)

Check these areas:

- **Skills:** Does the team know how to debug and upgrade it?
- **Operations:** Who is on call for it?
- **Cost:** What happens when traffic grows ten times?
- **Security:** Does it add another data or access boundary?
- **Delivery:** How long will setup and migration take?
- **Reversal:** How hard is it to replace?
- **Organization:** Does its boundary match team ownership?

Discord's storage story is useful again. The database migration was not only about benchmark speed. It was also about unpredictable latency and high operational toil.

Meta's TAO story is also about ownership. The company did not only add a cache. It created an abstraction so product teams did not need to handle every cache and database detail themselves.

This is why a smaller architecture can be the mature choice. A design is useful only when the team can keep it useful.

## Migration Is Part of System Design

Most systems are not built on empty ground. A new design must move from an old design.

A safe migration may use:

1. **Shadow reads:** read from the new system without using its answer.
2. **Dual writes:** write to old and new stores for a limited period.
3. **Backfill:** copy old data with checksums and progress tracking.
4. **Small rollout:** move one tenant, region, or traffic percentage.
5. **Compare:** check data, latency, errors, and business results.
6. **Cut over:** make the new path primary.
7. **Keep rollback:** preserve a safe return path until confidence is high.

Dual writes can fail on one side. Plan reconciliation before enabling them.

A migration tool also needs idempotency, monitoring, pause, resume, and audit support. Temporary systems have a habit of staying longer than expected.

## A Coaching Method for System Design

Do not begin by asking for a complete architecture. Make the problem small enough to discuss.

The coaching loop can look like this:

1. Ask the engineer to explain the user and the goal.
2. List the requirements that change the design.
3. Draw the smallest version that works.
4. Add one constraint.
5. Ask what breaks first.
6. Compare two or three options.
7. Choose a decisive reason.
8. Name the trade-off and owner.
9. Add failure and recovery.
10. Review what would make the team revisit the choice.

Useful coaching questions include:

- What is the source of truth?
- What is on the hot path?
- Which work can be asynchronous?
- What can run twice?
- Where can data be lost?
- Which key can become hot?
- What happens when the dependency is slow, not fully down?
- How will the team know the system is unhealthy?
- Which part will be hardest to change?
- Would you still choose this with a team of three?

The mentor does not need to hide the answer. The mentor should help the engineer connect each answer to a reason.

## Final Thoughts

System Design knowledge includes databases, caches, queues, load balancers, APIs, partitions, regions, and many other tools. Learning those tools matters.

But knowing the name of every component is not the end goal.

The stronger skill is being able to say:

- this is the problem;
- this is the smallest design that works;
- this constraint forced the design to change;
- this option fits our data, traffic, and team;
- this is what can fail;
- this is the trade-off we accept;
- this is who will own it;
- this is when we should review it again.

That is the path from drawing boxes to owning decisions.
