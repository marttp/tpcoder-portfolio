If you have opened an old architecture diagram and wondered why the team designed it that way, this situation may feel familiar.

Suppose you join a team and see Kafka between two services. You ask why the team chose Kafka.

The answers may sound like this:

- Someone decided it two years ago.
- It was discussed in a meeting.
- The staff engineer probably knows.
- We already use Kafka, so we kept using it.

The code and diagram survived. The decision did not.

I wrote this article to help teams keep those reasons without adding heavy paperwork. An **Architecture Decision Record**, or ADR, is a short document. It records one important architecture choice, its context, and the work that follows from it.

My main point is simple:

**An ADR should preserve the reason behind a decision. It should not become paperwork that protects the past from change.**

AWS gives a similar definition. An ADR records an important architecture choice, its context, and its consequences. A group of ADRs becomes the decision log for a system. [AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)

## The Smallest ADR That Helps

An ADR does not need to be long. For most decisions, I would start with these parts:

```md
# Use a queue for invoice generation

Status: Accepted
Date: 2026-08-10
Owner: Billing team

## Context
Invoice generation can take 5–20 seconds. The HTTP request should not wait for it.

## Options
1. Generate the invoice inside the request
2. Put the job in a database table and poll it
3. Publish the job to the existing queue

## Decision
Use the existing queue and a separate invoice worker.

## Consequences
- The API can return after accepting the job.
- The worker needs idempotency and retry handling.
- The team must monitor queue age and failed jobs.
```

The useful part is not the format. It is the thinking inside it:

- **Context:** What problem and limits did we have?
- **Options:** What choices did we consider?
- **Decision:** What did we choose?
- **Consequences:** What benefit and ownership did we accept?

Some templates add assumptions, evidence, reviewers, or a review date. Add them when they help. Do not add ten empty sections because the template has ten headings.

## One Decision, One Story

Let us continue with the invoice example.

The first option is simple: generate the PDF inside the request. It needs fewer components. If invoice generation is fast and traffic is low, this may be enough.

Then a constraint appears. Generation may take 20 seconds and the external tax service is sometimes slow. Customers retry when the page waits too long. Now the simple option can create duplicate work and a poor user experience.

The team already operates a queue. That changes the comparison:

| Option | What it gives us | What we must own |
|---|---|---|
| Inside the request | Simple flow | Long request, timeout, customer retry |
| Database job table | Uses an existing database | Polling, locking, cleanup |
| Existing queue | Async work and worker scaling | Idempotency, DLQ, queue monitoring |

The ADR should explain why the third option fits **this** context. It should not claim that queues are always better.

This small example also makes review easier. A reviewer can challenge the decision with a useful question:

- Is the queue already reliable enough?
- Can the worker safely retry?
- How does a customer check the invoice status?
- What happens when the tax service is unavailable for one day?

The discussion stays connected to the problem.

## Accepted Does Not Mean Permanent

An accepted ADR is a record of what the team knew at that time. Editing it later to make the old choice look better removes that history.

If the context changes, write a new ADR and mark the old one as superseded.

For example, the invoice volume may later become very small. The queue platform may also become expensive to run. The team can move the jobs into a database-backed scheduler. This does not prove that the old choice was wrong. The constraints have changed.

## Not Every Decision Needs an ADR

An ADR has a cost. Someone must write, review, find, and maintain the decision log.

I would consider an ADR when a decision:

- changes a system boundary or important data flow;
- creates a long-term dependency;
- affects security, availability, or recovery;
- is expensive to reverse;
- caused a meaningful disagreement;
- will be difficult to understand from the code alone.

I would usually skip it for:

- a local refactor with no architecture effect;
- a small library update with an easy rollback;
- a temporary experiment that has a clear end date;
- a choice already explained well by a team standard.

If I am still unsure, I use one simple question:

**If someone asks in 2–3 months why the system works this way, can they find the answer in the code, pull request, or team standard?**

If the answer is easy to find, the team may not need another ADR. If the answer exists only in the memory of a few people, writing it down now is usually worth the small cost.

The goal is not to count ADR files. The goal is to make important decisions easier to understand and revisit.

## Where I Would Keep Them

For a software system, I prefer keeping ADRs close to the code, for example:

```text
docs/
  adr/
    0001-use-postgresql.md
    0002-publish-invoice-jobs.md
    0003-supersede-invoice-queue.md
```

This gives the decision history the same review and version control as the system. A central documentation platform can also work if people can find it and the team already maintains it.

The storage tool matters less than three habits:

1. Link the ADR from the change that implements it.
2. Use a short title that people can search.
3. Create a new record when the decision changes.

## A Small Coaching Tool

An ADR can help mentoring because it gives a junior or new engineer a safe place to ask questions.

Instead of saying **we use Kafka because it scales**, open the ADR and walk through the context:

- What problem existed?
- Which option was simpler?
- Which constraint removed that option?
- What new work did the chosen design create?
- Is the decision still worth its cost?

That conversation teaches more than the final technology name.

An ADR is not proof that the architecture is correct. It is evidence that the team made a choice with a known context. When the context changes, the team can make another choice without pretending the past never happened.
