พอพูดถึง AI Agent หลายคนเริ่มกังวลว่า agent อาจลงมือทำสิ่งที่ย้อนกลับไม่ได้ครับ แต่ปัญหานี้ไม่ได้เริ่มจาก AI เพราะ information system ทั่วไปก็มี action แบบนี้อยู่แล้ว

- ส่ง email
- โอนเงิน
- ลบ customer record
- Publish document
- เปลี่ยน access ของคน
- ส่ง order ไปหา external company

Action เหล่านี้ fail ได้โดยไม่ต้องมี AI ครับ

Request อาจ timeout หลัง external system รับงานไปแล้ว Worker อาจ crash หลังส่ง message แต่ยังไม่ทัน save result หรือ requests ที่ retry อาจเข้ามาพร้อมกัน 2 ชุด แม้แต่ operator เองก็เลือกลูกค้าผิดคนได้

Distributed system จึงต้องมี validation, idempotency, state machine, audit history, reconciliation และ recovery อยู่ก่อนแล้ว

ทีนี้ลองวาง AI Agent ไว้เหนือ APIs ชุดเดิม ระบบยังมี failure mode เก่าครบทุกข้อ และมีของใหม่เพิ่มมาอีก 1 ข้อคือ **agent อาจเลือก action ผิด แม้ services ทุกตัวจะทำงานตามที่ออกแบบไว้**

ผมเขียนบทความนี้เพื่อเทียบปัญหาเดิมของ information system กับความไม่แน่นอนที่ AI Agent เพิ่มเข้ามา แล้วค่อยดูว่าเราควรวาง control และ recovery ไว้ส่วนไหน

ผมเลยมองเรื่องนี้แบบนี้ครับ

**AI Agent เสนอหรือ request action ได้ ส่วนระบบ deterministic รอบข้างต้องควบคุม permission, execution และ recovery**

## First, Separate Three Kinds of Action

หลายคนเรียก high-impact action ทุกอย่างว่า irreversible ผมคิดว่าแยกออกเป็น 3 กลุ่มจะช่วยให้คุณเลือก control ได้ง่ายกว่า

### Reversible

ระบบ restore state ก่อนหน้าได้ด้วย operation สำหรับย้อนการเปลี่ยนแปลงที่เราเชื่อถือได้

ตัวอย่างเช่น

- Save draft แล้ว restore version ก่อนหน้า
- เปลี่ยน feature flag แล้วเปลี่ยนกลับ
- ย้าย ticket แล้วส่งกลับ queue เดิม

การย้อนกลับยังต้องมี authorization และ history แต่ old state ยังอยู่ให้ใช้

### Compensatable

Action แรกยังอยู่ใน history เราใช้ action อีกอันเพื่อแก้ผลกระทบทาง business ได้

ตัวอย่างเช่น

- Refund captured payment
- Issue credit หลัง invoice ผิด
- คืน access ด้วย permission change ใหม่
- สร้าง correction entry ใน ledger

Refund ไม่ได้ลบ charge เดิมออก การ refund จะสร้าง financial event เพิ่มอีกอัน Customer อาจต้องรอ เสียค่าธรรมเนียม หรือเห็นทั้ง 2 records อยู่ดีครับ

### Irreversible

เราไม่สามารถย้อนผลที่เกิดขึ้นไปแล้วได้แบบรับประกัน

ตัวอย่างเช่น

- ส่ง private data ไปผิด address
- Publish secret ใน public channel
- เปิดเผยข้อมูลผ่าน model response
- สั่ง physical shipment ที่ออกเดินทางไปแล้ว
- ลบ data copy ชุดสุดท้าย

เรารับมือ incident ได้ แต่รับประกันไม่ได้ว่าผู้รับจะลืมข้อมูล หรือทุก copy ถูกลบออกหมด

Classification นี้มีผลกับ design ครับ Reversible work เปิดให้ automate ได้มากกว่า Compensatable work ต้องมี recovery path ที่ test แล้ว ส่วน irreversible work ต้องมี control ที่เข้มก่อนข้าม boundary

## Reversibility Is More Than One Label

Action class เป็นจุดเริ่มต้น ไม่ควรเป็นคำตอบสุดท้ายครับ Action ที่อยู่ class เดียวกันอาจต้องใช้ control ต่างกันมาก

ลองเทียบ email 2 ฉบับ

- Email แจ้งว่า ticket ถูกเปิดแล้ว ส่งผิดคนก็ยังต้องจัดการ แต่ข้อมูลข้างในมี impact จำกัด
- Email ที่แนบ customer statement ส่งผิดคนครั้งเดียวก็กลายเป็น data incident

ทั้งคู่เป็น irreversible หลังส่งออกไปแล้ว แต่ risk ไม่เท่ากันเลย

เวลาประเมิน action ผมจะดูเพิ่มอีกอย่างน้อย 6 ด้าน

| Dimension | สิ่งที่ต้องดู | ตัวอย่าง |
|---|---|---|
| **Undo quality** | ย้อนกลับได้ครบแค่ไหน | Restore draft ได้ครบ แต่ refund แก้ได้เฉพาะ business effect |
| **Time window** | ยังหยุดหรือย้อนได้อีกนานเท่าไร | Scheduled email cancel ได้ก่อน provider รับงาน |
| **Blast radius** | กระทบกี่ user, tenant หรือ resource | ปิด feature flag 1 tenant เทียบกับทั้งระบบ |
| **Data exposure** | ข้อมูลออกจาก trust boundary หรือยัง | Internal note เทียบกับ email ไป external address |
| **Detectability** | รู้ได้เร็วแค่ไหนว่า action ผิด | Payment มี provider status แต่ข้อมูลรั่วอาจรู้เมื่อมีคนแจ้ง |
| **Recovery cost** | ต้องใช้เงิน เวลา และคนเท่าไร | แก้ label เทียบกับ recall shipment หลายประเทศ |

เพราะฉะนั้นคำว่า reversible ไม่ได้แปลว่าเปิดให้ agent ทำได้ทุกครั้ง ส่วน irreversible ก็ไม่ได้แปลว่าต้องมีคนกด approve ทุก case เราต้องเอา class มารวมกับ impact, scope, confidence และ recovery quality ก่อนเลือก control

## Map the Existing Deterministic Workflow First

สมมุติว่า customer-support system ทำ refund และส่ง email หา customer ได้

ถ้ายังไม่มี agent พนักงานจะเลือก order กรอก amount เลือก reason ดู message ก่อนส่ง แล้วค่อยกด confirm

ก่อนเพิ่ม AI Agent เราควรแยก behavior เดิมของ workflow นี้ให้ได้ก่อนครับ

| Existing behavior | Action class | เหตุผล | Control และ recovery |
|---|---|---|---|
| Save หรือแก้ draft note | Reversible | ระบบเก็บ version ก่อนหน้าไว้และ restore ได้ | Version history, authorization และ audit |
| เปลี่ยน case status | Reversible | State machine พากลับไปยัง state ก่อนหน้าได้ ถ้า business rule อนุญาต | Allowed transitions และ audit |
| Capture หรือ refund payment | Compensatable | Financial event เดิมยังอยู่ ต้องใช้ event ใหม่แก้ business effect | Idempotency, limit, reconciliation และ manual recovery |
| ส่ง email หา customer | Irreversible | หลัง email ถูกส่ง เราบังคับให้ recipient ลบหรือไม่อ่านไม่ได้ | Preview, approved template และ approval ก่อนส่ง |

Action class เหล่านี้ควรถูกกำหนดไว้ใน tool definition หรือ action registry ของระบบ ไม่ควรให้ employee, UI หรือ AI Agent เลือกใหม่เองทุกครั้ง

## Turn the Classification into an Action Contract

ถ้า classification อยู่ใน diagram อย่างเดียว runtime ก็ใช้ประโยชน์จากข้อมูลนั้นไม่ได้ครับ ผมอยากให้แต่ละ action มี contract ที่ทั้ง agent, policy engine, execution service และ operator อ่านชุดเดียวกัน

ตัวอย่าง `payment.refund` อาจกำหนดไว้แบบนี้

```yaml
action: payment.refund
version: 3
class: compensatable
owner: payment-operations

input_schema:
  order_id: string
  amount_minor: integer
  currency: string
  reason_code: enum
  evidence_refs: array

authorization:
  required_scope: refund:propose
  tenant_bound: true

policy:
  auto_execute_max_minor: 1000
  daily_customer_limit_minor: 5000
  approval_above_minor: 1000

execution:
  endpoint: POST /internal/refunds
  idempotency: required
  timeout_state: outcome_unknown

recovery:
  verify_with: GET /internal/refunds/{request_id}
  compensate_with: payment.adjustment.propose
  manual_queue: payment-recovery

evidence:
  retain_days: 365
  fields:
    - actor
    - proposal_hash
    - policy_result
    - approver
    - provider_refund_id
```

Contract นี้ไม่ได้มีไว้ให้ model อ่านอย่างเดียว Backend ใช้ enforce schema กับ limit, approval UI ใช้แสดง impact, monitoring ใช้หา owner ส่วน recovery worker ใช้ตาม outcome กับ compensation ต่อได้

อีกเรื่องที่สำคัญคือ version ครับ ถ้า policy หรือ recovery path เปลี่ยน action ที่ approve ไว้ก่อนหน้าไม่ควรไหลผ่านด้วย contract ชุดใหม่แบบเงียบ ๆ

Backend ไม่ควรเชื่อข้อมูลจากหน้าจอเพียงอย่างเดียว Backend ยังต้อง check ว่า

- Employee เปิด case นี้ได้
- Order เป็นของ customer คนนี้
- Payment ยัง refund ได้
- Amount ไม่เกินยอดที่เหลือ
- Request เดิมยังไม่เคยทำสำเร็จมาก่อน
- State change เดินตาม transition ที่อนุญาต

จากนั้นจึง record intent และ call payment provider

State สำคัญไม่ได้มีแค่ `success` หรือ `failed` ครับ External action มี **unknown outcome** ได้ Timeout บอกเพียงว่า caller ไม่ได้รับ response เราจึงสรุปไม่ได้ว่า provider ทำงานไปแล้วหรือยัง

ผมเรียนรู้ technique นี้จาก Stripe เป็นหลักครับ Stripe ให้ client ส่ง `Idempotency-Key` ตอนสร้างหรือ update object ถ้าเกิด connection error แล้วต้อง retry request เดิม Stripe จะคืน result ที่เก็บไว้ แทนการทำ operation ซ้ำ [Stripe API Reference](https://docs.stripe.com/api/idempotent_requests)

AWS อธิบาย problem เดียวกันในมุมของ idempotent APIs ได้ละเอียดขึ้น Caller อาจ timeout หลัง resource ถูกสร้างไปแล้ว ถ้า retry โดยไม่รู้ state ก็อาจสร้างของซ้ำ Caller-provided request ID ช่วยให้ service รู้ว่า request นี้มาจาก intent เดิม และตอบกลับด้วย result เดิมได้ [Amazon Builders’ Library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

Recovery tools ที่ system ปกติใช้มีหลายแบบ

- **retry:** ทำ safe operation ซ้ำหลัง temporary failure
- **idempotency:** Request ซ้ำของ intent เดิมไม่สร้าง side effect เพิ่ม
- **compensation:** ทำ business action อีกอันเพื่อแก้ effect
- **reconciliation:** เทียบ internal state กับ external source of truth
- **manual recovery:** ให้ operator มี evidence และเครื่องมือพอสำหรับจัดการ case ให้จบ

## Know Where the Side Effect Begins

คำว่า execute กว้างเกินไปสำหรับงานที่มีผลกับระบบอื่นครับ เราต้องรู้ว่า step ไหนเป็นแค่การเตรียม intent และ step ไหนข้าม side-effect boundary ไปแล้ว

สำหรับ refund flow อาจแบ่งได้แบบนี้

1. Agent สร้าง proposal — ยังไม่มี side effect
2. Backend validate order, amount และ policy — ยังไม่มี side effect
3. System บันทึก intent กับ idempotency key — มี durable record แต่เงินยังไม่ขยับ
4. Payment provider รับ refund — ข้าม side-effect boundary
5. System บันทึก provider result — internal state ตาม external state ทัน
6. Reconciliation ตรวจซ้ำถ้า outcome ยัง unknown

ปัญหาที่เจอบ่อยคือ step 4 สำเร็จ แต่ process crash ก่อน step 5 ถ้ามองจาก database อย่างเดียวเหมือน refund ยังไม่เกิด ทั้งที่ provider ทำงานไปแล้ว

ระบบจึงต้องแยก **intent, dispatch และ outcome** ออกจากกัน พร้อมเก็บ correlation ID ที่ตามข้าม service ได้ ถ้าต้อง update database แล้วส่ง event ต่อ อย่าทำ dual write แบบหวังว่าทั้ง 2 คำสั่งจะสำเร็จพร้อมกัน Transactional outbox ช่วยบันทึก state change กับ event ใน database transaction เดียว แล้วให้ worker ส่ง event หลัง commit ส่วน consumer ยังต้องรองรับ duplicate ด้วย idempotency [AWS Transactional Outbox Pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

Outbox ไม่ได้ทำให้ external action atomic กับ database ครับ หน้าที่ของมันคือไม่ทำ event หล่นระหว่าง commit กับ publish ส่วน unknown outcome ของ provider ยังต้องใช้ idempotency และ reconciliation จัดการอยู่ดี

## Add the AI Agent to the Same Workflow

บริษัทเพิ่ม AI Agent เข้ามา Agent อ่าน support conversation ดู order เสนอ refund และ draft email

Agent อาจเสนอหลาย actions จาก request เดียว แต่ deterministic system จะจัดการแต่ละ action ตาม class ที่กำหนดไว้แล้ว

| Agent proposal | Existing action class | Deterministic response |
|---|---|---|
| `case.note.update` | Reversible | Validate access แล้ว save พร้อม version history |
| `payment.refund` | Compensatable | Check policy, amount และ idempotency จากนั้นขอ approval เมื่อเกิน limit |
| `customer.email.send` | Irreversible | สร้าง preview และหยุดรอ confirmation ก่อนส่ง |

Agent มีหน้าที่ตีความ request และเตรียม proposal ส่วน backend เป็นคนบอกว่า action นี้อยู่ class ไหน ใคร approve ได้ และต้องเตรียม recovery แบบใดครับ

Agent มี failure mode เพิ่มจาก backend code ทั่วไป

- เข้าใจสิ่งที่ customer ขอผิด
- เอารายละเอียดจากอีก case มาใช้
- เลือก tool ผิด
- สร้าง refund reason ที่ไม่มีอยู่
- เลือก amount ที่ฟังดูสมเหตุผลแต่ผิด policy
- ทำงานต่อหลัง goal เปลี่ยน
- ทำตาม malicious instruction ที่ซ่อนใน document หรือ message

Evaluation ที่ดีไม่ได้ลบ uncertainty ชุดนี้ออกครับ

สมมุติว่า agent ทำ evaluation set ถูก 90% ตัวเลขนี้ไม่ได้แปลว่า request ลำดับที่ 10 ใน production จะ fail ให้เราเดาได้ Production input เปลี่ยนอยู่ตลอด Rare case อาจสร้างผลกระทบสูงกว่า common case และ evaluation อาจยังไม่ครอบคลุม tool, policy, language หรือ attack แบบใหม่

Evaluation คือ evidence ครับ ไม่ใช่ permission สำหรับถอด system boundary ออก

## Keep Planning and Execution Separate

Agent มีประโยชน์กับงานที่ต้องตีความ

- เข้าใจ request
- รวบรวม context ที่เกี่ยวข้อง
- เสนอ action
- อธิบายเหตุผลที่เลือก
- เตรียม parameters

ส่วน execution service ควรดูแล deterministic checks

- Validate schema และ required fields
- Load authoritative data
- Evaluate permission และ business policy
- Check amount และ frequency limits
- Require approval เมื่อ risk สูง
- Apply idempotency และ state transition
- Record action และ result

## Bind Approval to the Exact Proposal

Human approval ช่วยได้เมื่อคนเห็นข้อมูลพอและ approval ผูกกับ action ที่กำลังจะ execute ครับ ปุ่ม Approve อย่างเดียวไม่ได้รับประกันว่าคนเข้าใจสิ่งที่กำลังกด

หน้าจอ review ควรแสดงอย่างน้อย

- ใครหรือ agent ตัวไหนเสนอ action
- Customer, tenant และ resource ที่ได้รับผลกระทบ
- ค่าเดิมกับค่าที่กำลังจะเปลี่ยน
- Amount, destination หรือ permission ที่จะใช้
- Evidence ที่ agent อ้างอิง
- Policy result และเหตุผลที่ต้อง approve
- Action class, recovery path และ point of no return

ตอน approver กด confirm ระบบควร bind approval กับข้อมูลชุดนั้น เช่นเก็บ `proposal_hash`, action contract version, policy version และ expiry ไว้ด้วย

ถ้า agent เปลี่ยน amount, recipient, attachment หรือ tool parameter หลัง approval ค่า hash ต้องเปลี่ยนและ approval เดิมต้องใช้ไม่ได้ อย่า approve intent กว้าง ๆ อย่างช่วยลูกค้าคนนี้ แล้วปล่อยให้ agent เลือก execution payload ทีหลัง

Approval ควรหมดอายุด้วยครับ Order state, balance, customer request หรือ policy อาจเปลี่ยนระหว่างรอคน review ก่อน execute backend ต้องโหลด authoritative state และ validate ซ้ำเสมอ

## Let Risk Choose the Control

ถ้าทุก tool call ต้องมี human approval agent จะช้าและแพง แต่ถ้าไม่มี approval เลย ความผิดพลาดจาก model ทุกครั้งก็จะกลายเป็น operational risk

ใช้ action class, impact, confidence และ context มาช่วยเลือก control ครับ

| Situation | Control ที่อาจใช้ |
|---|---|
| อ่าน public documentation | Allow และ log |
| เพิ่ม internal draft note | Allow พร้อม undo ง่าย ๆ |
| ส่ง normal reply จาก approved template | Preview หรือ sample review |
| Refund ยอดเล็กที่ผ่าน eligibility | Policy limit และ post-action review |
| Refund ยอดสูงหรือผิดจาก pattern | Human approval |
| Export sensitive data | Deny by default หรือใช้ controlled flow แยก |
| ลบ data copy ชุดสุดท้าย | ไม่เปิดเป็น agent tool |

flowchart TD
    P["Action proposal"] --> R["Risk classification"]
    R --> L["Low\nAllow + log"]
    R --> M["Medium\nPreview or bounded execution"]
    R --> H["High\nHuman approval"]
    R --> F["Forbidden\nDo not expose the tool"]
`} />

Limit บางข้อควรเป็น hard rule

- Maximum amount ต่อ action และต่อวัน
- Allowed customer หรือ tenant boundary
- Allowed destination domains
- Approved message templates
- Time window
- Maximum tool calls
- ห้าม delegate ต่อ
- ห้าม access raw credentials

Model อธิบายเหตุผลที่ขอ exception ได้ แต่อนุมัติ exception ให้ตัวเองไม่ได้

OWASP มี guidance สำหรับ agentic applications ครอบคลุม goal hijacking, tool misuse, identity abuse และ unexpected code execution Mitigation ที่แนะนำรวมถึง confirmation ผ่าน human approval, policy engine หรือ platform guardrail เมื่อ goal เปลี่ยนหรือ action เริ่มไม่ปลอดภัย [OWASP Agentic Security Initiative](https://genai.owasp.org/initiatives/agentic-security-initiative/)

## Put the Point of No Return Near the End

Request เดียวอาจสร้างหลาย actions ครับ สมมุติ customer ขอ cancel order, refund เงิน, คืน inventory และส่ง email ยืนยัน

ถ้าปล่อยให้ agent เลือกลำดับเอง เราอาจส่ง email ว่า refund สำเร็จก่อน payment provider รับคำสั่ง หรือคืน inventory กลับไปขายก่อน fulfillment ยืนยันว่าหยุด shipment แล้ว

ลำดับที่ปลอดภัยกว่าคือ

1. Validate authoritative state และ permission
2. Reserve resource ที่จำเป็นพร้อม timeout
3. บันทึก intent และ workflow state
4. ทำ reversible หรือ compensatable steps
5. Verify outcome ของแต่ละ step
6. ทำ irreversible step หลัง critical validations ผ่านแล้ว
7. Release reservation และปิด workflow

<MermaidDiagram chart={`

    R --> I["Record intent"]
    I --> C["Compensatable steps"]
    C --> G{"All critical checks pass?"}
    G -->|No| B["Compensate or recover"]
    G -->|Yes| P["Point of no return"]

ถ้า step หลังบ้านหลายตัวอยู่คนละ service เราอาจใช้ Saga เพื่อเก็บ progress และเลือกว่าจะ forward recovery หรือ backward recovery เมื่อบาง step fail [AWS Saga Patterns](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-patterns.html)

Compensation ไม่จำเป็นต้องคืน state ให้เหมือนก่อนเริ่มทุก byte และไม่จำเป็นต้องทำย้อนลำดับเสมอไปครับ Business rule อาจกำหนดให้แก้ resource ที่ sensitive กว่าก่อน อีกอย่างคือ compensation เองก็ fail ได้ จึงต้องทำให้ retry ได้ เก็บ checkpoint และมี manual recovery [Microsoft Compensating Transaction Pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)

สำหรับ workflow ที่มี irreversible step ให้ประกาศ **point of no return** ไว้ใน design แล้วขยับ step นั้นไปหลัง validation กับ compensatable work ที่สำคัญ ถ้ายังมี uncertainty สูง อย่ารีบข้าม boundary

## Design the Recovery Before the Happy Path

ก่อนเอา tool ขึ้น production ผมจะถาม 7 ข้อนี้

1. เรารู้ได้อย่างไรว่า action เกิดขึ้นแล้ว
2. Intent เดิม retry ได้อย่างปลอดภัยไหม
3. Reverse หรือ compensate ได้หรือเปล่า
4. State ไหนแทน unknown outcome
5. ใครรับ recovery task
6. คนนั้นจะเห็น evidence อะไร
7. หยุด agent ตัวนี้โดยไม่หยุด workflow ทั้งหมดอย่างไร

เก็บ checkpoint สำคัญไว้ให้ครบ

- Original request และ actor
- Agent, model, prompt และ tool versions
- Evidence ที่ใช้สร้าง proposal
- Structured proposal
- Policy result
- Approval และ approver
- Idempotency key
- External action ID
- Final หรือ unknown outcome
- Compensation หรือ manual recovery

## Observe the Action Lifecycle

ถ้าเราเก็บแค่ model latency กับ token usage เราจะไม่รู้ว่า agent สร้างภาระให้ operation แค่ไหนครับ Observability ของ action layer ต้องตามตั้งแต่ proposal ไปจนถึง recovery

| Signal | ช่วยให้เห็นอะไร |
|---|---|
| Proposal count แยกตาม action และ risk | Agent กำลังพยายามทำอะไรบ่อยขึ้น |
| Policy denial แยกตาม reason | Prompt, tool description หรือ user request กำลังชน rule ไหน |
| Approval rate, expiry และ review time | Human gate ช่วยอยู่หรือกลายเป็น bottleneck |
| Completed, failed และ outcome unknown | Execution path มี uncertainty อยู่จุดไหน |
| Reconciliation age | Unknown case ค้างนานเท่าไร |
| Compensation rate และ success | Agent หรือ workflow สร้างงานแก้ตามหลังมากแค่ไหน |
| Manual recovery queue age | Operation team รับภาระไหวหรือไม่ |
| Irreversible action แยกตาม actor และ tenant | มี anomaly หรือ blast radius ที่ควรหยุดหรือเปล่า |

Metric พวกนี้ต้องย้อนกลับไปหา trace, proposal, policy result, approval และ external action ID ได้ ไม่อย่างนั้น dashboard จะบอกว่ามีปัญหา แต่คนแก้ยังต้องไล่ข้อมูลใหม่ตั้งแต่ต้น

ก่อนเพิ่ม autonomy ผมจะค่อย ๆ เปิดเป็นขั้นครับ

1. **Offline evaluation:** ทดสอบ proposal กับ historical cases
2. **Shadow mode:** ให้ agent เสนอ action แต่ยังไม่ execute
3. **Decision comparison:** เทียบ proposal กับสิ่งที่ operator เลือก พร้อมดู disagreement
4. **Approval required:** ใช้ execution path ชุด production โดยทุก action ยังรอคน
5. **Bounded automation:** เปิดเฉพาะ low-risk cases ภายใต้ amount, tenant และ rate limit
6. **Continuous review:** Sample completed actions, incidents, denials และ compensation กลับเข้า evaluation

ถ้า unknown outcome, compensation หรือ manual recovery เพิ่มขึ้นหลังขยาย autonomy ระบบควรลดสิทธิ์กลับได้โดยไม่ต้องรอ deploy model ใหม่

## The Human System and Agent System Should Share the Core

Human กับ agent ไม่จำเป็นต้องมี transaction system คนละชุด

ทั้ง 2 path ควรใช้ของร่วมกัน

- authoritative data
- authorization service
- business rules
- state machine
- idempotent execution API
- audit และ reconciliation path

Agent path ต้องเพิ่ม control สำหรับ non-deterministic decision, tool selection, model context และ evaluation ส่วน human path มี UI control กับ operator accountability ถึงทางเข้าจะต่างกัน transaction core ยัง deterministic เหมือนเดิมครับ

สิ่งที่เปลี่ยนตอนเพิ่ม AI Agent คือทางเข้าของ decision ครับ System ต้องรับ structured proposal, ตรวจ model context และเลือก control จาก risk ส่วน transaction core ยังทำงานแบบเดิม

- Validate authoritative state
- Enforce authorization กับ business rule
- Bind approval เข้ากับ payload
- Execute ด้วย idempotency
- เก็บ durable state เมื่อ outcome ยัง unknown
- Reconcile, compensate หรือส่งต่อ manual recovery

ถ้าจะจำบทความนี้เพียงเรื่องเดียว ผมอยากให้จำว่า **Agent ช่วยคิดและเสนอ action ได้ แต่สิทธิ์ในการสร้าง side effect กับความรับผิดชอบเรื่อง recovery ต้องอยู่ใน deterministic system**

เมื่อวาง boundary แบบนี้ เราเพิ่ม autonomy จาก production evidence ได้โดยไม่ต้องสร้าง transaction path ชุดใหม่ และไม่ต้องหวังว่า model จะไม่พลาดอีกเลยครับ
