ถ้าคุณเคยเปิด dashboard แล้วทุกช่องยังเป็นสีเขียว ทั้งที่ customer ใช้งานไม่สำเร็จ บทความนี้เริ่มจากปัญหาเดียวกันครับ

สมมุติว่า customer แจ้งว่า checkout ใช้เวลา 18 วินาทีแล้วจบด้วย error คุณเปิด dashboard ขึ้นมาดู

- CPU ปกติ
- Memory ปกติ
- Error rate ยังต่ำกว่า alert threshold
- ทุก service ขึ้น healthy

Dashboard เป็นสีเขียว แต่ customer ใช้งานไม่สำเร็จครับ

Monitoring ช่วยบอกว่า condition ที่เรารู้จักเริ่มผิดปกติหรือยัง ส่วน Observability ควรพาเราไปต่อได้ แม้ทีมไม่เคยเตรียม dashboard สำหรับคำถามนั้นไว้ก่อน

ผมเขียนบทความนี้เพื่อพา Observability กลับมาเริ่มจากสิ่งที่ user เจอและคำถามที่ทีมต้องตอบ แล้วค่อยเลือก metrics, logs และ traces ที่ช่วยหาคำตอบนั้นครับ

| Monitoring ถาม | Observability ช่วยถามต่อ |
|---|---|
| Service ยังทำงานอยู่ไหม | Checkout ของ customer คนนี้ fail เพราะอะไร |
| CPU เกิน 80% หรือยัง | Dependency ตัวไหนทำให้ request นี้ช้า |
| Error rate เกิน threshold ไหม | Problem กระทบ user, version หรือ payment provider กลุ่มไหน |
| Queue กำลังโตไหม | Job ชุดไหนค้าง และ replay อย่างปลอดภัยได้หรือเปล่า |

ถ้าอธิบายแบบเอาไปใช้ทำงาน **Observability คือความสามารถที่ช่วยให้เราเข้าใจว่าภายในระบบกำลังเกิดอะไรขึ้น จากข้อมูลที่ระบบสร้างออกมา** เราควรใช้ข้อมูลเหล่านี้ตอบให้ได้ว่าเกิดอะไรขึ้น เพราะอะไร และกระทบ user กลุ่มไหน แม้ทีมจะยังไม่มี dashboard เตรียมไว้สำหรับคำถามนั้นก็ตาม

OpenTelemetry เรียกข้อมูลเหล่านี้ว่า signals โดย 3 แบบที่เราเจอบ่อยมีหน้าตาและหน้าที่ต่างกันครับ [OpenTelemetry Observability Primer](https://opentelemetry.io/docs/concepts/observability-primer/)

| Signal | ข้อมูลมีหน้าตาแบบไหน | เหมาะกับการตอบอะไร | ข้อจำกัดหลัก |
|---|---|---|---|
| Metrics | ตัวเลขที่วัดต่อเนื่องตามเวลา | Rate, trend, alert และ system health | มองไม่เห็นรายละเอียดของ request เดียว |
| Logs | Events ที่มีเวลา fields และ message | อธิบายว่าเกิดอะไรขึ้นในช่วงหนึ่ง | ปริมาณโตเร็ว และเชื่อม events ยากถ้าไม่มี shared IDs |
| Traces | Operation 1 งานซึ่งแบ่งเป็น spans ที่เชื่อมกัน | หาว่าเวลาและ failure อยู่ช่วงไหนเมื่อ request ข้ามหลาย services | ต้องส่ง context ข้าม service พร้อมควบคุม sampling และ storage |

Signal เพียงแบบเดียวตอบไม่ได้ทุกคำถามครับ Metrics ช่วยให้เห็นขนาดและแนวโน้มของปัญหา Logs ให้รายละเอียดของ event ส่วน Traces เชื่อม path ที่วิ่งข้าม services เข้าด้วยกัน

ประเด็นหลักของบทความนี้คือ

**Observability ควรเริ่มจาก user journey และคำถามที่ทีมต้องตอบ ไม่ควรเริ่มจากการเก็บทุก signal ที่ tool รองรับ**

## เริ่มจาก Checkout Journey เพียง 1 เส้น

บทความนี้จะใช้ E-commerce checkout เป็นตัวอย่างครับ

1. Customer ส่ง order
2. Order service ขอ reserve inventory
3. Payment service ขอ authorize payment
4. Order service confirm order
5. Worker ส่ง receipt

ก่อนเลือก tool ลองเขียนคำถามที่ทีมควรตอบให้ได้ก่อน

- Customer ได้ response ที่นำไปใช้ต่อได้หรือเปล่า
- Checkout ทั้ง flow ใช้เวลาเท่าไร
- Dependency ตัวไหนใช้เวลามากที่สุด
- Payment สำเร็จแล้ว แต่ confirm order ล้มเหลวหรือไม่
- Retry ทำให้เกิด payment attempt เพิ่มหรือเปล่า
- Problem เกิดเฉพาะ region, version, seller หรือ provider บางรายไหม

คำถามเป็นตัวกำหนดว่าเราต้องเก็บอะไร ส่วน tool ค่อยเลือกทีหลังครับ

## กำหนดหน้าที่ให้แต่ละ Signal

Metrics, logs และ traces ไม่ได้แข่งกันเก็บข้อมูลชุดเดียวกันนะครับ เวลา investigate เราใช้แต่ละแบบต่อกันประมาณนี้

1. Metrics บอกว่า checkout เริ่มช้าลง และ problem กระทบกว้างแค่ไหน
2. Traces พาเราไปเจอ payment span ที่ช้าอยู่ใน retry path
3. Logs อธิบาย timeout, provider response และ retry decision ของ span นั้น
4. Business events ยืนยันว่า payment หรือ order เปลี่ยน state ไปแล้ว และต้อง recovery ต่อหรือไม่

ผมแยก business events ออกมา เพราะข้อมูลกลุ่มนี้ใช้เก็บ state change สำคัญ เช่น `payment_authorized` หรือ `refund_requested` เราไม่ควรดูแลเหมือน debug logs ทั่วไป

- request, success และ failure count

- service และ deployment version

ข้อมูลชุดนี้พอให้เริ่ม investigate ได้ แต่ยังตอบไม่ได้ทุกคำถาม ซึ่งไม่เป็นไรครับ เราค่อยเพิ่มเมื่อเจอช่องว่างที่ควรปิด

## ออกแบบ Context ก่อนสร้าง Dashboard

Signal แต่ละแบบจะมีประโยชน์ขึ้นมาก ถ้าเราเชื่อมกลับมาหา request หรืองานชิ้นเดียวกันได้

Field ที่มักช่วยตอน investigate เช่น

- `trace_id` และ `span_id`
- `request_id` หรือ `operation_id`
- `order_id`, `payment_attempt_id` หรือ `job_id`
- `service.name` และ `service.version`
- deployment environment และ region
- dependency name
- outcome และ error category

OpenTelemetry Semantic Conventions กำหนดชื่อกลางสำหรับ service, HTTP call, database, messaging และ operation แบบอื่น การใช้ naming scheme ร่วมกันช่วยให้ query ข้ามภาษาและข้ามทีมได้ง่ายขึ้น [OpenTelemetry Semantic Conventions](https://opentelemetry.io/docs/concepts/semantic-conventions/)

OpenTelemetry Baggage ใช้ส่ง context บางส่วนข้าม service boundary ได้ แต่ baggage อาจติดไปกับ headers และไม่มี integrity check ในตัว อย่าใส่ secrets และอย่าใช้ข้อมูลใน baggage ตัดสิน authorization [OpenTelemetry Baggage](https://opentelemetry.io/docs/concepts/signals/baggage/)

Field ที่มี cardinality สูงอย่าง `order_id` เหมาะกับ logs และ traces ส่วนการนำไปทำ metric label อาจสร้าง time series หลายล้านชุดได้

## Log Format ที่ทีม Query ต่อได้

Log ที่ใช้สืบปัญหาได้ควรเป็น event ซึ่งมี fields ที่คงรูป ไม่ควรเป็นประโยคที่มีแค่คนเขียนเข้าใจครับ

ตัวอย่าง JSON log สำหรับ payment authorization ที่ fail

```json
{
  "timestamp": "2026-08-10T09:42:17.381Z",
  "severity": "ERROR",
  "service.name": "checkout-api",
  "service.version": "2026.08.10-3",
  "deployment.environment.name": "production",
  "event.name": "payment.authorization.failed",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "00f067aa0ba902b7",
  "request_id": "req_91ab",
  "order_id": "ord_84f2",
  "payment_attempt_id": "pay_18c1",
  "provider": "provider_a",
  "outcome": "timeout",
  "error.type": "provider_timeout",
  "duration_ms": 5032,
  "retryable": true
}
```

ชื่อ field ของแต่ละทีมอาจไม่เหมือนกัน ขอให้ใช้รูปแบบเดียวกันในระบบก็พอ

| กลุ่มข้อมูล | เก็บไว้ตอบอะไร |
|---|---|
| เวลาและ severity | วาง event ลงใน incident timeline |
| Service และ version | หา code กับ release ที่สร้าง log นี้ |
| Trace และ operation IDs | กระโดดจาก log ไปดู request path ทั้งเส้น |
| Business IDs | หา order หรือ payment attempt ที่ได้รับผลกระทบ |
| Outcome และ error type | รวม failure เป็นกลุ่มโดยไม่ต้อง parse ประโยค |
| Duration และ retry state | อธิบาย latency กับพฤติกรรมตอน recovery |

อย่าเก็บ password, access token, ข้อมูลบัตรแบบเต็ม หรือข้อมูล customer ที่ sensitive ลง log การทำ structured log ไม่ได้แปลว่าต้อง copy input ทุก field

ถ้าเก็บ logs ไว้ใน Grafana Loki เราใช้ LogQL query แบบนี้เพื่อหา events ของ trace เดียวกันได้

```logql
{service_name="checkout-api"}
| json
| trace_id="4bf92f3577b34da6a3ce929d0e0e4736"
```

Loki รองรับการ parse JSON และ `logfmt` ระหว่าง query [Grafana Loki log queries](https://grafana.com/docs/loki/latest/query/log_queries/)

![Grafana Explore พร้อม Loki data source และ LogQL editor](/assets/images/blogs/practical-observability/grafana-loki-explore-official.png)

ภาพจาก [Grafana Loki tutorial](https://grafana.com/docs/loki/latest/get-started/quick-start/tutorial/) ครับ Grafana Explore มีทั้ง visual query builder และ code editor หน้าตาของ UI อาจเปลี่ยนไปตาม version แต่ flow หลักยังคล้ายเดิม คือเลือก Loki กำหนด time range เขียนหรือประกอบ query แล้วค่อยดู logs ที่ได้กลับมา

## Metrics ต้องตอบคำถามได้ และ Query ต้องใช้ต่อได้

เลือก metric type จากคำถามที่อยากตอบครับ

| Metric type | เหมาะกับ | ตัวอย่างจาก checkout |
|---|---|---|
| Counter | ยอดรวมที่เพิ่มอย่างเดียว | Requests, failures, retries |
| Histogram | การกระจายของค่า | Request และ provider latency |
| Gauge | ค่าที่เพิ่มและลดได้ | Queue depth, active connections |

ตัวอย่างต่อไปนี้เป็น PromQL และสมมุติว่า histogram หลัง export ชื่อ `http_server_request_duration_seconds` Backend อาจเปลี่ยนชื่อจาก OpenTelemetry หรือ Micrometer คนละแบบ เพราะงั้นเปิดดู series ที่ส่งออกมาก่อน copy query ไปใช้ครับ

### Request rate

```promql
sum(
  rate(http_server_request_duration_seconds_count{
    service_name="checkout-api",
    http_route="/checkout"
  }[5m])
)
```

`rate()` เปลี่ยน counter ให้เป็นค่าเฉลี่ยต่อวินาทีภายใน time window ที่เลือก

### Server error ratio

```promql
sum(
  rate(http_server_request_duration_seconds_count{
    service_name="checkout-api",
    http_route="/checkout",
    http_response_status_code=~"5.."
  }[5m])
)
/
sum(
  rate(http_server_request_duration_seconds_count{
    service_name="checkout-api",
    http_route="/checkout"
  }[5m])
)
```

Query นี้ให้สัดส่วน HTTP 5xx แต่ยังไม่รวม business failure ทุกแบบ เช่น payment ถูก reject แล้ว API ตอบ HTTP 200 เราอาจต้องมี counter สำหรับ product outcome แยกอีกชุด

### p95 checkout latency

```promql
histogram_quantile(
  0.95,
  sum by (le) (
    rate(http_server_request_duration_seconds_bucket{
      service_name="checkout-api",
      http_route="/checkout"
    }[5m])
  )
)
```

Prometheus ใช้ `histogram_quantile()` คำนวณ quantile จาก histogram buckets และ classic histogram ต้องเก็บ label `le` ไว้ตอน aggregate [Prometheus query functions](https://prometheus.io/docs/prometheus/latest/querying/functions/#histogram_quantile)

อย่าดูแต่ average ครับ เพราะค่าเฉลี่ยอาจนิ่ง ทั้งที่ customer กลุ่มเล็กกำลังรอนานกว่าคนอื่นมาก

## ใช้ Traces เชื่อม Request Path

Distributed trace ตาม operation 1 งานข้าม services แต่ละ span แทนช่วงงานที่มีประโยชน์ พร้อม timing, status และ attributes

Slow checkout 1 ครั้งอาจมีข้อมูลแบบนี้

| Span | Duration | สิ่งที่เราเริ่มตอบได้ |
|---|---:|---|
| Inventory reserve | 120 ms | Inventory ไม่ใช่ช่วงที่ช้า |
| Order database | 45 ms | เวลาใน database ค่อนข้างน้อย |
| Payment provider attempt 1 | 5,032 ms | Call แรกชน timeout |
| Payment provider attempt 2 | 5,010 ms | Retry เพิ่มเวลาอีก 5 วินาที |
| Response mapping | 20 ms | งานฝั่ง response ใช้เวลาน้อย |

จากคำกว้าง ๆ ว่า **checkout ช้า** ทีมเริ่มถามได้แล้วว่า **ทำไม payment ถึง retry หลัง timeout 5 วินาที**

ถ้าใช้ Grafana Tempo เราหา error spans ที่ช้ากว่า 1 วินาทีด้วย TraceQL ได้

```traceql
{
  resource.service.name = "checkout-api" &&
  status = error &&
  duration > 1s
}
```

TraceQL ใช้ filter spans จาก service, status, duration และ OpenTelemetry attributes ได้ [Grafana TraceQL examples](https://grafana.com/docs/grafana/latest/datasources/tempo/query-editor/traceql-query-examples/)

![Grafana Tempo search builder ที่สร้าง TraceQL และแสดง trace results](/assets/images/blogs/practical-observability/grafana-tempo-query-builder-official.png)

ภาพจาก [Grafana Tempo search documentation](https://grafana.com/docs/grafana/latest/datasources/tempo/query-editor/traceql-search/) ครับ Builder จะเปลี่ยน filters เช่น service, status, duration และ tags ให้เป็น TraceQL เหมาะกับคนที่ยังจำ query syntax ไม่ได้ทั้งหมด

ไม่ต้องสร้าง span ให้ทุก function ครับ เลือก boundary ที่ช่วยอธิบาย remote call, queue, database และ business operation สำคัญก็พอ

## Business Events ต้องมีความหมายที่คงอยู่

บาง event ควรมี durable history แยกจาก application logs ทั่วไป

- order accepted
- payment authorized
- refund requested
- permission changed
- deployment started
- feature flag changed

Events ชุดนี้ช่วยเรื่อง audit, recovery และการตรวจสอบฝั่ง business จึงควรมี owner, schema, retention rule และ delivery expectation ที่ระบุไว้

Debug log หลุดหายไป 1 บรรทัดอาจไม่กระทบ business state แต่ `payment_authorized` อาจเป็นส่วนที่ใช้ยืนยันว่าเกิดการเปลี่ยน state ขึ้นแล้ว การดูแลข้อมูล 2 แบบนี้เหมือนกันทั้งหมดจะสร้างปัญหาภายหลังครับ

## OpenTelemetry ทำหน้าที่อะไร

OpenTelemetry ไม่ใช่ dashboard และไม่ใช่ storage database ครับ OpenTelemetry เป็นชุดของ APIs, SDKs, semantic conventions, instrumentation และ protocols สำหรับสร้างและส่ง telemetry โดยไม่ผูกกับ vendor รายเดียว

แต่ละส่วนรับผิดชอบคนละงาน

| ส่วนประกอบ | หน้าที่ |
|---|---|
| API และ SDK | สร้าง telemetry ภายใน application |
| Auto-instrumentation | เก็บ HTTP, database และ messaging telemetry โดยแก้ code น้อยหรือไม่ต้องแก้ |
| Semantic Conventions | กำหนดชื่อกลางให้ operations และ attributes |
| OTLP | ส่ง traces, metrics และ logs ผ่าน telemetry protocol ชุดเดียว |
| Collector | Receive, process, filter, batch และ export telemetry |
| Backend | Store, query, visualize และ alert จากข้อมูล |

Collector ใช้ pipeline ที่ประกอบด้วย receivers, processors และ exporters เพื่อรับ OTLP แล้วส่ง telemetry ไปยัง backends 1 ตัวหรือหลายตัว [OpenTelemetry Collector architecture](https://opentelemetry.io/docs/collector/architecture/)

![OpenTelemetry Collector diagram จาก official documentation ซึ่งแสดง receivers, processors และ exporters](/assets/images/blogs/practical-observability/otel-collector-official.svg)

ภาพจาก [OpenTelemetry Collector documentation](https://opentelemetry.io/docs/collector/) ภายใต้ [CC BY 4.0](https://github.com/open-telemetry/opentelemetry.io/blob/main/LICENSE) ครับ ภาพนี้ช่วยให้เห็นว่า Collector 1 ตัวรับข้อมูลได้หลาย protocol จากนั้นค่อย process แต่ละ pipeline แล้วส่งออกไปคนละปลายทาง

Collector configuration ขนาดเล็กอาจมีหน้าตาแบบนี้

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  memory_limiter:
    check_interval: 1s
    limit_mib: 512
  batch: {}

exporters:
  otlphttp/backend:
    endpoint: https://telemetry.example.com
    headers:
      authorization: Bearer ${env:OTEL_EXPORTER_TOKEN}

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlphttp/backend]
    metrics:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlphttp/backend]
    logs:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlphttp/backend]
```

ตัวอย่างนี้มีไว้ให้เห็น shape ของ configuration ยังไม่ควรยกไปใช้ production ทั้งก้อนนะครับ Authentication, TLS, retries, queueing, resource limits, filtering และ high availability ยังต้องออกแบบเพิ่ม

## เริ่มด้วย Automatic Instrumentation แล้วค่อยเติม Business Context

Automatic instrumentation ช่วยเก็บ HTTP, database และ messaging spans ได้เร็ว แต่ไม่มีทางรู้เองว่า order ถูก accepted หรือ payment attempt นี้สำคัญอย่างไร

| วิธี | ทำอะไรได้ดี | ข้อจำกัด |
|---|---|---|
| Auto-instrumentation | Framework และ library calls ทั่วไป | ไม่รู้ business outcome ของระบบ |
| Manual instrumentation | Business spans, attributes และ custom metrics | ต้องแก้ code และดูแล naming ให้เป็นระบบ |
| Structured application events | Domain outcomes และ audit context | ต้องมี event schema ที่คงรูป |

สำหรับ Java เราใช้ OpenTelemetry Java agent เพื่อทำ zero-code instrumentation ให้หลาย libraries ได้ ส่วน Spring Boot รองรับทั้ง Micrometer Observation และการ export ผ่าน OTLP [OpenTelemetry Java](https://opentelemetry.io/docs/languages/java/), [Spring Boot Observability](https://docs.spring.io/spring-boot/reference/actuator/observability.html)

ลำดับที่ผมแนะนำคือ

1. เริ่มจาก auto-instrumentation สำหรับ calls ทั่วไป
2. กำหนด resource attributes เช่น service name, version และ environment ให้คงที่
3. เพิ่ม manual spans หรือ metrics เฉพาะ business boundary ที่สำคัญ
4. เพิ่ม structured domain events สำหรับ outcome ที่ต้อง audit หรือ recover
5. ตัด telemetry ที่ซ้ำหรือไม่มีใครใช้ออก ก่อนเก็บอย่างอื่นเพิ่ม

## Technology แต่ละตัวอยู่ส่วนไหน

ไม่มี product stack ชุดเดียวที่ทุกทีมต้องใช้ครับ ตารางนี้เป็นเพียงตัวอย่างว่า technology แต่ละกลุ่มอยู่ส่วนไหน

| Layer | Open-source examples | Managed หรือ cloud examples |
|---|---|---|
| Instrumentation | OpenTelemetry SDK และ agents, Micrometer, Prometheus client libraries | Vendor SDKs และ agents |
| Collection | OpenTelemetry Collector, Fluent Bit, Vector, Grafana Alloy | Cloud collectors และ agents |
| Metrics | Prometheus, VictoriaMetrics, Grafana Mimir | Amazon CloudWatch, Google Cloud Monitoring, Azure Monitor, Datadog, New Relic |
| Logs | Grafana Loki, OpenSearch, Elasticsearch | CloudWatch Logs, Google Cloud Logging, Azure Log Analytics, Datadog, Elastic Cloud |
| Traces | Jaeger, Grafana Tempo | AWS X-Ray, Google Cloud Trace, Azure Application Insights, Datadog, New Relic |
| Query และ dashboards | Grafana, OpenSearch Dashboards, Kibana | Cloud consoles และ vendor platforms |

ทีมขนาดเล็กอาจเริ่มด้วย Prometheus, Loki, Tempo, Grafana และ OpenTelemetry Collector 1 ชุด อีกทีมอาจเลือก managed platform เพราะการดูแล observability storage ไม่ใช่งานหลักของบริษัท

เวลาตัดสินใจ ผมจะดูเรื่องเหล่านี้

- ทีมมีความรู้กับ platform ไหนอยู่แล้ว
- Data volume และ retention เท่าไร
- ต้องใช้ query แบบไหน
- มีข้อกำหนดเรื่อง compliance และ data location หรือไม่
- ค่าใช้จ่ายและงาน operation เป็นอย่างไร
- Signals แต่ละแบบ link หากันได้ง่ายไหม
- ถ้าจะเปลี่ยน vendor ภายหลังต้องแก้อะไรบ้าง

## วัดผลลัพธ์ที่ User ต้องการ

Infrastructure health สำคัญ แต่ CPU ปกติไม่ได้แปลว่า product ให้ผลลัพธ์ที่ user ต้องการ

สำหรับ checkout เราอาจนิยาม service-level indicator แบบนี้

> Order request ที่ valid ต้องได้ผลลัพธ์ว่า accepted หรือ rejected ภายใน 3 วินาที และต้องไม่เกิด duplicate charge

จากประโยคนี้ ทีมสร้างได้ทั้ง

- **SLI:** สัดส่วนของ requests ที่ได้ผลลัพธ์และ latency ตามเงื่อนไข
- **SLO:** เป้าหมาย เช่น 99.9% ภายใน 28 วัน
- **error budget:** สัดส่วนที่ยอมให้พลาดจากเป้าหมาย

ตัวเลขนี้ควรเป็น decision ร่วมกันระหว่าง product และ engineering ยิ่งตั้งเป้าใกล้ 100% มากเท่าไร ระบบก็ยิ่งต้องลงทุนกับ redundancy, testing และ operation มากขึ้น

<MermaidDiagram chart={`
flowchart LR
    J["User journey"] --> S["SLI measures the outcome"]
    S --> O["SLO sets the target"]
    O --> B["Error budget tracks the gap"]
    B --> A{Needs action now?}
    A -->|Yes| P["Page with context"]
    A -->|No| W["Ticket or review"]
`} />

Alert ควรพาคนไปหา action ที่ทำต่อได้ครับ

| ปลายทาง | ใช้เมื่อ | ตัวอย่าง |
|---|---|---|
| Page | User กำลังเสีย outcome สำคัญ และคนที่รับ alert ช่วยได้ตอนนี้ | Checkout กำลังเผา error budget อย่างรวดเร็ว |
| Ticket | Trend นี้ควรแก้ แต่ยังไม่ต้องตอบสนองทันที | Error budget ลดช้า ๆ ต่อเนื่องหลายวัน |
| Dashboard | ข้อมูลช่วยให้เห็น context แต่ยังไม่มี action ที่ต้องทำทันที | JVM heap distribution แยกตาม instance |

Google SRE แนะนำ multiwindow, multi-burn-rate alerts เป็นจุดเริ่มต้นสำหรับ SLO alerting โดยเช็กทั้ง window ยาวและ window สั้น เพื่อให้ spike เก่าหยุด page เมื่อ failure ปัจจุบันจบไปแล้ว [Google SRE Workbook: Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/)

## ไล่ดู Checkout ที่ล้มเหลวหลังผ่านไป 18 วินาที

กลับมาที่ customer ซึ่งรอ 18 วินาที เราอาจไล่ investigation แบบนี้

1. Checkout SLO alert แสดงว่า slow requests เพิ่มขึ้นเล็กน้อย
2. Alert link ไปยัง time range และ deployment version ที่ได้รับผลกระทบ
3. PromQL บอกว่า p95 แย่ลงเพียงเล็กน้อย ทีมจึงไปดู slow tail ต่อ
4. Slow traces ใช้ payment provider และ retry path เดียวกัน
5. Logs แสดงว่า provider call แรก timeout หลัง 5 วินาที
6. Client library retry อีก 2 ครั้ง พร้อม backoff ที่ยาว
7. Payment สำเร็จ 1 ครั้ง และ idempotency ป้องกัน duplicate charge
8. Configuration change ล่าสุดเพิ่มทั้ง timeout และ retry count

ตอนนี้ทีมรู้ทั้ง cause, impact และ next action ที่ปลอดภัยแล้ว เราสามารถ rollback configuration เช็ก payment status และหา orders ที่ยังค้างอยู่ใน unknown state ต่อได้

## Observability ก็มี Failure Modes

ยิ่งเก็บ telemetry มาก cost และจุดที่ทีมต้องควบคุมก็ยิ่งเพิ่มตามครับ

| Risk | Problem ที่ตามมา | วิธีรับมือ |
|---|---|---|
| Cardinality | IDs หรือค่าที่ไม่จำกัดสร้าง metric series มากเกินไป | เก็บ IDs ไว้ใน logs และ traces พร้อม allowlist metric labels |
| Sampling | Rare failure trace ถูกทิ้ง | เลือกเก็บ errors และ slow traces ด้วย sampling policy ที่เหมาะ |
| Retention | Evidence หมดอายุก่อนเริ่ม investigation | กำหนด retention จากวิธีใช้ signal แต่ละแบบ |
| Sensitive data | Secrets หรือ personal data หลุดเข้า telemetry ที่ค้นหาได้ | Redact ตั้งแต่ต้น พร้อม access control, retention และ deletion |
| Pipeline failure | Collector หรือ exporter ทำข้อมูลหาย | Monitor telemetry pipeline และกำหนด buffering rule |
| Cost growth | ทุกทีมเก็บทุก field ไว้ตลอด | ตั้ง volume budget และ review fields ที่ไม่มีใครใช้ |

ถ้า telemetry collector ใช้งานไม่ได้ application ไม่ควรล้มตามทุกครั้ง ทีมต้องเลือกให้ได้ว่า signal ไหน drop ได้ buffer ได้ หรือควรส่งผ่านอีก path

## ค่อย ๆ เพิ่ม Observability ทีละ Layer

ผมจะค่อย ๆ เพิ่ม Observability ตามลำดับนี้

1. เลือก user journey ที่สำคัญ 1 อัน
2. นิยาม useful result กับ failure states
3. เพิ่ม metrics ชุดเล็กสำหรับ service และ dependencies
4. ใช้ structured events และ operation context ร่วมกัน
5. Trace path ข้าม service boundaries
6. สร้าง SLI และ SLO จาก user outcome
7. Alert เมื่อมีคนและ action ที่ช่วยสถานการณ์ได้
8. หลัง incident ให้ review cost, security และข้อมูลที่ยังขาด

Technology เปลี่ยนได้เรื่อย ๆ ส่วนคำถามที่มีประโยชน์ยังคล้ายเดิม

- User เจออะไร
- Path เริ่มช้าหรือ fail ที่ช่วงไหน
- System state อะไรอธิบายเหตุการณ์นั้นได้
- มี user กี่คนได้รับผลกระทบ
- ตอนนี้ทีมทำอะไรได้อย่างปลอดภัย

ถ้า telemetry ตอบคำถามเหล่านี้ไม่ได้ การเก็บข้อมูลแบบเดิมเพิ่มก็ไม่ช่วยครับ เริ่มจาก journey แล้วเพิ่ม signal เมื่อข้อมูลนั้นช่วยปิดคำถามที่ทีมยังตอบไม่ได้
