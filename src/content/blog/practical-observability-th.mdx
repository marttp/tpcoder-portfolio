## The Dashboard Is Green. The User Still Failed.

สมมุติว่า customer แจ้งว่า checkout ใช้เวลา 18 วินาทีแล้วจบด้วย error คุณเปิด dashboard ขึ้นมาดู

- CPU ปกติ
- Memory ปกติ
- Error rate ยังต่ำกว่า alert threshold
- ทุก service ขึ้น healthy

Dashboard เป็นสีเขียว แต่ customer ใช้งานไม่สำเร็จครับ

Monitoring บอกเราได้ว่า condition ที่รู้จักเริ่มผิดปกติหรือยัง ส่วน Observability ควรช่วยให้เราสืบต่อได้ แม้ทีมไม่เคยเตรียม dashboard สำหรับคำถามนั้นไว้ก่อน

OpenTelemetry อธิบาย Observability ว่าเป็นความสามารถในการเข้าใจระบบผ่าน signal ที่ระบบปล่อยออกมา และช่วยตอบคำถามว่าทำไมเหตุการณ์นี้ถึงเกิดขึ้น ระบบจึงต้องมี instrumentation ที่ใช้งานได้ เช่น traces, metrics และ logs [OpenTelemetry Observability Primer](https://opentelemetry.io/docs/concepts/observability-primer/)

ประเด็นหลักของบทความนี้คือ

**Observability ควรเริ่มจาก user journey และคำถามที่ทีมต้องตอบ ไม่ควรเริ่มจากการเก็บทุก signal ที่ tool รองรับ**

## Start with One User Journey

เราจะใช้ E-commerce checkout เป็นตัวอย่างครับ

1. Customer ส่ง order
2. Order service ขอ reserve inventory
3. Payment service ขอ authorize payment
4. Order service confirm order
5. Worker ส่ง receipt

ก่อนเลือก tool ลองเขียนคำถามที่ทีมควรตอบให้ได้ก่อน

- Customer ได้ response สำเร็จหรือเปล่า
- Checkout ทั้ง flow ใช้เวลาเท่าไร
- Dependency ตัวไหนใช้เวลามากที่สุด
- Payment สำเร็จ แต่ confirm order ล้มเหลวหรือไม่
- Retry ทำให้เกิด payment attempt อีกอันหรือเปล่า
- Problem เกิดเฉพาะ region, version, seller หรือ payment provider บางรายไหม

พอรู้ว่าจะตอบคำถามอะไร เราค่อยเลือกครับว่าเรื่องไหนควรดูจาก metrics, logs, traces หรือ events

## The Smallest Useful View

สำหรับ version แรก ผมจะเก็บเฉพาะข้อมูลที่ช่วยให้ทีมดูแล journey นี้ได้ก่อน

- request count
- success และ failure count
- latency distribution
- dependency errors และ latency
- structured logs ที่มี operation ID
- queue age และ failed jobs
- deployment version

ข้อมูลเท่านี้ช่วยตอบคำถามพื้นฐานได้หลายข้อแล้ว เช่น checkout fail เพิ่มขึ้นไหม latency เปลี่ยนหลัง release หรือเปล่า และ receipt jobs ค้างนานแค่ไหน

แต่ view นี้ยังมีข้อจำกัดครับ Metric แบบ aggregate อาจบอกว่า p95 latency อยู่ที่ 800 milliseconds ทั้งที่ customer กลุ่มเล็กต้องรอ 18 วินาที Log อาจมี payment timeout แต่ไม่เห็น inventory call ก่อนหน้า ส่วน trace อาจเห็น path ครบ แต่ไม่รู้ว่า business rule ข้อไหน reject order

ถ้าอยากอธิบายเหตุการณ์ให้ครบ เราจึงต้องใช้หลาย signals ประกอบกัน

## Give Each Signal a Job

### Metrics show shape over time

Metrics เหมาะกับ rate, distribution และ trend

- requests per second
- error ratio
- p50, p95 และ p99 latency
- queue depth และ age
- connection-pool usage
- payment-provider timeouts

ใช้ metrics เพื่อดูว่า **มี problem เกิดขึ้นหรือเปล่า** และมีผลกระทบกว้างแค่ไหน

ถ้า slow tail สำคัญ อย่าดูแต่ average เพราะค่าเฉลี่ยซ่อน user ที่รอนานกว่าคนอื่นได้

### Logs explain an event

Structured logs ควรอธิบาย event ด้วย field ที่ค้นหาได้

```json
{
  "event": "payment_authorization_failed",
  "order_id": "ord_84f2",
  "payment_attempt_id": "pay_18c1",
  "provider": "provider_a",
  "reason": "timeout",
  "duration_ms": 5032,
  "trace_id": "4bf92f3577b34da6"
}
```

อย่าเก็บ password, token, ข้อมูลบัตรแบบเต็ม หรือข้อมูล customer ที่ sensitive ลง log การทำ log ที่มีประโยชน์ไม่ได้แปลว่าต้อง copy input ทุก field

### Traces connect the path

Distributed trace เชื่อมงานข้าม services แต่ละ span แทน operation 1 ช่วง พร้อม timing, status และ attributes ที่ใช้สืบต่อได้

Slow checkout อาจมีหน้าตาแบบนี้

- inventory: 120 ms
- order database: 45 ms
- payment provider: 5,032 ms
- payment retry: อีก 5,010 ms
- response mapping: 20 ms

จากคำกว้าง ๆ ว่า **checkout ช้า** เราเริ่มตอบได้แล้วว่า **payment 2 attempts ใช้เวลาไปรวมประมาณ 10 วินาที**

### Events record meaningful changes

บาง event ควรมี durable history แยกจาก application logs ทั่วไป

- order accepted
- payment authorized
- refund requested
- permission changed
- deployment started
- feature flag changed

Event แบบนี้ช่วยได้ทั้ง audit, recovery และการตรวจสอบฝั่ง business ควรมี owner และ retention rule ระบุไว้ให้ครบ

## Context Connects the Signals

Signal แต่ละแบบจะมีประโยชน์ขึ้นมาก ถ้าเราเชื่อมกลับมาหา request หรืองานชิ้นเดียวกันได้

Field ที่พบได้บ่อย เช่น

- trace ID และ span ID
- operation หรือ request ID
- order ID หรือ job ID
- service และ version
- region และ environment
- dependency name
- result หรือ error category

OpenTelemetry Baggage ส่ง contextual key-value data ข้าม services และนำไปใช้กับ traces, metrics หรือ logs ได้ Documentation เตือนด้วยว่า baggage อาจเดินทางไปกับ headers และไม่มี integrity check ในตัว อย่าใส่ secrets หรือเอาข้อมูล authorization จาก baggage ไปเชื่อทันที [OpenTelemetry Baggage](https://opentelemetry.io/docs/concepts/signals/baggage/)

## Measure What the User Needs

Infrastructure health สำคัญ แต่ CPU ปกติไม่ได้แปลว่า product ให้ผลลัพธ์ที่ user ต้องการ

สำหรับ checkout เราอาจนิยาม outcome แบบนี้

> Order request ที่ valid ต้องได้ผลลัพธ์ว่า accepted หรือ rejected ภายใน 3 วินาที และต้องไม่เกิด duplicate charge

จากประโยคนี้ เราสร้างได้ทั้ง

- **SLI:** สัดส่วนของ checkout requests ที่ได้ผลลัพธ์และ latency ตามเงื่อนไข
- **SLO:** เป้าหมาย เช่น 99.9% ภายใน 28 วัน
- **error budget:** สัดส่วนที่ยอมให้พลาดจากเป้าหมาย

ตัวเลขนี้ควรเป็น decision ร่วมกันระหว่าง product และ engineering ยิ่งตั้งเป้าไว้ใกล้ 100% มากเท่าไร ระบบก็ยิ่งต้องลงทุนกับ redundancy, testing และ operation มากขึ้นครับ

Alert ควรชี้ไปยัง condition ที่ต้องมีคนลงมือทำ Google SRE อธิบายว่า monitoring ใช้สำหรับ alerting, investigation, visualization และ long-term planning และถ้าอยากเห็นการเติบโตของระบบ เราต้องเก็บข้อมูลนานพอ [Google SRE Workbook](https://sre.google/workbook/monitoring/)

ผมจะไม่รีบ page คนเพราะ 1 instance ใช้ CPU 80% อยู่ 2 นาที ผมจะ page เมื่อ user กำลังเสีย outcome สำคัญ และคนที่รับ alert มี action ที่ช่วยสถานการณ์ตอนนั้นได้ครับ

## Walk Through the Failure

กลับมาที่ customer ซึ่งรอ 18 วินาที เราอาจไล่ investigation แบบนี้

1. Checkout SLO alert แสดงว่า slow requests เพิ่มขึ้นเล็กน้อย
2. Alert link ไปหา traces ในช่วงเวลาและ version ที่ได้รับผลกระทบ
3. Slow traces ใช้ payment provider และ retry path เดียวกัน
4. Logs แสดงว่า call แรก timeout หลัง 5 วินาที
5. Client library retry อีก 2 ครั้ง พร้อม backoff ที่ยาว
6. Payment สำเร็จ 1 ครั้ง และ idempotency ป้องกันการ charge ซ้ำ
7. Configuration change ล่าสุดเพิ่ม timeout และ retry count

ตอนนี้ทีมรู้ทั้ง cause, impact และ next action ที่ปลอดภัยแล้ว เราสามารถ rollback configuration เช็ก payment status และตรวจต่อว่าไม่มี order ค้างอยู่

## Observability Has Its Own Failure Modes

ยิ่งเก็บ telemetry มาก cost และจุดที่ทีมต้องควบคุมก็ยิ่งเพิ่มตามครับ

### Cardinality

Metric label อย่าง `status=failed` มีค่าที่เป็นไปได้ไม่กี่แบบ ส่วน `order_id` อาจสร้าง time series หลายล้านชุด Field ที่ใช้ค้นหาเหตุการณ์ราย request ควรอยู่ใน signal ที่เหมาะกับงานนั้นครับ

### Sampling

เก็บทุก trace อาจแพงเกินไป Random sampling เรียบง่าย แต่อาจทิ้ง rare failure ส่วน tail sampling เก็บ slow หรือ failed traces หลังเห็นผลลัพธ์ได้ แลกกับ infrastructure ที่เพิ่มขึ้น

### Retention

Detailed traces ของช่วงล่าสุดช่วยตอนเกิด incident ส่วน aggregated metrics ระยะยาวช่วยเรื่อง capacity planning ข้อมูล 2 แบบนี้ไม่จำเป็นต้องเก็บนานเท่ากัน

### Sensitive data

Telemetry เดินทางผ่านหลายระบบและมักถูกค้นหาได้กว้าง ดูแล telemetry เหมือน data product ที่ต้องมี access control, redaction, retention และ deletion rule

### Pipeline failure

ถ้า telemetry collector ล้ม application ไม่ควรล้มตามไปด้วยทุกครั้ง ทีมควรเลือกให้ชัดว่า signal ไหน drop ได้ signal ไหน buffer ได้ หรือ signal ไหนต้องส่งผ่านอีก path แล้วอย่าลืม monitor observability pipeline ด้วยครับ

## Build It in Layers

ผมจะค่อย ๆ เพิ่ม Observability ตามลำดับนี้

1. เลือก user journey ที่สำคัญ 1 อัน
2. นิยาม useful result กับ failure states
3. เพิ่ม metrics ชุดเล็กสำหรับ service และ dependencies
4. ใช้ structured events และ operation context ร่วมกัน
5. Trace path ข้าม service boundaries
6. สร้าง SLI และ SLO จาก user outcome
7. Alert เฉพาะเมื่อมี action ที่ต้องทำ
8. หลัง incident ให้ review ทั้ง cost, security และข้อมูลที่ยังขาด

Tool เปลี่ยนได้เรื่อย ๆ ส่วนคำถามที่มีประโยชน์ยังคล้ายเดิม

- User เจออะไร
- Path เปลี่ยนที่ช่วงไหน
- System state อะไรอธิบายเหตุการณ์นั้นได้
- มี user กี่คนได้รับผลกระทบ
- ตอนนี้เราทำอะไรได้อย่างปลอดภัย

ถ้า telemetry ตอบคำถามเหล่านี้ไม่ได้ การเก็บข้อมูลแบบเดิมเพิ่มก็ไม่ช่วยครับ เริ่มจาก journey แล้วค่อยเพิ่ม signal เพื่อปิดคำถามถัดไปที่เรายังตอบไม่ได้
