พอเห็นอาจารย์ Andrew Ng ปล่อย The AI Engineering Skills Map ออกมาทีละส่วน ผมมีคำถามขึ้นมาว่า ถ้าเอา map นี้มาวางทับงานที่ผมทำอยู่ ภาพจะออกมาเป็นยังไง

อะไรที่พอมีพื้นอยู่แล้ว อะไรที่ผมกำลังเรียน แล้วมีเรื่องไหนบ้างที่เมื่อก่อนผมมองว่าไกลตัว แต่วันนี้เริ่มหนีไม่พ้น

บทความนี้เลยเป็นโน้ตที่ผมใช้ reflect งานตัวเองครับ ไม่ได้ตั้งใจเขียนเป็น roadmap ให้ทุกคนเดินตาม ผมจะเก็บไว้เป็น **living reflection** แล้วค่อยกลับมาเติมเมื่อ Skills Map หรืองานของผมเปลี่ยนไป

ภาพด้านบนมาจาก [The AI Engineering Skills Map ฉบับเปิดตัวของ Andrew Ng และ DeepLearning.AI](https://charonhub.deeplearning.ai/the-ai-engineering-skills-map/) ครับ ช่วงนี้ผมจะใช้ภาพจากบทความต้นทางเท่านั้น แล้วค่อยปรับภาพประกอบของบทความนี้ในรอบถัดไป

ณ วันที่ 12 กันยายน 2026 รายละเอียดออกมาครบทั้ง 4 กลุ่มใหญ่แล้ว:

- [Building and Deploying AI Applications](https://x.com/AndrewYNg/status/2090840747738374568)
- [Software Engineering Fundamentals](https://x.com/AndrewYNg/status/2093388974194872781)
- [Using Coding Agents](https://charonhub.deeplearning.ai/the-ai-engineering-skills-map-in-detail-using-coding-agents/)
- [Shaping the Build](https://charonhub.deeplearning.ai/the-ai-engineering-skills-map-in-detail-shaping-the-build/)

ถ้าคุณกำลังหาสรุป Skills Map ทุกช่อง บทความนี้อาจไม่ตอบโจทย์ครับ สิ่งที่ผมอยากรู้มีอยู่ประมาณนี้:

- ทักษะไหนกำลังใช้ในงานอยู่แล้ว
- ทักษะไหนเคยคิดว่าเป็นเรื่องรอง แต่กำลังมีน้ำหนักมากขึ้น
- งานแบบไหนที่ผมน่าจะขยับไปทำมากขึ้นในอนาคต
- ช่องว่างส่วนไหนที่ยังตอบตัวเองไม่ได้

พอไล่ดูครบ สิ่งที่ค้างอยู่ในหัวผมมีประโยคเดียวครับ:

**AI Engineering ไม่ได้ทำให้ Software Engineering เล็กลงครับ งานของ engineer กำลังขยายจากการเขียน code ไปสู่การกำหนดระบบ วัดผล คุมความเสี่ยง แล้วก็ช่วยเลือกว่าสิ่งไหนควรถูกสร้างขึ้นมา**

## The Map So Far

ก่อนจะเอา map มาส่องตัวเอง ขอแวะดูที่มาสักนิดครับ Andrew Ng กับทีมสร้าง Skills Map นี้จากประกาศงานมากกว่า 10,000 รายการ การสัมภาษณ์ AI experts, hiring managers และ recruiters รวมถึง survey กับข้อมูล online อื่น ๆ

เพราะงั้น Skills Map ชุดนี้เลยไม่ใช่ list เครื่องมือที่ใครคนหนึ่งใช้แล้วเอามาเรียงเป็น roadmap แต่เป็นภาพที่ทีมพยายามสกัดจากตลาดงานกับคนที่กำลังจ้างสายนี้อยู่

ผลลัพธ์ระดับบนมี 4 กลุ่ม:

1. **Building and Deploying AI Applications**
2. **Software Engineering Fundamentals**
3. **Using Coding Agents**
4. **Shaping the Build**

คำที่ผมสะดุดคือ **AI Engineering skills** ไม่ได้ถูกล็อกไว้กับตำแหน่ง AI Engineer ครับ Andrew เทียบกับ cloud skills ที่ developer หลายสายใช้กันอยู่ ถึงใน job title จะไม่มีคำว่า Cloud Engineer ก็ตาม

เออ พอมองแบบนี้ คำถามว่าจะเป็น Software Engineer หรือ AI Engineer ก็เบาลงเยอะ ผมไม่จำเป็นต้องทิ้งฝั่งหนึ่งเพื่อไปอีกฝั่ง งานน่าจะค่อย ๆ กลายเป็น Software Engineering ที่มี AI capabilities, coding agents และ evaluation loop อยู่ในงานเดียวกันมากกว่า

## Building and Deploying AI Applications

![AI Engineering Skills Map for Building and Deploying AI Applications](/assets/images/blogs/andrew-ng-ai-engineering-skills-map/building-and-deploying-ai-applications.webp)

ภาพจาก [Building and Deploying AI Applications โดย Andrew Ng และ DeepLearning.AI](https://charonhub.deeplearning.ai/he-ai-engineering-skills-map-in-detail-building-and-deploying-ai-applications/) ครับ

ส่วนแรกแบ่งออกเป็น 6 ทักษะ:

- LLM foundations
- Grounding models with data
- Building agentic systems
- Evaluation-driven development
- Operating in production
- Machine learning foundations

### What Already Connects with My Work

ถ้าคุณเคยเรียก model API ได้ครั้งแรก คุณน่าจะรู้ว่า demo ช่วงนั้นดูง่ายมากครับ ส่วนที่เชื่อมกับสิ่งที่ผมกำลังศึกษาและเขียนอยู่มากที่สุดคือ งานหลังจากนั้นต่างหาก เราจะพา model call ไปเป็นระบบที่ใช้งานได้ยังไง

ในบทความ [Practical AI System Design by TP Coder](/blog/practical-ai-system-design-from-model-call-to-reliable-product-th/) ผมวาง model ไว้เป็น component หนึ่งในระบบ รอบ ๆ ยังมี data, API, access control, evaluation, observability, cost และวิธีรับมือเมื่อ model ตอบพลาด

พอมาเห็น Andrew แยกงานกลุ่มนี้ออกเป็นช่อง ๆ ผมเลยลองเอาสิ่งที่ศึกษาอยู่มาเทียบดู:

- **Grounding models with data** เชื่อมกับการเลือกว่าจะใส่อะไรใน prompt, ให้ model เรียกข้อมูลผ่าน tool เมื่อไหร่ และ data representation แบบไหนเหมาะกับคำถาม
- **Building agentic systems** เชื่อมกับการออกแบบ loop, tools, memory, context, permission, fallback และจุดหยุดของ agent
- **Evaluation-driven development** เชื่อมกับการดู trace กับ error แล้วเลือกสิ่งที่จะปรับรอบถัดไป แทนการเปลี่ยน prompt ตามความรู้สึก
- **Operating in production** เชื่อมกับงานที่คุ้นเคยจาก backend และ cloud ทั้ง latency, reliability, observability, incident, security และ cost

พอเรียงแบบนี้ ผมกลับไม่ได้คิดถึงคำถามว่า model ตัวไหนเก่งที่สุดเท่าไหร่ครับ เรื่องที่วนอยู่ในหัวมากกว่าคือ context มาจากไหน เรารู้ได้ยังไงว่า output ดีพอ แล้วถ้าระบบพลาด เราย้อนกลับไปหาเหตุได้หรือเปล่า

### The Part I Need to Take More Seriously

ส่วนที่ผมวงไว้ให้ตัวเองเลยคือ **Machine Learning foundations**

ช่วงที่ LLM API ใช้ง่าย เราอาจสร้างของได้โดยยังไม่ต้อง train model เอง แต่ Andrew ย้ำว่า engineer ที่สร้างระบบ LLM ได้ดีมักเข้าใจ Machine Learning และ Deep Learning ในระดับหนึ่ง เพราะแนวคิดอย่าง bias/variance, error analysis, data quality, training กับ inference trade-offs ยังช่วยตัดสินใจในระบบที่ output มีความไม่แน่นอน

ผมไม่ได้ตีความว่าต้องกลับไปเริ่มด้วยการ train foundation model ครับ แค่รู้ว่าความเข้าใจของผมต้องลึกพอจะไล่ failure ได้ ไม่โยนทุกปัญหาให้ prompt แล้วก็ไม่ฝากการตัดสินใจไว้กับ model provider หมด

### My Current Reflection

ถ้าเอาหกช่องนี้มาวางข้างงานของผม ภาพตอนนี้ออกมาประมาณนี้ครับ:

- จุดแข็งของผมอยู่ฝั่ง system integration, backend, architecture และ production thinking
- Agent systems เป็นพื้นที่ที่กำลังเชื่อมความรู้เดิมกับงานแบบใหม่
- Evaluation ต้องกลายเป็น engineering loop ที่อยู่ในงานตั้งแต่ต้น ไม่ใช่ checklist ก่อน release
- ML foundations ยังเป็นช่องที่ต้องพัฒนาให้ลึกพอสำหรับการวิเคราะห์และเลือก trade-off

ผมยังไม่อยากให้คะแนนตัวเองเป็นตัวเลขครับ อ่านแล้วรู้จักแต่ละคำ กับเคยถือระบบที่ใช้ skill เหล่านั้นบน production ยังห่างกันอยู่เยอะ

## Software Engineering Fundamentals

![AI Engineering Skills Map for Software Engineering Fundamentals](/assets/images/blogs/andrew-ng-ai-engineering-skills-map/software-engineering-fundamentals.webp)

ภาพจาก [Software Engineering Fundamentals โดย Andrew Ng และ DeepLearning.AI](https://charonhub.deeplearning.ai/the-ai-engineering-skills-map-in-detail-software-engineering-fundamentals/) ครับ

ส่วนที่สองแบ่งออกเป็น 5 ทักษะ:

- Building full-stack applications
- Managing data
- Designing system architectures
- Making systems secure and reliable
- Scaling and operating in production

ส่วนนี้อ่านแล้วผมค่อนข้างสบายใจกับคำถามเรื่อง AI เขียน code แทนคนครับ Andrew บอกว่า ต่อให้ coding agent เขียน code ให้ทั้งหมด คนคุมงานก็ยังต้องรู้ว่ามี trade-off อะไรให้เลือกบ้าง ตั้งแต่ latency, availability, consistency, reliability, maintainability, simplicity ไปจนถึง cost

ถ้าคุณไม่รู้ว่ามีทางเลือกอะไร คุณก็ให้ context กับ agent ไม่พอ และไม่รู้ด้วยว่า output ที่ได้ยอมแลกอะไรไป

### Fundamentals Become Steering Context

เมื่อก่อน software fundamentals ช่วยให้เราเขียนและ review code ได้ดีขึ้น ตอนนี้ความรู้ชุดเดียวกันทำหน้าที่เป็น **steering context** ให้ coding agent ด้วยครับ

สมมุติว่า agent เสนอ microservices ให้ prototype ที่ยังมี user กลุ่มเล็ก ถ้าคนคุมงานไม่เข้าใจ deployment, network, data ownership และ operational cost คำตอบอาจดูเป็น architecture ที่ครบ แต่ทีมกลับต้องแบกความซับซ้อนเกินช่วงของ product

หรือถ้า agent เลือก database จากความคุ้นเคยของ training data โดยไม่ได้รู้ access pattern, retention, compliance และ volume ของระบบ งาน migration ที่ตามมาอาจแพงกว่าความเร็วที่ได้จากการ generate code รอบแรก

เพราะงั้น code ที่ออกมาเร็วขึ้นไม่ได้ลดคุณค่าของ system design ครับ กลับกัน เราต้องเลือกขอบเขตกับ trade-off บ่อยขึ้น เพราะ agent สร้างทางเลือกมาให้เร็วกว่าเดิม

### Why Backend Experience Still Matters

พอหันกลับมาดูงาน backend ที่ผมทำอยู่ ของเดิมหลายอย่างยังเอาไปต่อได้เยอะครับ:

- การออกแบบ API, authentication, state และ asynchronous processing
- การมอง data lifecycle มากกว่ามองเฉพาะ database schema
- การออกแบบระบบให้รับ failure ผ่าน timeout, retry, idempotency, fallback และ graceful degradation
- การใช้ CI/CD, observability และ incident feedback เพื่อให้ระบบพัฒนาต่อหลังขึ้น production
- การคุม permission กับ blast radius เมื่อ agent เรียก tool หรือแก้ state ได้

AI เพิ่ม component ที่คาดเดายากเข้ามา แต่ระบบยังต้องรับ request, อ่าน data, จัดการสิทธิ์, เรียก service, เก็บ state, วัดผล และ recovery เมื่อมีบางอย่างพลาด งาน backend ไม่ได้หายไปครับ ขอบเขตของงานกลับกว้างขึ้น

### Full-Stack Means Broader Judgment

อีกคำที่ทำให้ผมหยุดคิดคือ full-stack

Andrew ไม่ได้บอกว่าทุกคนต้องจำ syntax ของทุก framework เขากำลังชี้ว่า coding agents เปิดทางให้ engineer ข้ามไปทำงานในส่วนที่ไม่คุ้นเคยได้เร็วขึ้น แต่คนทำยังต้องเข้าใจว่า UI rendering, caching, API, session, persistence, testing, security และ accessibility เชื่อมกันอย่างไร

ผมเลยไม่ได้อ่านคำว่า full-stack ว่าต้องเก่งทุก layer เท่ากันครับ แค่ต้องมี mental model กว้างพอจะเห็นว่าการแก้ฝั่งหนึ่งไปกระทบอีกฝั่งยังไง แล้วรู้ด้วยว่าช่วงไหนควรหยุดเดาและดึงคนที่รู้กว่ามาช่วย

### My Current Reflection

สุดท้ายแล้ว ผมไม่ได้มอง software fundamentals เป็นของเก่าที่ต้องเรียนไว้กัน AI แย่งงานครับ ความรู้ชุดนี้คือภาษาที่เราใช้บอก agent ว่างานแบบไหนถึงเรียกว่าดีพอ

สิ่งที่เปลี่ยนคือ engineer อาจใช้เวลาน้อยลงกับการจำ syntax หรือพิมพ์ implementation ทีละบรรทัด แล้วขยับไปใช้เวลากับเรื่องเหล่านี้มากขึ้น:

- อธิบาย requirement และ constraint ที่ agent มองไม่เห็น
- review architecture กับ data decision
- ออกแบบ verifier, test และ release boundary
- ดู production behavior แล้วพาระบบแก้รอบถัดไป
- ลด technical debt ที่เกิดได้เร็วตามความเร็วของ code generation

code อาจสร้างได้เยอะขึ้นครับ แต่งานคุม architecture กับดูแลระบบไม่ได้เบาตามลงมาเลย

## Using Coding Agents

![AI Engineering Skills Map for Using Coding Agents](/assets/images/blogs/andrew-ng-ai-engineering-skills-map/using-coding-agents.webp)

ภาพจาก [Using Coding Agents โดย Andrew Ng และ DeepLearning.AI](https://charonhub.deeplearning.ai/the-ai-engineering-skills-map-in-detail-using-coding-agents/) ครับ

Andrew วาง workflow ไว้ 3 ช่วง:

- **Planning** — research, ทำความเข้าใจ codebase, เขียน spec, วาง architecture แล้วแตกเป็น execution plan
- **Execution** — สร้าง ทดสอบ และตรวจผล โดยเลือกสมดุลระหว่าง agent autonomy กับ human oversight
- **Deployment and monitoring** — ปล่อยงานผ่าน CI/CD หรือ human gate แล้วใช้ agent ช่วยดู log หา issue และเสนอการแก้รอบถัดไป

workflow สามช่วงนี้ไม่ได้ใหม่ครับ ทีม software ทำกันมาก่อนมี coding agent อยู่แล้ว ของที่เปลี่ยนคือน้ำหนักของงาน เราใช้เวลาพิมพ์ code น้อยลง แล้วเอาเวลาไปลงกับการเลือกว่าจะสร้างอะไร ออกแบบ architecture เขียน spec และยืนยันว่า output ใช้ได้

ถ้าคุณสร้าง prototype ใหม่ spec อาจเป็น prompt สั้น ๆ ก็พอ แต่ถ้าคุณแก้ระบบเดิมที่มี user กับ data อยู่แล้ว การวางแผนและ review assumptions ต้องละเอียดขึ้นเยอะ งานสองแบบนี้ใช้ autonomy ระดับเดียวกันไม่ได้ครับ

### Five Skills Behind the Workflow

Skills Map แบ่งการใช้ coding agents ออกเป็น 5 ทักษะ:

- Directing the workflow
- Enabling agent autonomy
- Reviewing the work
- Customizing the agent and its environment
- Coding agent foundations

ห้าข้อนี้ทำให้ผมเห็นเลยว่า **เรียก coding agent ให้สร้าง output ได้** กับ **ใช้ coding agent เป็น** ห่างกันพอสมควรครับ ได้ code กลับมาไม่ยากแล้ว ของยากคือพางานผ่านทั้ง loop โดยไม่หลุดเป้าหมาย ไม่เปิดสิทธิ์กว้างเกินไป และไม่กองงาน review ไว้ให้คนทีหลัง

### Autonomy Is Something We Calibrate

ก่อนอ่านส่วนนี้ ผมมีคำถามค้างอยู่ว่า งานไหนควรปล่อยให้ agent เดินเอง แล้วงานไหนเราควรแทรกระหว่างทาง คำตอบของ Andrew ไม่ได้เลือกข้างครับ เขามอง autonomy เป็นค่าที่ต้องปรับตามงาน

งานที่ขอบเขตเล็ก มี verifier ดี และย้อนกลับได้ อาจปล่อยให้ agent วนจนผ่าน goal ได้ ส่วนงานที่แตะ production data, security boundary หรือ architecture decision ยังควรมี human gate

การปล่อย agent ทำงานหลายชั่วโมงและใช้ token จำนวนมากอาจมีประโยชน์ในบางกรณีครับ แต่ Andrew เตือนว่าประโยชน์ของ long-horizon task ถูกพูดเกินสภาพการใช้งานตอนนี้ งานที่ได้ผลมักเป็น iterative loop ที่คนรู้ว่าเมื่อไหร่ควรเข้าไปช่วยเปลี่ยนทิศ แทนที่จะวัดความเก่งจากเวลาที่ agent ทำงานโดยไม่มีคนดู

ถ้าใช้หลาย agent พร้อมกัน เรื่องก็ไม่ได้จบแค่แบ่งงานครับ เรายังต้องดูว่าใครถือ context ไหน งานชนกันหรือเปล่า แล้วคนหนึ่งคนมี attention พอ review ทุก session ไหม เปิด concurrency เยอะขึ้นก็เร็วขึ้นได้ แต่ coordination cost วิ่งตามมาด้วย

### Context Is Part of the Engineering System

ช่วงนี้ใกล้กับวิธีทำงานของผมมากครับ เพราะผม customize ทั้ง agent และ environment อยู่เรื่อย ๆ

Context ไม่ได้มีเฉพาะ prompt ของรอบนั้น Context อาจอยู่ใน repository documentation, AGENTS.md, skill, memory, architecture note, test หรือ spec แต่ละแบบมีอายุและหน้าที่คนละอย่าง ถ้าเก็บ assumption เก่าไว้โดยไม่มีใครทบทวน agent ก็อาจทำตามข้อมูลเก่าอย่างสม่ำเสมอ ซึ่งไม่ได้ช่วยให้งานดีขึ้นครับ

Andrew พูดถึงการเพิ่มและเอา skill, plugin หรือ MCP server ออกตามความจำเป็นด้วย จุดนี้สำคัญเพราะ tool ที่เยอะขึ้นไม่ได้แปลว่า agent เก่งขึ้นทุกครั้ง Context กับ permission เพิ่มตามมาด้วย และบาง skill อาจหมดประโยชน์เมื่อ model หรือ workflow เปลี่ยน

ผมเลยเริ่มมอง environment ของ agent เป็น engineering system อีกชุดหนึ่งครับ มีทั้ง convention, version, review และ cleanup ถ้าปล่อยไว้ยาว ๆ เราอาจได้ agent-generated debt มาซ้อน technical debt เดิมอีกชั้น

### Review the Result and the Verifier

Andrew ให้น้ำหนักกับการ review งานมาก เพราะ output ของ coding agent ยังมีความไม่แน่นอน การตรวจจึงต้องเลือกให้เข้ากับสิ่งที่สร้าง:

- Functional verification เช็กว่า feature ทำงานตาม requirement
- Behavioral verification ดูพฤติกรรมที่ไม่ได้ตัดสินด้วย boolean ง่าย ๆ
- User-flow test หรือ screenshot ช่วยยืนยันสิ่งที่คนใช้จะเจอ
- Eval set กับ LLM-as-a-judge ใช้กับ output เชิงคุณภาพเมื่อเหมาะ
- Human review อยู่ในช่วงที่ risk หรือบริบทยังเกินกว่าจะ automate ได้

ประโยคที่ผมขีดไว้ให้ตัวเองคือ **เราต้อง review verifier ด้วย** ครับ ต่อให้ test ผ่านหมด ถ้า test วัดคนละเรื่องกับเป้าหมาย งานก็ยังพลาดได้ Agent อาจปิด loop ได้ไวมากแล้วบอกว่าสำเร็จ เพราะเราให้เส้นชัยผิดตั้งแต่แรก

### My Current Reflection

ในสี่กลุ่มของ Skills Map ส่วนนี้ใกล้กับงานประจำวันของผมที่สุดครับ ผมใช้ agent ช่วย research, เขียน, review, test และจัดการงานเป็นช่วง ๆ อยู่แล้ว พอเอา map มาส่องก็เห็นประมาณนี้:

- จุดแข็งของผมน่าจะอยู่ที่การกำหนด workflow, context และ verifier ให้เหมาะกับงาน
- การคุม permission กับ production boundary ต้องอยู่ใน design ตั้งแต่เริ่ม ไม่รอให้ agent พลาดก่อน
- Multi-agent มีประโยชน์เมื่อแบ่งงานได้ดี ถ้า decomposition ยังคลุมเครือ จำนวน agent จะขยายความสับสนตามไปด้วย
- Coding agent foundations ยังต้องเรียนต่อ เพราะถ้าไม่เข้าใจ context window, retrieval, harness และ subagent interaction เราจะวิเคราะห์ failure ได้ยาก
- Human attention เป็น resource ที่ต้องคุมพอ ๆ กับ token และ compute

ผมเลยไม่ค่อยอยากวัดตัวเองจากจำนวนงานที่โยนให้ agent แล้วครับ คำถามที่อยากถามมากกว่าคือ ของที่ส่งกลับมามีหลักฐานพอให้เชื่อไหม ผมยังถือ ownership ของผลลัพธ์อยู่หรือเปล่า แล้ว workflow รอบนี้เรียนรู้อะไรจากรอบก่อนได้บ้าง

## Shaping the Build

![AI Engineering Skills Map for Shaping the Build](/assets/images/blogs/andrew-ng-ai-engineering-skills-map/shaping-the-build.webp)

ภาพจาก [Shaping the Build โดย Andrew Ng และ DeepLearning.AI](https://charonhub.deeplearning.ai/the-ai-engineering-skills-map-in-detail-shaping-the-build/) ครับ

ส่วนสุดท้ายแบ่งออกเป็น 4 ทักษะ:

- Driving the build loop
- Making product decisions
- Communicating and leading
- High-agency ownership

ส่วนนี้สะกิดผมมากที่สุดครับ เพราะ Andrew ไม่ได้หยุดงาน engineer ไว้ที่การรับ spec แล้วเอาไป build เขามองว่าเมื่อเราสร้างของได้เร็วขึ้น เส้นระหว่าง developer, product manager และ designer ก็เริ่มซ้อนกันมากขึ้นด้วย

ไม่ได้หมายความว่า developer ทุกคนต้องกลายเป็น PM นะครับ แต่ spec ไม่มีทางครอบคลุมทุก decision อยู่แล้ว คนที่อยู่ใกล้ทั้ง technology กับ user problem เลยควรช่วยเลือก next step เก็บ feedback และพางานเดินต่อได้ โดยไม่ต้องรอคำสั่งทุกจังหวะ

### Drive the Loop, Not Only the Task

การสร้าง software เป็น loop อยู่แล้วครับ ทำของออกมานิดหนึ่ง เก็บ feedback แล้วค่อยเลือกว่าจะไปทางไหนต่อ พอ AI ทำให้แต่ละรอบสั้นลง ผมเลยรู้สึกว่าคำถามสำคัญขยับจาก **task นี้เสร็จหรือยัง** ไปเป็น **ทำอะไรต่อแล้วเราจะได้ข้อมูลหรือคุณค่ามากที่สุด**

บางช่วงทำ prototype เพื่อเช็ก technical feasibility ก็พอ บางช่วงควรเอา MVP ไปให้ user ลอง แล้วบางช่วงค่อยยอมจ่ายให้ production quality เรื่องยากไม่ใช่รู้จักคำพวกนี้ครับ เรื่องยากคือเลือกให้ถูกว่าตอนนี้งานอยู่ช่วงไหน

จุดนี้โยงกลับไปหา Using Coding Agents เต็ม ๆ Agent ช่วยเร่ง execution ได้ ส่วนคนยังเลือก loop กับ feedback อยู่ ถ้าเลือกโจทย์พลาด ความเร็วก็แค่พาเราไปผิดทางไวขึ้นครับ

### Product Sense Starts with User Empathy

พอมาเรื่อง Making product decisions รายการยาวตั้งแต่ product sense, design sense ไปจนถึง business sense เช่น go-to-market, market size, unit economics และ P&L ครับ แต่ต้นทางของทุกอย่างยังกลับมาที่ user empathy

สมมุติว่าเราออกแบบ architecture มาอย่างดี แต่ความเข้าใจ user ทั้งหมดมาจาก assumption สุดท้ายก็อาจกำลัง optimize ระบบให้โจทย์ที่ไม่มีน้ำหนักอยู่ดี วิธีเรียนรู้จาก user มีตั้งแต่คุยกัน 2–3 คน, ทำ survey, รัน A/B test ไปจนถึงดู behavior ของ user จำนวนมาก เลือกให้พอดีกับ stage ของ product ก็พอครับ

สิ่งที่ผมขาดเลยไม่ใช่การจำคำศัพท์ฝั่ง product ให้ครบครับ ของที่ต้องฝึกคือเอาข้อมูลจาก user, business และระบบมารวมกัน แล้วตัดสินใจออกมาให้คนอื่นเข้าใจได้ว่าเราเลือกอะไรและยอมแลกอะไร

### Communication Is Part of Delivery

พองานเลยออกไปนอก code เราก็ต้องคุยกับ product, design, marketing, finance และ legal มากขึ้นครับ

AI เปลี่ยนเร็ว คนที่อยู่นอก engineering อาจยังประเมินยากว่าอะไรทำได้ อะไรเสี่ยง หรือข้อเสนอไหนมี cost ซ่อนอยู่ ช่วงนี้ engineer เลยต้องช่วยแปล technical feasibility กับข้อจำกัดให้ทีมเอาไปตัดสินใจต่อได้

เมื่อก่อนผมอาจมองการสื่อสารเป็นงานที่ตามมาหลัง architecture เสร็จ ตอนนี้เริ่มมองใหม่ครับ ต่อให้ code ผ่าน test ถ้าทีมเข้าใจคนละภาพ งานก็ไปไม่ถึง outcome เดียวกันอยู่ดี

### High Agency Still Needs Boundaries

High-agency ownership เป็นคำที่อ่านแล้วดูดีมากครับ Andrew ใช้ในความหมายของการมองเห็นปัญหา เสนอทางแก้ ลงมือภายใต้ priority กับ constraint ขององค์กร และถือผลลัพธ์แบบ end-to-end โดยไม่รอ top-down direction ละเอียดทุกขั้น

แต่คำนี้ก็มีมุมที่ผมระวังนะครับ high agency ไม่ได้แปลว่าเดินข้าม owner, policy หรือ production gate เรื่องที่ย้อนกลับยากยังต้องเปิด assumption และคุยให้เห็นภาพเดียวกันก่อน ส่วนผลงานก็ควรวัดจาก value ที่เกิดขึ้น มากกว่านับจำนวน task ที่ปิดไป

พออ่านถึงช่วงนี้ ผมนึกถึง Forward Deployed Engineering มากที่สุดครับ Engineer ต้องเข้าใจ domain คุยกับ user หาโอกาส แล้วพา solution จาก implementation ไปถึงผลลัพธ์ ระหว่างทางก็ต้องรู้ว่าเมื่อไหร่ควรตัด scope หรือชวนคนที่เชี่ยวชาญด้านอื่นเข้ามา

### My Current Reflection

พอรายละเอียดออกมาครบ ผมเลยย้อนมาถามตัวเองประมาณนี้ครับ:

- ผมเข้าใจปัญหาของ user ลึกแค่ไหนก่อนเริ่มออกแบบ solution
- ผมแยกได้หรือยังว่าอะไรควรทำเป็น prototype และอะไรต้องออกแบบแบบ production ตั้งแต่ต้น
- เวลาสร้างได้เร็วขึ้น ผมเลือกหยุดสิ่งที่ไม่ควรสร้างได้เร็วขึ้นด้วยหรือเปล่า
- ผมอธิบาย cost, risk และ trade-off ให้คนที่ไม่ได้อยู่สาย engineering เข้าใจได้แค่ไหน
- งานส่วนไหนต้องอาศัย domain knowledge ที่ coding agent หาแทนจาก codebase ไม่ได้

ผมยังตอบไม่ได้ครบทุกข้อครับ แต่พอเห็นแล้วว่า gap ของตัวเองไม่ได้อยู่ฝั่ง technology อย่างเดียว ถ้าจะรับงานกว้างขึ้น ผมต้องฝึก product judgment, user empathy, communication และการขับ build loop ไปพร้อมกับ engineering

## What This May Mean for My Future Work

พออ่านครบทั้งสี่ส่วน ผมยังตอบไม่ได้หรอกครับว่า job title ในอนาคตของตัวเองจะชื่ออะไร แต่รู้แล้วว่างานคงไม่แคบลงเหลือแค่เขียน code ด้วย AI ให้เร็วที่สุด

งานที่ผมน่าจะขยับเข้าไปหามากขึ้นจะประมาณนี้:

- เปลี่ยนปัญหาของ product หรือ operation ให้เป็น system boundary ที่สร้างได้
- ออกแบบ AI application ให้ทำงานร่วมกับ data และระบบเดิม
- วาง evaluation กับ observability เพื่อดูว่าระบบช่วยงานได้แค่ไหน
- ใช้ coding agents เพิ่ม leverage โดยยังรักษา ownership ของ architecture และ production outcome
- ช่วยทีมคุยเรื่อง requirement, risk และ trade-off ด้วยภาษาที่เข้าใจร่วมกัน

พอเอามารวมกัน ภาพออกมาใกล้กับ **AI-enabled Software Engineer** หรือ **Forward Deployed Engineer** มากกว่าคนที่นั่งเขียน prompt อย่างเดียวครับ

ชื่ออาจไม่ได้สำคัญมากเท่างานที่ถืออยู่ครับ สิ่งที่ผมเริ่มเห็นคือเส้นระหว่าง Software, AI, Product และ Domain บางลงเรื่อย ๆ แล้วคนที่เชื่อมสี่ฝั่งนี้ได้ น่าจะมีพื้นที่สร้างผลลัพธ์ได้กว้างกว่าเดิม
