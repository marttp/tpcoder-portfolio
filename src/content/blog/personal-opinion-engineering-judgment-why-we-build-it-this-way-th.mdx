## Why This Post Exists

- วางกรอบว่าโพสต์นี้เป็นความเห็นส่วนตัวจากงานด้าน backend, payment และ financial services ไม่ได้เป็นสูตรเลือก Technology ที่ใช้ได้กับทุกองค์กร
- เริ่มจากปัญหาที่เจอบ่อย: บทสนทนาเรื่อง Technology มักจบอยู่ที่ความเร็ว ความนิยม หรือผล benchmark
- ตั้งแกนหลักของโพสต์: การเลือก Technology คือการตัดสินใจทางธุรกิจด้วย เพราะมีคนต้องรับต้นทุน ความเสี่ยง และรูปแบบการดูแลระบบต่อ
- ระบุขอบเขต: โพสต์นี้จะไม่จัดอันดับ Technology และไม่เดินซ้ำรอยบทความ system design
- เกริ่นคำถามที่จะพาไปสำรวจ: เจตนาแรกของเครื่องมือ ความเข้ากันกับปัญหา ผลต่อธุรกิจ ต้นทุนการเป็นเจ้าของ เศรษฐศาสตร์ในยุค AI และการเติบโตในสายงาน
- ยอมรับข้อจำกัด: กรอบคิดนี้ควรเปลี่ยนตามประสบการณ์ใหม่และ environment ที่ผู้เขียนยังไม่เคยเจอ

## Technology Has an Intention

- อธิบายว่า Technology หนึ่งชิ้นมักเริ่มจากปัญหาและข้อจำกัดที่เฉพาะเจาะจง ไม่ได้เริ่มจากเป้าหมายว่าจะเป็นเครื่องมือที่ “ดีที่สุด”
- แยกเจตนาแรกของเครื่องมือออกจากประโยชน์ข้างเคียง ผล benchmark หรือคำอธิบายที่ได้รับความนิยมในช่วงหนึ่ง
- ชวนถามว่าปัญหาและข้อจำกัดของเราใกล้กับ environment ที่ Technology นั้นถูกออกแบบมาหรือไม่
- มอง Technology เป็นชุดของสมมติฐานและ trade-off รวมถึงเงื่อนไขที่ทำให้เครื่องมือนั้นเริ่มไม่เหมาะ
- อธิบายความเสี่ยงของการเลือกตามบริษัทเดิม ทีมเดิม หรือ Engineer ที่เราเชื่อถือ โดยยังไม่เข้าใจเหตุผลเบื้องหลัง
- เว้นพื้นที่ไว้เติมการตัดสินใจจากประสบการณ์ส่วนตัวภายหลัง โดยไม่เปลี่ยนหัวข้อนี้ให้เป็นบทความเปรียบเทียบ Technology

## From Technical Choice to Business Consequence

- แปลงการเลือกทางเทคนิคให้เห็นผลต่อเวลาส่งมอบ ต้นทุนดูแล ผลกระทบเมื่อระบบล้ม compliance การพึ่ง vendor การจ้าง การ onboard และความยากในการย้อนการตัดสินใจ
- แยก technical metric ออกจากผลลัพธ์ของลูกค้าหรือธุรกิจที่เราคาดว่าจะดีขึ้น
- รวมงานระยะยาวที่มาพร้อมการเป็นเจ้าของระบบ: upgrade, observability, security, on-call support และความรู้ที่กระจุกอยู่กับคนไม่กี่คน
- ชวนถามว่าใครจะดูแลระบบนี้ในอีกสองปี และจะเกิดอะไรขึ้นเมื่อคนที่เข้าใจระบบลาออก
- วางการเลือก Technology เป็น co-decision ระหว่าง Engineering และ Business ภายใต้ข้อจำกัดร่วมกัน ไม่ได้หมายถึงให้ฝ่ายธุรกิจเป็นคนเลือก stack
- ยอมรับว่าตัวเลือกที่เรียบง่ายหรือทีมคุ้นเคยอาจเป็นการตัดสินใจทางธุรกิจที่แข็งแรงกว่า เมื่อขีดจำกัดของมันยังรับได้

## AI Changes the Cost Equation

- แยกต้นทุนการสร้าง code ออกจากต้นทุนการเป็นเจ้าของ Software ตลอดอายุการใช้งาน
- สำรวจจุดที่ AI ช่วยลดแรงเสียดทาน: investigation, scaffolding, implementation, documentation และการทำ test รอบแรก
- ตรวจดูสิ่งที่ยังแพงหรืออาจแพงขึ้น: verification, domain context, security, ความรับผิดชอบต่อ production และ maintenance
- ทบทวนเส้นแบ่งของการสร้าง Software ใช้ภายใน เมื่อการทดลองและ automation ขนาดเล็กมีต้นทุนลดลง
- พิจารณาว่า automation หรือ process design ที่เคยแพงจะเริ่มคุ้มไหม หากควบคุมต้นทุนการดูแลต่อได้
- เตือนว่า code ราคาถูกสร้าง complexity ราคาถูกตามมาได้ effort ตอน implement ที่ลดลงไม่ได้ลบความเสี่ยงจาก over-engineering
- เสนอกรอบเทียบต้นทุนก่อนและหลังมี AI เพื่อใช้ตรวจสอบกับประสบการณ์ส่วนตัว โดยไม่อ้างตัวเลข productivity ที่ใช้ได้กับทุกทีม
